# Sysacta — Phase 1C-1: ディスプレイ基本操作

## 目的と範囲

spec §7.2 / §8 / §9 / §10 / §12 に従い、Windows 11 のディスプレイ列挙・状態取得・輝度・コントラスト・利用可能な表示モードの列挙を実装する。Phase 1C-2（解像度/リフレッシュレート変更・電源・入力切替）は別 PR とし、今回は実装しない。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/phase-1a-progress.md、docs/phase-1b-progress.md、docs/phase-1b-exp-progress.md、docs/manual-tests.md と現行コードを確認する。最新 main を基点とする専用ブランチ（例: phase-1c-1）で作業し、独立した PR を作成する。自動マージしない。

Phase 0〜1B-EXP で確立した認証・認可・監査容量・要求予算・タイムアウト・排他・副作用開始点・部分結果の契約を維持する。通常のオーディオ機能と既存の JSON 契約を壊さない。オーディオの残課題（両方向の既定役割ロックの競合）は別修正タスクとし、本 PR に無関係な変更を混ぜない。

## 1. 技術調査

実装前に公式 Microsoft 文書、実際の API 契約、必要に応じ既存 OSS の利用実績を確認し、採否の根拠・参照 URL・ライセンス・対応環境・権限・制約を docs/phase-1c-1-progress.md に記録する。候補の API がすべての機器で利用できるとは仮定しない。

| 用途 | 調査候補 |
|---|---|
| 表示トポロジー・論理/物理対象の識別 | QueryDisplayConfig / DisplayConfigGetDeviceInfo / EnumDisplayMonitors / GetMonitorInfo |
| 現在の表示設定・利用可能モード | EnumDisplaySettingsEx / DisplayConfig のモード情報 |
| 外部モニターの輝度・コントラスト | Monitor Configuration API（Dxva2）・DDC/CI の high-level API |
| 内蔵パネルの輝度 | root\\WMI の WmiMonitorBrightness / WmiMonitorBrightnessMethods 等 |
| ハードウェア能力と物理ハンドル | GetMonitorCapabilities / GetPhysicalMonitorsFromHMONITOR / DestroyPhysicalMonitor(s) 等 |

- P/Invoke の構造体レイアウト、文字コード、配列・バッファ長、戻り値と Win32/HRESULT エラー、ハンドル所有権、x64 での ABI を公式定義に照合する。必要な範囲だけ宣言する。
- DDC/CI はモニター・接続経路・GPU・ドック・OSD 設定によって利用できない。能力フラグや MCCS 情報だけで実際の読み書き成功を保証しない。読み取り結果を優先し、問い合わせ失敗と明確な非対応を区別する。
- 内蔵パネル用 WMI は対象インスタンスと表示トポロジーを確実に対応付ける。最初のインスタンスを選ぶ、すべてのパネルに書く等の代替は禁止する。
- 同一デバイス・同一機能で複数方式が候補になる場合、確実に対応する方式を決める。書き込み失敗後に別方式へ自動フォールバックしない。
- 初期能力判定に状態変更を行わない。能力照会、DDC/CI、WMI を UI スレッドや認可前の無制限の同期処理で実行しない。
- 公式 API を優先する。非公開 API、任意 VCP 操作、外部 CLI、GUI 自動化、レジストリ直接操作、ドライバの追加、権限昇格は今回の対象外。疑似輝度（ガンマ変更・暗色オーバーレイ）でハードウェア輝度変更を代替しない。
- 依存追加は必要最小限とし、現行の中央パッケージ管理・依存方向を維持する。

## 2. ツール契約

| ツール | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| display_list_devices | なし | 読み取り | On |
| display_get_state | device? | 読み取り | On |
| display_set_brightness | level, device? | 状態変更 | On |
| display_set_contrast | level, device? | 状態変更 | On |
| display_list_modes | device | 読み取り | On |

新規 DB と新規クライアントの初期許可は現行ルールに従う。既存環境へ追加するツールは全体無効で登録し、既存クライアントには自動付与しない。

下記は初期 JSON 契約案。spec と既存の共通契約を優先し、細部の判断・実際のスキーマを進捗ログに記録する。

- level は必須の整数 0〜100。絶対値指定とし、相対変更・トグルを追加しない。
- device は OS 由来の正規 ID またはローカルで登録済みの別名。省略可能な場合はプライマリ表示を対象とする。明示 null、未知引数、空文字、制御文字、不正な型は既存の厳格な検証で拒否する。
- device=all は輝度変更のみの明示的一括指定として採用する初期案。コントラスト・状態取得・モード列挙では許可しない。default 等の予約語をデバイス別名に使わない。
- 状態取得は原則 5 秒、DDC/CI を含む呼び出しは 10 秒を初期案とする。一括処理は対象数・実測に応じた有限の全体予算を設け、理由を記録する。

## 3. ディスプレイ識別・トポロジー

論理ディスプレイ、表示ソース、表示ターゲット、物理モニターが常に 1 対 1 ではないことを前提とする。クローン表示、拡張表示、ドック、仮想ディスプレイ、複数の物理ハンドルを考慮する。

- DisplayConfig 等の OS が返す安定した対象情報を基に、ディスプレイの正規 ID を設計する。HMONITOR、物理ハンドル値、列挙順、名前、EDID の製品名だけを永続 ID にしない。
- OS のデバイスパス等を直接公開する必要がなければ、不透明な ID を利用する。元情報から決定的に解決でき、衝突や曖昧さを検出できる方式を選ぶ。無制限のキャッシュを持たない。
- 同じ表示名・同型番のモニターを識別する。安定 ID が再接続・ポート変更等で変わる場合はその制約を記録する。類似名による自動再紐付けは禁止する。
- プライマリ表示が複数の物理対象に対応していて一意に解決できない場合は AMBIGUOUS_TARGET 等で拒否する。ハードウェア操作の対象を列挙順から選ばない。
- 一時切断、トポロジー変更、ホットプラグに備え、ロック取得後にも同じ対象かを確認する。対象やプライマリが変わったら TARGET_CHANGED 等で副作用なく拒否する。解決した ID と異なる機器へ暗黙に変更しない。
- ローカルで確実に列挙できない切断機器について、登録済み別名の情報を利用して UI で管理できるようにする。接続されていると偽らない。

## 4. 読み取りツール

### display_list_devices

- 現在の表示トポロジーを列挙する。各項目には正規 ID、表示名、状態、プライマリかどうか、内蔵/外部/仮想/不明の区別（確実に分かる場合）、別名、対応操作を含める。
- 現在の解像度・リフレッシュレート等の取得可能な情報も返してよい。ただし列挙だけで全モニターへ時間のかかる DDC 問い合わせを強制しない。
- 機能ごとに対応 / 非対応 / 未確認・一時取得不能を区別する。未確認の機能を対応済みとして返さない。能力情報は機器・トポロジーの変化で再評価できるようにする。
- 空一覧、個別の取得失敗、列挙全体の API エラーを区別する。結果件数・サイズに上限を設け、切り詰めを明示する。ID や表示名だけの基本列挙は DDC 非対応でも利用可能にする。

### display_get_state

- device を省略した場合は一意に解決できるプライマリ表示。
- 対象 ID、表示名、接続状態、現在の表示解像度・リフレッシュレート、輝度、コントラスト、機能別の対応状況・取得エラーを返す案とする。
- 表示ソースの解像度と物理パネルのネイティブ解像度を混同しない。リフレッシュレートが分数で表現される場合は精度を保持する。
- 輝度・コントラストが非対応または取得不能なら null とし、0 として扱わない。各値がハードウェア値か内蔵パネルの OS 制御値かを説明する。
- 読み取りのみに限定する。取得できない情報を得るためにデバイスを変更しない。

### display_list_modes

- device 必須。ID/別名から一意に解決できる論理表示と物理対象の関係を検証する。
- OS から列挙できるモードのみ返す。mode_id、幅、高さ、リフレッシュレート、必要に応じスキャン方式・その他の識別に必要な属性、現在モードの情報を含める。
- mode_id は対象機器・モードの正規情報を含む決定的な識別子とし、異なるモードを誤って同一視しない。ID が再列挙・トポロジー変更で無効になる場合を文書化する。
- リフレッシュレートの 59.94 Hz / 60 Hz 等を表示上の丸めだけで同一扱いしない。OS が区別できない値を捏造しない。
- 列挙モードは「現在の環境で適用できることを保証する値」ではない。Phase 1C-2 では適用前の再列挙・検証が必要である旨を記載する。
- 今回はモード適用、CDS_TEST 等の変更試行、カスタムモード生成を行わない。件数上限と切り詰めを明示する。

## 5. 輝度・コントラストの変更

### 共通

- 公式 Monitor Configuration API 等で取得した最小・最大・現在値を使い、公開値 0〜100 とネイティブ値を相互変換する。範囲不正、min=max、取得不能、丸め、離散値、オーバーフローを考慮する。
- 内蔵パネルが離散輝度を提供する場合は対応値への丸めを明示し、同じ規則で目標値・読み戻しを比較する。要求値と実効目標値を区別する。
- 一般的な DDC/CI の値域を 0〜100 と決めつけない。機器が返した値域・対応値の外へ書き込まない。
- 読み取りで現在値が確認できない場合、既定では変更しない。明確な非対応なら NOT_SUPPORTED、一時的な通信エラーや切断なら OS_API_ERROR / DEVICE_DISCONNECTED 等を返す。
- 変更前の状態を確認し、実効目標値と一致していれば no-op / verified。変更する場合は最初の OS 書き込み直前に execution.BeginSideEffect() を呼び、変更後に読み戻す。
- DDC/CI の反映遅延がある場合は、有限の時間内で読み戻しだけを再試行してよい。書き込みを繰り返して一致させない。キャンセル・タイムアウトを尊重する。
- 検証不一致は VERIFICATION_FAILED、書き込み後に状態が分からない場合は unknown とする。API が受理したという事実だけで verified にしない。失敗でも変更された可能性がある API は未変更と断定しない。
- 結果は対象 ID、要求 level、実効目標、変更前後の値、changed、必要に応じネイティブ範囲と固定のエラーコードを含める。生の例外・デバイスパス・入力文字列をエラーに反映しない。
- コントラストは輝度とは独立した機能。対応していない機器に代替の操作を書き込まない。

### display_set_brightness の device=all

- 解決時に対象を有限の正規 ID 一覧へ確定し、全対象を表示/物理実体単位で重複排除する。クローン等で安全に一意化できない対象は操作しない。対象上限を超える場合は暗黙に一部だけ変更せず、開始前に拒否する。
- 各対象について変更前に能力・状態・実効目標値を確認する。非対応や一時切断を明示する。途中で新たに接続した機器を操作対象へ追加しない。
- 各対象のロックを既存 ResourceLocks の固定順序で取得し、開始点と後続の副作用を既存 ToolExecution で管理する。後続の OS 書き込み直前に BeginNextSideEffect を呼び、拒否・失効・タイムアウト後は新たな変更を開始しない。
- 個別の非対応・切断等はその対象の結果を記録する。副作用が不明なエラー・認可取り消し・キャンセル・全体タイムアウトでは残りの変更を中止する。副作用のない個別失敗後に継続する条件を限定して文書化する。
- すべての対象が目標に一致すれば success / verified。一部達成かつ未達があれば partial。副作用の有無が不明な対象があれば unknown。変更できた対象がなく目標未達の場合は error とする。既に目標値だった対象も明示する。
- ReportProgress で途中の各対象結果を保存する。未着手・成功/no-op・失敗・不明を区別し、MCP isError、監査 outcome、管理画面表示、outputSchema と整合させる。未着手対象や不明結果を成功として数えない。
- 無条件の再試行・ロールバックを行わない。単一対象操作と一括操作の実行経路を可能な範囲で共有する。

## 6. 排他・リソース管理

- Core に OS 非依存の必要最小限のインターフェースを定義し、Windows 固有 API を Sysacta.Windows/Display 等へ隔離する。Core に Win32 ハンドルや WMI オブジェクトを持ち込まない。
- すべてのツールを ToolCatalog に登録し、MCP とローカル動作確認は ToolExecutor を通す。既存の認可、pending 監査、要求予算、監査容量を迂回しない。
- 状態変更のロックキーは正規物理対象に基づく。輝度とコントラスト、将来の入力・電源変更で同一実体を共有する。論理 ID の違いで同じ物理モニターへのロックを分断しない。
- 同じ DDC/CI 経路への同時アクセスで通信が競合する場合に備える。既存 ToolExecutor は読み取り専用ツールに変更ロックを取らないため、Windows アダプター内の有限な直列化等で DDC/CI の読み取りと書き込みを安全に調停する。UI の列挙からも同じ調停を利用する。OS 書き込みを UI 独自の経路から実行しない。
- 共用バス・アダプター経路を確実に識別できない場合は、保守的な DDC/CI 直列化も許容する。待機が無制限にならないこと、共通ロックとの取得順、ネイティブ呼び出しが終わるまでの所有権を明確にする。
- タイムアウトでネイティブ処理が隔離された場合も、実処理終了まで関連ロック・スロット・ハンドルを保持する。後続の書き込みは開始しない。
- 物理モニターハンドルを永続化しない。所有するハンドルは成功・失敗・途中キャンセル・複数モニターの部分取得時にも解放する。解放前に処理が完了していることを保証する。WMI オブジェクトも適切に Dispose する。
- 能力判定 GetAvailability は安価・副作用なし・同期的な長時間 OS 呼び出しなし。特定機種の一時的非対応でカテゴリ全体を隠さない。恒常的な API 非対応と一時的な接続障害を区別する。
- 監査の allow-list は level 等の数値・列挙値だけ。解決済み target は OS/登録情報由来の安全な ID とする。一括指定は固定の識別子と必要な最小限の情報で表現し、生入力・任意配列・結果全文を記録しない。

## 7. デバイス管理画面

既存のオーディオ画面にディスプレイカテゴリを追加する。カテゴリ選択またはタブ等は既存 WPF UI の構成に合わせる。大規模な再設計はしない。

- 表示名、正規 ID、プライマリ、接続状態、能力・取得失敗、登録済み別名を表示する。
- ローカル UI から別名を登録・変更・削除・明示的な再紐付けができる。既存 AccessStore とカテゴリ内の一意性を維持し、ID/予約語との衝突を拒否する。オーディオの別名を誤って変更しない。
- 切断中や列挙失敗の登録済み機器も管理可能にする。自動再紐付けはしない。
- 列挙はバックグラウンドで有限に行い、UI 更新の競合・古い結果の上書き、連打による無制限の問い合わせを防ぐ。応答しない DDC/CI 機器でウィンドウを停止させない。
- デバイス一覧は MCP と共通の取得処理を利用する。表示のための読み取りに限り既存オーディオ画面と同様のローカル経路を許容する。
- 状態変更の専用スライダー、ディスプレイ設定アプリの代替、危険操作 UI は追加しない。既存ツールの動作確認 UI を利用する。
- ライト/ダーク、DPI、空・エラー・部分取得状態、キーボード操作を確認する。

## 8. テスト要件

### Core / Infrastructure / MCP

フェイクアダプターと一時 DB を使い、以下を検証する。

- 全 5 ツールのスキーマ、必須引数、未知引数、明示 null、範囲外、予約語、all の許可範囲。
- 既存 DB で新規ツール無効、既存トークンへ権限の自動付与なし、新規 DB の既定許可、直接呼び出し時の認可、能力判定。
- 同型番の複数機器、論理/物理の対応、複製表示、曖昧なプライマリ、切断、別名の衝突、ホットプラグ、ロック待機中の対象変更。
- 0 / 100 / 中間値、非標準 min/max、離散値、丸め、不正範囲、no-op、非対応、取得失敗、検証不一致、書き込み後の結果不明。
- モードの列挙、モード ID の一意性、同じ解像度で異なるリフレッシュレート、対象ごとのモード、切り詰め、API エラー。
- 同一物理対象への輝度・コントラストの排他、DDC/CI 読み取りとの調停、一括と単一の競合、異なる対象の独立性。ハング中のタイムアウト・ロック維持・解放、停止/再起動時のリソース管理。
- 初回書き込み前の失効・再発行・権限取り消し・期限切れ・監査容量不足で副作用ゼロ。
- 一括処理の部分成功、非対応混在、後続の再認可、キャンセル、タイムアウト、進捗報告、未着手対象への書き込みゼロ、重複物理対象への二重書き込みなし。
- pending と最終監査、MCP isError、outputSchema、結果の整合性。合成機密文字列が DB/WAL/CSV/JSON に残らない。
- 既存オーディオ・SEC-01/03/05/06・複数副作用の回帰テストを維持する。必要な基盤変更に限り、回帰テストを追加する。

### Windows 実機 / App

- 通常の Windows CI では読み取り・フェイクアダプター・XAML・アプリスモークテストを中心に行う。実機がない場合は明示的にスキップする。
- 読み取りで、接続方式、モニター名・型番（公開時は必要な範囲）、Windows ビルド、DDC/CI 設定、検出した能力、実行時間、対応方式を記録する。
- 外部モニターと内蔵パネルを別に検証する。存在しない種類は未検証とする。1 機種の成功をすべてのモニターの対応と見なさない。
- 輝度・コントラストの実機変更は SYSACTA_HARDWARE_TESTS=1 に加え、利用者が対象機器・変更幅を明示承認した場合のみ行う。元の値を取得・保存し、十分に視認可能な小さい変化に限定して finally 等で復元する。極端な 0/100 の実機変更・全機器一括変更は自動テストで行わない。
- 画面消失・復元不能の恐れ、必要な対応機器がない場合はスキップする。復元失敗は隠さない。製品側の自動リトライ/ロールバックとは区別する。
- モード変更・ディスプレイ電源 OFF・入力切替は実機でも CI でも行わない。
- 実際の MCP クライアント経由の確認は手動テストへ追加し、未実施は未実施と記録する。

## 9. 完了条件・成果物

- 5 ツールの実装と共通基盤への統合、ディスプレイの識別・能力判定、機器単位のエラー、対応機器でのハードウェア制御が設計されている。
