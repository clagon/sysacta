# Sysacta — Phase 0 実装

## 目的

`docs/spec.md` を正本として、SysactaのPhase 0を実装してください。

Phase 0の目的は、単にMCPサーバーを起動できるようにすることではなく、後続フェーズで別のコーディングエージェントや比較的能力の低いモデルでも、安全かつ一貫した方法で機能を追加できる開発基盤を確立することです。

## 作業方針

- 最初にREADME.mdとdocs/spec.mdを全文読み、既存のリポジトリ構成を確認してください。
- 仕様書に記載された合意事項を尊重し、確定済みの設計判断を独自に変更しないでください。
- 利用するSDK、ライブラリ、Windows APIについて、公式ドキュメントや実際のAPI定義を確認してください。存在しないAPIや古い使用方法を推測で実装しないでください。
- 未確定の実装詳細については、保守性、安全性、シンプルさを重視して自律的に判断してください。
- 重大な仕様変更、責務の変更、権限の拡大が必要な場合に限り、ユーザーに確認してください。
- 計画の提示だけで終了せず、実装、ビルド、テスト、修正まで進めてください。

## 実装範囲

### 1. プロジェクト基盤

仕様書に従って.NET 10 LTSのソリューションを構築してください。

- Sysacta.App
- Sysacta.Core
- Sysacta.Mcp
- Sysacta.Windows
- Sysacta.Infrastructure
- 各テストプロジェクト

プロジェクト間の依存方向を遵守してください。

依存パッケージのバージョンを一元管理し、再現可能なビルド環境を整備してください。過剰な抽象化や、将来使うかもしれない機能の先行実装は避けてください。

### 2. アプリケーションライフサイクル

- WPFアプリケーション
- タスクトレイ常駐
- 単一インスタンス制御
- MCPサーバーの開始・停止・再起動
- ウィンドウを閉じた場合のトレイ常駐
- 正常終了時のリソース解放
- Windowsログイン時の自動起動設定
- 現在の権限レベルの検出

UIスレッドをブロックしない構成とし、MCPホストとWPFのライフサイクルを適切に管理してください。

### 3. MCPサーバー

- 公式C# MCP SDK
- ASP.NET Core / Kestrel
- Streamable HTTP
- `/mcp` エンドポイント
- localhostをデフォルトとするバインド設定
- ポート番号の変更
- プロトコルバージョンの互換性
- 構造化されたツール入出力
- 共通エラーハンドリング
- リクエストのキャンセルとタイムアウト
- リクエストサイズ・レート・同時実行数の制限
- Host・Originの検証

SDKの現行仕様を確認し、認証主体ごとのツール一覧フィルタリングと実行時の認可が実際に機能する構成にしてください。

stdioやレガシーSSEの独立したエンドポイントは追加しないでください。

### 4. 認証・認可

複数のBearerトークンとクライアント別権限管理を実装してください。

- 暗号学的に安全なトークン生成
- トークンハッシュによる保存
- 固定時間比較
- 発行・失効・再発行・有効期限
- 最終利用日時
- サーバー全体の権限とクライアント別権限
- カテゴリ・ツール単位の設定
- 読み取り専用などの権限プリセット
- 設定変更の即時反映
- 認証主体ごとのtools/list
- tools/call実行時の独立した認可
- 待機中の操作に対する副作用発生直前の再認可

すべてのMCPリクエストに認証を適用してください。

ツール一覧から除外するだけで認可を成立させないでください。既知のツール名を直接呼び出した場合も、必ずサーバー側で拒否できる必要があります。

権限や認証設定をMCP経由で変更する手段は提供しないでください。

### 5. ツール実行基盤

後続フェーズで共通利用できる、シンプルで明確なツール実行基盤を構築してください。

- ツールの登録
- メタデータ・カテゴリ管理
- 入力スキーマとバリデーション
- 実行環境の能力判定
- ツールの利用可否判定
- 認可
- 対象リソースの識別
- リソース単位の排他制御
- 待機キューと同時実行制限
- タイムアウト
- 操作結果と検証状態
- 構造化エラー
- 監査ログ

各ツールが独自にセキュリティ処理を実装するのではなく、共通の実行経路によって必要な処理が適用される設計にしてください。

新しいツールの追加時に認証・認可・監査処理を実装し忘れる構造は避けてください。

キャンセル不能なネイティブ処理については、HTTPリクエストのタイムアウトだけで排他制御を解除しないよう考慮してください。

### 6. 永続化・監査ログ

SQLiteを使用し、仕様書に記載されたデータ管理基盤を実装してください。

- 設定
- ツール許可状態
- クライアント
- クライアント別権限
- デバイス別名
- 登録アプリ
- 監査ログ
- スキーママイグレーション

デバイス別名や登録アプリなど、後続フェーズで利用する機能はPhase 0で必要な範囲の基盤整備に留めてください。

監査ログは実行成功、失敗、拒否、認証失敗を記録し、保持期間、検索、フィルタリング、CSV・JSONエクスポートに対応してください。

トークン原文、認証ヘッダー、生の例外、機密情報などをログへ記録しないでください。

### 7. 管理コンソール

WPF + WPF UI + MVVMによって、モダンなWindows 11向け管理コンソールを実装してください。

Phase 0では以下の画面を実際に利用できる状態にしてください。

- 概要
- 接続設定
- ツール管理
- クライアント管理
- 監査ログ
- 一般設定

デバイス・アプリ管理画面については、後続フェーズで追加できる構成としてください。未実装の機能を動作可能に見せるダミーUIは作らないでください。

デザイン要件：

- Windows 11 Fluent Designとの親和性
- ライト・ダーク・OS追従テーマ
- 一貫した余白、タイポグラフィ、アイコン、視覚的階層
- 適切な情報密度
- 過剰なカード、装飾、グラデーションを避ける
- DPIスケーリング対応
- 空状態、読み込み状態、エラー状態の適切な表現
- 操作結果の明確なフィードバック
- 管理者権限で動作中の場合の明示

サンプルアプリのような外観ではなく、日常的に利用できるデスクトップユーティリティとして仕上げてください。

### 8. リファレンス実装

後続の機能追加における模範として、以下の2つの実ツールを先行実装してください。

- `audio_get_state`
- `audio_set_volume`

これらは本来Phase 1の機能ですが、Phase 0の共通基盤が実際のWindows API操作でも機能することを確認するための、最小限の垂直統合実装とします。

状態取得系と状態変更系の両方について、以下の処理を確立してください。

- MCPスキーマ
- 入力検証
- 認証・認可
- 対象デバイスの解決
- Windows APIアダプター
- 必要な排他制御
- 操作後の状態検証
- 構造化された実行結果
- 監査ログ
- 単体テスト
- 統合テスト

追加のPhase 1機能には原則着手しないでください。

テスト専用のモックツールが必要な場合は、製品ビルドで意図せず公開されない構造としてください。

## テスト要件

仕様書のテスト方針を遵守し、特に以下を重点的に検証してください。

- 認証情報なし・不正・期限切れ・失効済みトークン
- クライアント別のツール一覧
- 無効化されたツールの直接呼び出し
- サーバー全体の権限とクライアント別権限の組み合わせ
- 待機中のツールに対する権限変更・トークン失効
- Host・Originの不正な指定
- 不正な引数と未知の引数
- 排他制御と並列実行
- タイムアウト・キャンセル
- デバイス操作の失敗
- 監査ログへの機密情報の混入防止
- CSVエクスポートの数式注入対策
- 設定・DBのマイグレーション
- サーバー停止・再起動時のリソース解放

GitHub ActionsでWindows向けのビルドと自動テストを実行できるようにしてください。

物理デバイスやWindowsの対話セッションが必要なテストを実行できない場合は、その制約と手動確認手順を記録してください。未実施のテストを成功扱いしないでください。

## 後続エージェント向けの整備

Phase 0の成果を後続モデルが容易に理解・拡張できるよう、必要最小限のドキュメントを整備してください。

- `AGENTS.md`：開発規約、ビルド・テスト方法、依存方向、変更時に守るべき制約
- `docs/tools.md`：新規MCPツールの追加手順とリファレンス実装への参照
- `docs/security.md`：セキュリティ境界、認証・認可の実行経路、禁止事項
- `docs/manual-tests.md`：実機テスト手順と確認状況
- `README.md`：現在の実装状況と起動・接続方法

AGENTS.mdには仕様書全体を複製せず、エージェントが実装時に守るべき具体的なルールと参照先を記載してください。

特に、後続モデルが新しいツールを追加する際に、どのファイルを変更し、どの実装を参考にし、どのテストを追加すべきかを明確にしてください。

## 完了条件

以下を満たした時点でPhase 0を完了とします。

- Windows向けに正常にビルドできる。
- 実装した自動テストが成功する。
- 管理コンソールとタスクトレイの基盤が動作する。
- Bearerトークンの発行とMCP接続が可能である。
- クライアントごとの認証・認可が機能する。
- リファレンスツールが共通実行基盤を経由する。
- 操作履歴が適切に記録される。
- 後続エージェントが新規ツールを追加できる実装パターンとドキュメントが存在する。
- 実行できなかった実機テストや未検証事項が明記されている。

## 最終レビュー

実装完了前に、仕様との整合性、コード品質、セキュリティ、並列処理、リソース管理についてセルフレビューを実施してください。

発見した問題は可能な限り修正し、再度ビルドとテストを行ってください。

最終報告には以下を含めてください。

- 実装した機能
- 主要な設計判断とその理由
- 仕様書との差分
- ビルド・テスト結果
- 未検証事項と既知の制約
- 残存するセキュリティリスク
- 後続フェーズへの引き継ぎ事項

不要な機能追加や過剰な設計を避けながら、Phase 0の完成度を最大化してください。
