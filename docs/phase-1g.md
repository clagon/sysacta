# Sysacta — Phase 1G: 通知

## 目的と範囲

spec §7.9 / §8 / §9 / §10 / §15 に従い、Windows の標準デスクトップ通知を送信する MCP ツールを 1 つ追加する。送信元は Sysacta 固有、内容はテキストのみ。認可、通知の連投防止、プライバシー、API 受理と実際の表示の区別を重視する。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/manual-tests.md、docs/phase-1d-progress.md、docs/phase-1e-progress.md、docs/phase-1f-progress.md と現行コード・テストを読む。最新 main を基点とする専用ブランチ（例: phase-1g）で作業し、独立した PR を作成する。自動マージしない。

既存の認証・認可・監査容量・要求予算・副作用開始点・実行スロット・電源遷移ゲートを維持する。Phase 2 以降、過去フェーズの残課題、通知履歴の独自管理、スケジューラー、リモート通知、管理 UI 全体の再設計は対象外。

## 1. 技術調査・配布との互換性

実装前に Microsoft の公式文書、Windows SDK / Windows App SDK、.NET 10、通常権限の非パッケージ WPF アプリでの契約を確認し、採否・参照 URL・バージョン・ライセンス・依存関係・登録要件・未確認事項を docs/phase-1g-progress.md に記録する。

| 用途 | 調査候補 |
|---|---|
| 通知送信 | Windows App SDK の AppNotificationManager / AppNotificationBuilder |
| 代替 | 公式のデスクトップ向け Windows.UI.Notifications / ToastNotificationManager と必要なアプリ識別登録 |
| アプリ登録 | 非パッケージアプリの登録、AUMID、必要なショートカット/アクティベーション登録 |
| 能力確認 | 通知設定・登録状態の公式読み取り API |

- Windows App SDK を必須とはしない。公式にサポートされる方法の中から、依存・登録・配布・実行時の複雑さが最小のものを選ぶ。既存の .NET 10 / Windows SDK TFM、WPF、win-x64 自己完結型フォルダ配布、WSL クロスビルド、Windows CI / smoke への影響を確認する。
- Windows App SDK 採用時は自己完結型とフレームワーク依存の差、ランタイムの存在・バージョン、ブートストラップ、x64 配布物、ライセンスを確認する。追加 NuGet は中央管理し、必要最小限とする。既存 TFM や全体のビルド設定を不必要に変更しない。
- Core は OS 非依存の型とインターフェースのみ。Windows 固有の処理は Sysacta.Windows/Notification 等、WPF のライフサイクルとの接続は App の構成ルートに分ける。COM/WinRT のスレッド・アパートメント、Dispatcher への依存、登録/解放の寿命を調査する。
- 外部 CLI、PowerShell、非公開 API、他アプリへの通知偽装、任意プロセス起動、権限昇格、サービス導入、通知設定や集中モードの変更は禁止する。単なるトレイバルーンや WPF の独自ポップアップを Windows 標準通知の成功として返さない。

### 登録とライフサイクル

- 固定の Sysacta アプリ ID・送信元・表示名を使用し、別アプリの ID や送信元を引数で指定できないようにする。通知のアイコンが必要な場合はアプリ同梱の固定リソースのみ。
- 登録はアプリ自身のローカルな起動/セットアップ/インストーラーに限定する。MCP 呼び出しをきっかけにショートカット、レジストリ、COM 登録、ランタイムのインストール、OS 設定を変更しない。通常ユーザーの範囲を超えない。
- ポータブル版（ZIP 展開した自己完結型 exe）とユーザー単位 Inno Setup 版での登録方法を検討する。既存の配布方針を維持し、登録の所有範囲、実行ファイル移動・更新・再起動・アンインストール、同一アプリ ID の競合を考慮する。他アプリの登録を上書き/削除しない。
- 現段階でインストーラーが存在しない場合は、ローカルに必要な最小の登録方式を実装し、インストーラー連携の要件と検証手順を Phase 3 に引き継ぐ。実物を使った検証なしに両配布形式を対応済みとしない。配布システム全体を今回追加しない。
- 起動時登録が失敗しても通知以外のツールやアプリ全体を停止させない。恒常的非対応、登録不足、通知無効、一時 API エラーを区別する。GetAvailability は安価で副作用なし。UI に固定文言の理由を表示する。
- 既存の単一起動制御を利用し、登録とコールバックの重複・リークを防ぐ。MCP ホスト再起動だけで通知アダプターや連投制限を再生成しない。アプリ終了時は進行中のネイティブ処理との競合を避け、安全に解放する。
- 通知クリック/アクティベーションが登録上必要な場合、既定動作を最小化する。入力されたデータを解析してツール実行・ファイルアクセス・URL オープン・コマンド実行を行わない。OS 固有のクリック挙動と制約は記録する。

## 2. ツール契約

| ツール | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| notification_send | title, body | 状態変更 | On |

- title / body は必須の文字列。初期案は title 1〜64、body 1〜256 UTF-16 コード単位（JSON Schema の文字数と .NET の文字数の違いも考慮して実測・明記する）。空/空白のみ、明示 null、型不正、未知引数、上限超過、無効な UTF-16、禁止制御文字を拒否する。上限で黙って切り詰めない。
- title は単一行、body の通常の改行は許可してよい（CRLF 正規化等は明記）。NUL・その他の制御文字・双方向制御等の表示偽装に利用され得る文字は拒否する。日本語、通常の Unicode、絵文字が利用できることをテストする。正当な絵文字の結合文字まで無条件に禁止しない。
- ユーザー指定の XML/HTML テンプレート、画像、音声、ボタン、リンク、アクション、起動引数、送信元、優先度、緊急フラグ、任意 ID、置換、通知時刻/スケジュールは提供しない。明示的な URL/URI を通知の起動先として受け取ることは不可。本文もプレーンテキストのみで、リンク化・マークアップ解釈を行わない。OS 側で文字列がリンク化される等の挙動を確認し、安全に制御できない形式は拒否する。
- テキストを XML や通知テンプレートに入れる必要がある場合は、公式ビルダーまたは DOM のテキストノードなど構造化 API を使う。文字列連結による XML/引数生成は行わない。<、>、&、引用符等が文字として表示されることを確認する。
- 新規 DB は On、既存 DB への追加は無効、既存クライアントへの自動付与なし。既存の全体・クライアント別許可、失効、直接呼び出し拒否を維持する。
- 既存の SysactaTool<TArgs,TData>、厳格な JSON Schema / outputSchema、ToolCatalog 登録を利用する。ReadOnly: false、Transition なし、AuditedArguments は空。ローカル管理画面の動作確認も共通 executor を経由し、実際に通知を送る旨を明示する。
- 既定タイムアウト 5 秒。API の実測で変更する場合は理由を記録する。

## 3. 連投防止

既存 HTTP 要求予算（クライアント単位 60 件/分等）だけでは通知スパムを抑えられない。通知送信固有の上限を Core に設ける。

- 初期案は全体で直近 60 秒間に最大 5 回の OS 送信開始、送信開始間隔は最低 2 秒。トークン複数・再発行・異なる接続元・ローカル動作確認からの呼び出しも同一の上限を共有する。追加のクライアント別上限・設定 UI・DB は今回必須としない。数値は実用性を踏まえて調整してよいが、根拠を記録する。
- プロセス内で一つの有限な状態を持ち、TimeProvider 等の単調時刻で計算する。壁時計変更・時刻逆転・ウィンドウ境界の連投・並行要求を考慮する。タイトル/本文をキーにせず、内容を保持しない。通知単位の無制限な履歴・タイマー・バックグラウンドキューを作らない。
- 送信は共通のリソースキー（例: notification:send）で直列化し、上限の確認・枠確保と実際の開始を競合なく扱う。上限超過は BUSY 等の構造化エラー、何も送らない。待機による自動送信・間隔調整・自動再試行はしない。必要なら固定の retry_after_ms を安全な結果契約で返す。
- 最終認可・キャンセルで開始前に拒否された要求は、OS への送信枠を消費しない設計を初期案とする。副作用開始後は OS の拒否・例外・タイムアウト・受理不明でも枠を消費する。予約/確定/解除の順序を明記し、認可後に時間のかかる準備を挟まない。
- MCP ホストの停止/再開や権限変更、設定変更では上限をリセットしない。アプリプロセス再起動でのリセットは残存制約として記録する（永続レート制限は今回不要）。共通 HTTP 予算と監査容量を迂回しない。

## 4. 実行フロー・結果契約

1. 共通 executor の認可、引数検証、電源遷移ゲート、対象ロック、監査 pending の永続化を通る。
2. 登録/通知 API の利用可否、テキストの検証、送信枠、ネイティブ引数の生成を確認する。能力判定を送信で行わない。
3. 必要な準備を完了してからキャンセルを確認し、execution.BeginSideEffect() で最終認可する。その直後に固定の通知 API を 1 回だけ呼ぶ。
4. API の戻り値/例外を公式契約に従って解釈する。結果の証拠を得たら必要に応じ ReportAccepted を使い、監査結果と応答を返す。

- Dispatcher や専用スレッドが必要なら、そこで最終認可から OS 呼び出しまでを行う。開始点の後にキューへ投入し、タイムアウト後に遅れて送信する設計は禁止。キャンセルや失効後の未開始要求が拒否されることを確認する。
- 通知 API が受理した場合は success / accepted とする。ユーザーが見た、バナーが表示された、通知センターへ残った等を API 戻り値だけで断定しない。集中モード、通知設定、ロック状態、OS 側の抑制・失敗を文書化する。
- 結果は accepted（不明なら null）等の最小の型付きデータに限定する。title/body のエコーや通知ペイロード、XML、内部登録パス、OS 内部情報は返さない。不要な通知 ID を外部に公開しない。
- 確実な開始前拒否は error、開始後に受理・副作用が不明な場合は unknown、明確に受理された場合は accepted。開始後の retryable=false。二重通知を避けるため自動再送・別 API へのフォールバックをしない。
- ネイティブ呼び出しがキャンセル不能なら、既存 executor の隔離を利用し、実完了までロック、実行スロット、電源遷移ゲートの共有 admission、アダプター参照を保持する。準備処理のキャンセルも伝播し、追加の送信を始めない。
- UI スレッド上でブロッキング処理をしない。初期化や登録がハングしても無制限に Task/Dispatcher キューを増やさない。

## 5. プライバシーと通知の悪用防止

- 監査ではタイトル・本文の両方を常にマスク（保存しない）。生の入力、XML/ペイロード、例外全文、内部パスを DB/WAL/CSV/JSON、診断ログ、エラー文、UI エラーへ出さない。固定のエラー文、ツール名、結果、所要時間等だけを既存監査契約に従い記録する。
- 通知本文は OS の通知センター・ロック画面・他の人が見られる画面に残る可能性がある。OS の保持・同期・表示設定は Sysacta が制御できない。秘密、認証情報、個人情報を送らないようツール説明と docs/security.md に記載する。送信内容の任意の秘密を検出できるとは主張しない。
- Sysacta 固有の送信元と通常の通知優先度を使う。アラーム・着信・システム警告を装う scenario、他アプリや Windows の送信元への偽装、通知設定の回避、ロック画面上の特別な権限を要求しない。
- 通知をクリックしたことを MCP の認可、確認、外部コマンド、追加処理のトリガーにしない。本文のテキストを命令として実行しない。
- ローカル UI は既存のツール/クライアント/監査ページへの統合で十分。通知履歴取得/削除、他アプリの通知取得、通知アクション管理、Webhook、スケジュールは対象外。

## 6. テスト要件

### Core / MCP / Infrastructure

- title/body の必須・型・null・空白・未知引数・長さ境界・Unicode/日本語/絵文字・改行・禁止文字・無効 UTF-16 を検証する。JSON Schema と実際の検証の整合、特殊文字がテキストとして扱われることを確認する。
- On / ReadOnly false、新規 DB の既定、既存 DB の無効、既存クライアントに付与なし、未許可/全体無効/失効した直接呼び出しでは OS API 0 回。
- 共有レート制限の間隔、ローリング窓、境界値、複数クライアント、再発行、ローカル動作確認、同時実行、ホスト再開、時刻変更、開始前拒否、開始後失敗/unknown を決定的な時刻とフェイクで確認する。
- 監査 pending が送信開始より先、監査不能時は送信しない、準備中の権限剥奪・再発行・期限切れ・全体無効・キャンセル・タイムアウトで送信 0 回。
- 受理/失敗/不明、OS 通知設定の非対応、登録失敗、API 例外、キャンセル不能な処理の終了までロック保持、電源遷移時に開始しないことを確認する。重複通知や自動再送がないこと。
- 合成の秘密を title/body/例外等に入れ、監査 DB/WAL/CSV/JSON・診断ログ・エラー応答に残らないことを確認する。出力スキーマに本文が存在しないこと。
- 過去フェーズの認可・監査・電源ゲート・ローカル専用ツール・accepted progress の回帰テストを維持する。

### Windows / App / 実機

- CI と通常の自動テストは送信フェイクを使う。実通知を勝手に表示せず、登録/アンインストールの実操作・通知設定変更・外部アプリ起動を行わない。公式ビルダー等のペイロード生成は副作用なしで検証する。Windows CI の Release build / test / smoke を維持する。
- 実機通知は利用者が対象 PC・送信内容を明示承認した場合の手動確認に限定する。固定の無害なテスト文言を 1 件送る。通知の連投・スパムを実機で試さず、レート上限はフェイクで検証する。
- 通常権限の Windows 11、非パッケージ WPF の実アプリで登録、Sysacta の送信元、タイトル/本文（日本語・特殊文字）、実際の表示、クリック時に任意処理を開始しないことを確認する。通知設定や集中モードは勝手に変更しない。無効環境では表示されないことと結果契約を区別して記録する。
- 自己完結型フォルダ配布を別パスへ展開した起動・再起動、MCP クライアントからの許可/送信/監査を確認する。既存インストーラーがある場合はユーザー単位の登録・更新・アンインストールを確認する。存在しない場合や未承認・未確認の項目は Phase 3 の手動チェックリストへ明記する。
- 管理画面の通知カテゴリ、全体・クライアント許可、ローカル動作確認、登録失敗表示を確認する。実機未検証を自動テスト成功と混同しない。

- 文字数/制御文字、XML/アクション注入防止、固定送信元、全体レート制限、最終認可と永続監査、電源遷移ゲート、API 受理と実表示の区別を検証する。
- dotnet build Sysacta.sln -c Release が警告・エラーゼロ、dotnet test Sysacta.sln -c Release と Windows CI / スモークテストが成功する。
- docs/phase-1g-progress.md に API 採否・参照 URL・依存/ライセンス、登録と寿命、配布方式別の検証、文字列契約、連投制限、プライバシー、テスト、未確認事項、仕様との差分、残存リスクを記録する。
- README.md、docs/tools.md、docs/security.md、docs/manual-tests.md を実態に合わせて更新する。AGENTS.md の追記は共通ルールが必要な場合のみ。
