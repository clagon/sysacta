# Sysacta — Phase 1D: メディア制御

## 目的と範囲

spec §7.3 / §8 / §9 / §10 に従い、Windows 11 の GlobalSystemMediaTransportControlsSessionManager (GSMTC) を使ったメディアセッションの列挙、状態取得、再生操作を実装する。対象は Windows のシステムメディアコントロールにセッションを公開するアプリに限る。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/manual-tests.md、docs/phase-1b-progress.md、docs/phase-1b-exp-progress.md、docs/phase-1c-1-progress.md、docs/phase-1c-2-progress.md と現行コード・テストを読む。最新 main を基点とする専用ブランチ（例: phase-1d）で作業し、独立した PR を作成する。自動マージしない。

既存の認証・認可・監査容量・要求予算・排他・タイムアウト・対象識別・副作用開始点を維持する。オーディオの残課題、ディスプレイの追加機能、Phase 1E 以降、管理 UI 全体の再設計は今回の対象外。

## 1. 技術調査

実装前に Microsoft の公式文書と実際の Windows SDK / .NET 10 の契約を確認し、採否・参照 URL・必要な依存関係・ライセンス・権限・対応環境・制約を docs/phase-1d-progress.md に記録する。

| 用途 | API 候補 |
|---|---|
| セッションの取得 | GlobalSystemMediaTransportControlsSessionManager.RequestAsync / GetSessions / GetCurrentSession |
| セッションの変化 | SessionsChanged / CurrentSessionChanged |
| 再生状態と操作可否 | GetPlaybackInfo / GlobalSystemMediaTransportControlsSessionPlaybackControls |
| メディア情報 | TryGetMediaPropertiesAsync |
| 再生位置・範囲 | GetTimelineProperties |
| 再生操作 | TryPlayAsync / TryPauseAsync / TryStopAsync |
| 曲送り・曲戻し | TrySkipNextAsync / TrySkipPreviousAsync |
| シーク | TryChangePlaybackPositionAsync |

- 非パッケージ WPF デスクトップアプリ、通常ユーザー、ログオン中のセッション、自立型 win-x64 配布で GSMTC が利用できるか確認する。UWP の宣言や権限を無条件に前提にしない。
- Windows SDK の TFM / C#/WinRT 投影、COM/WinRT アパートメント、非同期 API、イベント購読・解放、スレッド間利用、.NET 10 との互換性を調査する。必要な最小 Windows SDK バージョンを根拠付きで選び、既存プロジェクト・Windows.Tests・WSL ビルドへの影響を確認する。
- Core は OS 非依存を維持し、WinRT の型を持ち込まない。Windows 固有処理は Sysacta.Windows/Media 等へ隔離する。依存追加は必要最小限とし、中央パッケージ管理に従う。
- API が返す bool と例外の意味、非同期操作の開始点・完了・キャンセルの保証を確認する。アプリが要求を受理したことと実際に再生状態が変わったことを区別する。
- 公式 API のみで実現する。任意のメディアキー送信、SendInput、アプリ個別 API、ブラウザ自動化、外部 CLI、非公開 API、権限昇格へフォールバックしない。
- 音声のキャプチャ、再生ファイル、URL、アルバム画像、サムネイルの取得・転送は行わない。

## 2. ツール契約

| ツール | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| media_get_state | session_id? | 読み取り | On |
| media_list_sessions | なし | 読み取り | On |
| media_play | session_id? | 状態変更 | On |
| media_pause | session_id? | 状態変更 | On |
| media_stop | session_id? | 状態変更 | On |
| media_next_track | session_id? | 状態変更 | On |
| media_previous_track | session_id? | 状態変更 | On |
| media_seek | position_ms, session_id? | 状態変更 | On |

新規 DB は spec の既定許可に従う。アップグレードで追加する 8 ツールは無効、既存クライアントに自動付与しない。新規クライアントの許可は既存のスナップショット方式を維持する。

- session_id は列挙で取得した不透明なセッション ID。省略した場合に限り、GSMTC の GetCurrentSession が返す現在のセッションを使う。再生中の先頭・最後に使ったアプリ等で代替しない。
- 明示 null、空文字、制御文字、長過ぎる文字列、未知引数、型の暗黙変換、all/default 等の予約語、名前による指定は拒否する。セッションは一時的な実体であるため、今回は別名登録・永続紐付け・一括操作を追加しない。
- position_ms は必須の非負整数（long）。単位はミリ秒。TimeSpan/WinRT の ticks（100 ns）へ変換するときは checked 等でオーバーフローを防止する。上限は変換可能な範囲と当該セッションの現在のシーク範囲の両方で検証する。
- すべてのツールは既存の SysactaTool<TArgs,TData>、厳格な JSON Schema、outputSchema、構造化結果、ToolCatalog 登録を使用する。説明とエラーは英語、管理画面文言は日本語。
- タイムアウトは通常 5 秒を初期案とする。実測により調整する場合は根拠と影響を記録する。

## 3. セッション識別・寿命（最重要）

GSMTC の SourceAppUserModelId はアプリの識別子であり、個々のメディアセッションを一意に識別するものとは限らない。API が安定したセッション実体 ID を直接提供するか調査し、アプリ ID だけで同一セッションと見なさない。

- セッションの実体に対応する一時的な ID を設計する。安定した公式 ID がなければ、同一の WinRT/COM 実体を確実に照合する方法を検証した上で、プロセス内で不透明な ID を割り当てる方式を初期案とする。
- AUMID、アプリ名、タイトル、PID、列挙順、GetHashCode、ラッパーの参照等だけで実体が同一と仮定しない。COM の同一性を利用する場合は投影のラッパー再生成、IUnknown の同一性・参照寿命・AddRef/Release・アパートメントを検証する。ポインタ値をそのまま ID として公開しない。
- 同一セッションが列挙・現在セッション取得・状態変更・読み戻しで同じ ID とロックキーになることを保証する。タイトル変更・曲送り・一時停止だけで ID を変えない。
- セッション終了・再作成・アプリ再起動・マネージャー再初期化・Sysacta 再起動時に古い ID を新しいセッションへ再割当てしない。古い ID は TARGET_NOT_FOUND 等で拒否する。
- 同一アプリの複数セッション、同一メタデータ、ラッパーの差異、オブジェクト再利用を考慮する。実体の同一性を保証できない場合は曖昧な操作を拒否し、未対応範囲と理由を記録する。アプリ名が一意に見えるという理由で操作しない。
- 省略指定は解決時点の現在セッションを固定し、状態変更ではロック取得後と最終準備後に現在セッションが同じ実体か再確認する。変化した場合は TARGET_CHANGED で副作用なく拒否する。明示 ID 指定は現在セッションの変化だけで別セッションへ切り替えない。
- 列挙結果のキャッシュを使う場合は、最新の存在確認と同一性検証を省略しない。キャッシュの上限・失効・スレッド安全性・イベント欠落時の再同期を設計する。キャッシュの競合で同じ実体に異なるロックが割り当たらないようにする。
- マネージャーの初期化、再初期化、イベント購読を必要最小限にする。無制限の Task、イベントキュー、セッション参照の保持を禁止する。サーバーの停止/再開で処理中の対象やロックを誤って破棄しない。アプリ終了時に購読を解除して解放する。
- 取得件数の上限は初期案として応答 64 件、内部探索/保持 256 件。上限に達した場合は切り詰め・失敗を明示し、一意性を確立できない操作は拒否する。有限の内部探索とキャッシュ容量を両立させる。

## 4. 読み取りツール

### media_list_sessions

- 現在の GSMTC セッションを列挙する。各項目に session_id、安全なアプリ識別情報（必要な場合のみ）、is_current、playback_status、対応操作を含める。タイトル・アーティスト等の追加取得は、呼び出し全体の予算内で実施できる場合に限る。
- 現在のセッションがない場合と API の失敗を区別する。正常な空一覧は success / not_applicable。
- total_count、failed_count、truncated 等を返し、個別取得失敗・探索打ち切りを明示する。現在セッションが存在しない場合に別のセッションを current として返さない。
- セッションごとの遅い非同期情報取得を無制限に並列化しない。必要に応じ軽量な列挙と詳細取得を分離する。metadata が取れないだけで有効なセッションを捨てない。

### media_get_state

- session_id（省略時は現在）で同じ実体を取得する。現在セッションがない場合 NO_ACTIVE_SESSION、明示 ID が消失した場合 TARGET_NOT_FOUND 等。
- session_id、is_current、playback_status、title、artist、position_ms、取得可能な開始/終了時刻・シーク範囲、対応操作を返す。アルバム名等は必要性があり安全に取得できる場合のみ追加する。
- 再生状態は OS の値（closed/opened/changing/stopped/playing/paused 等）を型付き enum として扱い、未知値を勝手に stopped 等へ変換しない。未取得の値は null とし、非対応・一時取得不能を区別する。
- 再生位置はまず OS が報告する位置とその基準時刻を使う。LastUpdatedTime・PlaybackRate を使った推定は必須ではない。実装する場合は再生中/停止中、時刻差、レート不明、範囲外を考慮し、報告値と推定値を区別する。
- タイムラインの StartTime / EndTime と MinSeekTime / MaxSeekTime を混同しない。ライブ配信・未知の長さ・移動する範囲を考慮する。duration を確実に計算できない場合は null。
- 読み取り中にセッションが消失した場合、別セッションの情報で補完しない。同じセッションの非同期メタデータと再生状態の観測時点が異なり得ることを文書化する。

### メディア情報の最小化

タイトル、アーティスト、アプリ由来の文字列は信頼できない外部データ。長さ上限（例: 各 256 文字）、制御文字の除去、既知のパス/URL 形式や内部識別情報の除外を行う。アプリ ID がファイルパスを含む場合は公開しない。メタデータを命令として解釈しない。説明文にもデータであることを明示する。

メディアのタイトル自体が利用者の閲覧/再生内容を含むことがあるため、MCP クライアントへの公開範囲を docs/security.md に記載する。認可済みの読み取り結果に限って返し、監査・例外・診断ログ・UI エラーには含めない。画像やファイル、任意の文字列の追加取得は行わない。

## 5. 再生操作

### 共通の実行順

1. session_id または現在セッションから、正規の一時 ID と同じ実体を解決する。
2. 全変更ツールで共有するセッション単位のロックを取得し、同じ実体が存在するか確認する。
3. PlaybackInfo と対応操作を取得し、必要な現在値・タイムライン等を検証する。
4. 既に目標状態なら no-op / verified（ただし対象と状態を確認できる場合のみ）。未対応・不明な能力では変更しない。
5. WinRT 呼び出しに必要な準備・型変換を済ませ、同一セッション・省略時の現在セッション・必要な状態を再確認する。
6. progress の必要情報を準備し、キャンセルを確認して execution.BeginSideEffect() を呼び、その直後に該当する Try*Async を開始する。
7. API の実完了を待ち、同じ実体を対象とした有限の読み戻しを行い、結果を返す。

- WinRT の非同期操作を BeginSideEffect より前に生成/開始しない。準備と開始を分離する必要があれば Phase 1C-1 の PrepareWrite と同様の考え方を利用する。
- API 呼び出しは原則 1 回。失敗後の自動再試行・トグルによる代替・別セッションへのフォールバックを禁止する。
- playback controls の IsPlayEnabled / IsPauseEnabled / IsStopEnabled / IsNextEnabled / IsPreviousEnabled / IsPlaybackPositionEnabled 等は実際の SDK 契約に合わせて利用する。能力判定は書き込み直前にも有効な情報に基づく。
- Try*Async の true は API 受理の根拠にできるが、状態変化の証明とは限らない。false の意味は公式契約に従い、未実行と断定できない失敗を unknown とする。
- 結果には session_id、operation、必要な変更前後の値、changed（不明なら null）、API 受理や観測された状態に関する情報を型付きで含める。既存の status / verification / isError と整合させる。
- 同一セッションの操作を有限時間内に確認できた場合のみ verified。API 受理のみなら accepted、受理/副作用が不明なら unknown、明確な未実行は error。読めた状態が要求と一致しない場合も、アプリ側の非同期反映や進行中の状態を考慮し、根拠なく成功または確定失敗としない。
- 変更開始後にセッションが終了した場合、別セッションに読み替えない。受理の根拠がある場合と副作用自体が不明な場合を分ける。
- 読み戻しを繰り返す場合は少数回・有限時間・読み取りのみ。タイムアウト後に追加書き込みを行わない。

### media_play / media_pause / media_stop

- それぞれ明示的な TryPlayAsync / TryPauseAsync / TryStopAsync を用いる。Play/Pause トグルで代替しない。
- 既に playing / paused / stopped のときは対応する no-op。closed/changing や状態不明を勝手に同一視しない。
- 対応する再生状態の読み戻しが確認できれば verified。遅延反映等で確定できなければ API 受理のみを accepted として報告する。明確な不一致・拒否は適切なエラーにする。

### media_next_track / media_previous_track

- 対応する Skip API を 1 回だけ呼ぶ。相対的な非冪等操作であり、再試行すると曲を飛ばす可能性があるため、副作用開始後の retryable は false。
- 同じタイトル・アーティストの別トラック、曲の先頭に戻る previous、広告・プレイリスト末尾等があるため、メタデータの一致/不一致だけで成功・失敗を断定しない。
- 初期方針は API 受理が確認できた場合に accepted。変更後メタデータは観測情報として返してよいが、信頼できるトラック識別や確実な操作結果の根拠がなければ verified にしない。changed も不明なら null とする。

### media_seek

- 対応能力と現在の MinSeekTime / MaxSeekTime 等により、要求 position_ms が検証可能な範囲内であることを確認する。範囲不明・不正・空・変換不能な場合は変更しない。
- 範囲外は INVALID_ARGUMENT 等で拒否し、暗黙のクランプや相対シークに変換しない。
- メディアが切り替わった、シーク範囲が変化した等の観測可能な変更を準備後に再確認する。新しいメディアに古い位置を自動適用しない。公式トラック ID が得られない場合の検出限界は明記する。
- すでに同じ位置と確実に判断できる場合の no-op と、再生中の進行・アプリ側の丸め・報告値の遅延を区別する。読み戻しの許容誤差は初期案として 500 ms を上限の目安とし、再生レート・実際の経過時間・タイムラインの基準時刻を踏まえた根拠を記録する。根拠のない広い許容範囲で verified にしない。
- 再生中に進行する位置を比較できない場合、受理のみとして報告する。ライブ配信等で検証可能な範囲を取得できない場合は NOT_SUPPORTED。位置変換の境界値、時刻の扱い、報告値と推定値の区別をテストする。

## 6. 非同期処理・排他・セキュリティ

- 状態変更のロックは media:session:{正規ID} 等を全 6 操作で共有し、読み戻し終了まで保持する。現在セッション省略指定も明示 ID と同じロックを使う。異なる実体は独立実行可能とする。
- Windows アダプターに必要な直列化がある場合はその範囲と理由を記録し、共通ロックとの取得順を固定する。マネージャー/ID 管理の内部ロックを長時間の WinRT await をまたいで不必要に保持しない。
- WinRT 非同期処理がキャンセル不能、またはキャンセル通知後もネイティブ側で続く場合は、Task.WaitAsync 等による待機打ち切りだけで実処理完了と見なさない。既存 ToolExecutor の隔離を利用し、実処理が完了するまでロック・実行スロット・対象参照を維持する。キャンセル後の新規書き込みは禁止。
- RequestAsync やメタデータ読み取り等の非同期準備にも有限の要求予算を適用する。初期化は共有・有限とし、タイムアウトした処理を無制限に増殖させない。
- GetAvailability は安価・副作用なし。メディアが再生されていない、セッションがない、特定アプリで非対応等は恒常非対応としない。GSMTC が利用できない環境と一時的な取得失敗を区別する。
- 既存の認証・認可・監査 pending・最終認可・要求予算を迂回しない。追加の HTTP エンドポイント、MCP 設定変更、メディアイベントの外部配信は作らない。
- 監査の allow-list は position_ms 等の検証済み数値のみ。対象は解決済みの不透明 ID。タイトル、アーティスト、アプリ由来文字列、生の session_id 入力、URI、ファイルパス、例外全文、結果全文は残さない。
- 共通基盤の変更は必要最小限に留める。LocalOnly はこのフェーズでは不要。管理画面のカテゴリ・許可・ログ・既存動作確認に統合し、専用メディアプレイヤーやセッション別名管理を追加しない。

## 7. テスト要件

### Core / Infrastructure / MCP

フェイクアダプターと一時 DB を使い、以下を検証する。

- 8 ツールの JSON Schema と outputSchema、必須引数、未知引数、明示 null、型不正、予約語、position_ms の負値・オーバーフロー・範囲外の拒否。
- 新規 DB の既定許可、既存 DB の新規無効、既存クライアントへの自動付与なし、無効/未許可ツールの直接呼び出しで OS 操作ゼロ。
- セッションなし・現在セッションなし・列挙エラー・部分失敗・上限超過、同一アプリの複数セッション、同じタイトル、ID の一意性と寿命、ラッパー再生成、セッションの終了/再生成、マネージャー再初期化、古い ID の拒否。
- 現在セッションの切替（解決/ロック待ち/準備中）、明示 ID 指定時の別セッションへの非フォールバック、同一対象のロックキー一致。
- 各再生操作の能力フラグ、no-op、未対応、Try*Async の false/例外/受理、読み戻しの遅延・失敗・対象消失。曲送り/戻しを繰り返さず、メタデータだけで verified にしない。
- シーク範囲の検証、非ゼロの開始位置、未知/不正/移動する範囲、メディア切替、停止中/再生中の位置、誤差の境界、単位変換。
- 準備中の失効・権限剥奪・再発行・期限切れ・全体無効・キャンセル・タイムアウト・監査容量不足で Try*Async が開始されない。
- 同一セッションの play/pause/stop/seek/skip の排他、明示 ID と省略指定の競合、異なる実体の独立性、非同期操作の実完了までのロック保持、切り離し後の遅延書き込みゼロ。
- マネージャー初期化の同時呼び出し、イベント購読解除、キャッシュの容量・再同期・並列競合、ハング時の有限な待機。
- 合成の秘密文字列（タイトル、アーティスト、アプリ ID、任意のクライアント入力、例外）が監査 DB/WAL/CSV/JSON/診断ログに残らない。許可された読み取り応答と禁止される内部情報を区別する。
- 既存オーディオ・ディスプレイ・セキュリティ・複数副作用・LocalOnly の回帰テストを維持する。

### Windows / 実機 / App

- Windows CI では実メディアを勝手に開始・停止・スキップしない。API 初期化・空一覧等の読み取りとフェイク、アプリのビルド・スモークテストを行う。セッションがない環境の成功を実メディア制御の検証と見なさない。
- Windows 実機で通常権限の Sysacta から GSMTC が利用できるか、アプリ別のセッション識別、対応操作、状態・メタデータ・位置の取得を確認する。Firefox 等のブラウザと、利用可能な別のメディアアプリでの違いを記録する。特定アプリの導入やログインを強制しない。
- 複数アプリ/複数セッション、現在セッションの切替、同じセッションの再列挙、終了後の古い ID、メディア切替、位置の検証を可能な範囲で実機確認する。特に実際の WinRT/COM 同一性はフェイクだけで確認済みとしない。
- 実メディアの変更は利用者が対象と操作を明示承認した場合の手動テストを基本とする。実機自動変更テストは AGENTS.md に従い SYSACTA_HARDWARE_TESTS=1 を必要条件とし、確実に元の状態へ戻せる場合のみ。元に戻せない next/previous/stop 等は手動確認に限定する。
- 実機で確認できない機能は未検証とする。MCP クライアント経由の許可・状態取得・操作、管理画面のカテゴリ/権限表示、ログのマスキングを手動チェックリストへ追加する。
