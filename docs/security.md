# セキュリティ境界と実行経路

仕様の根拠は [spec.md](spec.md) §5, §6, §9〜§12。ここでは「どこで何が強制されるか」をコードの位置とともに示します。変更する場合は対応するテストを必ず更新してください。

## 信頼境界

| 境界 | 信頼しないもの | 強制する場所 |
|---|---|---|
| ネットワーク → HTTP | Host / Origin / Authorization ヘッダー、本文、転送ヘッダー | `src/Sysacta.Mcp/RequestGuards.cs`, `McpServerHost.Build` |
| MCP クライアント → ツール | ツール名、引数、tools/list のキャッシュ、annotations | `src/Sysacta.Core/Tools/ToolExecutor.cs`, `ToolJson.cs`, `Security/Access.cs` |
| ツール → OS | (OS の応答は検証して返す) | 各アダプター (`src/Sysacta.Windows/`、非公開 API は `Experimental/` に隔離) |
| ローカルユーザー → 管理コンソール | — 信頼する(同一ユーザー) | UI のみが設定・権限・クライアントを変更できる |

同じ Windows ユーザーで動作する他のプロセスや管理者は、設定DB・監査ログを改変できます(サンドボックスではない。spec §6, §11)。

## HTTP リクエストの経路

1. **ホスト設定の固定** (`McpServerHost.Build`): appsettings・環境変数・コマンドラインを読まず、環境は Production 固定。`Kestrel:Endpoints`・`ASPNETCORE_URLS`・`ASPNETCORE_FORWARDEDHEADERS_ENABLED` などで待受の追加や接続元の書き換えが起きない(Mcp.Tests で検査)。
1. **Kestrel 制限** (`McpServerHost.Build`): 本文 256 KiB (超過 413)、同時接続 64、`Server` ヘッダーなし、ログ出力なし。待受は既定 `127.0.0.1:8765`。
2. **要求予算** (`RequestGuards` + `RequestBudget`、SEC-05): すべての HTTP リクエストを、Host/Origin 検証・認証・DB 照会・監査より前に数える。全体 600 件/分、接続元アドレスごとに 240 件/分(1分の固定窓)。超過は 429 + `Retry-After`、DB には書かず集約カウンターに数えるだけ。接続元はソケットのアドレスのみ(IPv4-mapped IPv6 は IPv4 に、IPv6 のスコープは除去して正規化)。`X-Forwarded-For` / `Forwarded` などは見ない。localhost も例外にしない。
   - 予算に拒否された要求は何も消費しないため、1つのアドレスの洪水が全体予算を自分の取り分(240)以上に使い切ることはない。アドレスの表は予算を通過したときだけ増えるので、窓あたり最大 600 件。窓が変わると表ごと捨てる。タイマーを持たず、ホストの1回の起動ごとに作り直す(再起動で状態は破棄)。
3. **認証段階の同時実行数**: 以下 4〜6 の検査とトークンの照会(DB の読み取り 1 回)を同時に処理するのは 8 件まで。空きがなければ待たずに 429 (`Retry-After: 1`)。待機キューはない。拒否の記録と最終利用日時の書き込みは枠を返してから行う(保守などで DB が書き込み待ちでも、枠が書き込み待ちで埋まって正規クライアントが締め出されない)。
4. **Host 検証** (`RequestGuards.IsHostAllowed`): `localhost`、ループバックIP、バインド先IP、設定済みホスト名のみ。`0.0.0.0` 待受時は IP リテラルの Host を許可(IP リテラルは DNS rebinding の対象にならない)。それ以外は 403(固定文言の理由を本文に返す)。監査に `denied` / `HostNotAllowed` とメソッド・パスの区分を記録。
5. **Origin 検証**: Origin ヘッダーがある場合のみ、設定済みの Origin と完全一致しなければ 403(`null` も拒否)。監査に `OriginNotAllowed`。CORS ヘッダーは一切返さない。Origin のない非ブラウザークライアントは許可。
6. **Bearer 認証** (`TokenAuthenticator.Authenticate`、読み取りのみ): すべてのリクエスト(localhost でも、initialize/discover でも)に必須。毎回 DB で照合し、トークンや権限をキャッシュしない。失敗は 401 + `WWW-Authenticate: Bearer`、監査に `auth_failed`(クライアントIDは null、メソッドとパスの区分のみ)。拒否(認証・Host・Origin)を個別に監査するのは接続元ごとに 30 件/分、全体で 120 件/分まで。超過分の認証失敗は 429、Host/Origin の拒否は 403 のまま、どちらも集約カウンターに数えるだけ。
7. **クライアント別予算**: 認証済みクライアントごとに 60 リクエスト/分(超過 429 + `Retry-After`、集約カウンターに `ClientRateLimited`)。これを通過した要求だけが最終利用日時を更新する(`TokenAuthenticator.RecordUse`。保存済みの値が1分以内なら書かない)。
8. **MCP**: `/mcp` の Streamable HTTP(stateless)のみ。stdio・レガシー SSE (`/sse`, `/message`) はマップしない。その他のパスは 404。
9. **tools/list**: `ToolExecutor.ListTools(caller)` が実効権限で絞り込む。**これは表示上の絞り込みで、認可ではない。**
10. **tools/call**: `ToolExecutor.ExecuteAsync` が毎回独立に認可する(下記)。

## ツール実行の経路 (`ToolExecutor.ExecuteAsync`)

| 順序 | 処理 | 失敗時 |
|---|---|---|
| 1 | ツール検索 | 未知 → MCP プロトコルエラー (InvalidParams)、監査 `denied` |
| 2 | 実効権限 = 能力 (`GetAvailability`) ∩ サーバー全体 (`tools.enabled`) ∩ クライアント (`client_permissions`、明示許可のみ) ∩ クライアントが有効(未失効・期限内) | NOT_SUPPORTED / TOOL_DISABLED / PERMISSION_DENIED |
| 3 | 引数検証: 未知プロパティ・型変換・重複・範囲外・`null`(省略で表す)・公開した綴り以外の列挙値・制御文字(`[NoControlCharacters]`)を拒否 | INVALID_ARGUMENT(メッセージには既知の引数名だけを含め、値や未知の名前は返さない) |
| 4 | 待機キュー上限 (同時実行 8 + 待機 32) | BUSY (retryable) |
| 4b | 電源遷移ゲート(状態変更のみ。Phase 1E): 通常の変更は遷移が実行中/保持中なら拒否、遷移は他の変更か遷移が 1 件でもあれば拒否。1 つのロックで原子的に判定 | BUSY (retryable、監査 `denied`。何も実行していない) |
| 5 | 対象解決 → リソースロック(状態変更のみ、キー順に取得)→ 実行スロット | TIMEOUT/CANCELLED (retryable。何も実行していない) |
| 6 | 状態変更ツールは監査 `pending` を永続化 | AUDIT_UNAVAILABLE(実行しない) |
| 7 | 再認可(実行の直前。待機中や pending 書き込み中の変更を早めに検出する) | PERMISSION_DENIED / TOOL_DISABLED(pending を拒否で置き換える) |
| 8 | 実行(タイムアウト付き)。状態変更ツールは最初の OS 書き込みの直前に `ToolExecution.BeginSideEffect()` を呼ぶ。ここが**最終の認可点かつ副作用の開始点**: `AuthorizationGate` の読み取り側で認可を評価し、許可なら「開始済み」と記録する | 開始点での拒否 → PERMISSION_DENIED / TOOL_DISABLED(監査は denied、書き込みなし)。開始前のタイムアウト/キャンセル → 呼び出しを「放棄」にして、後から開始点に来ても書き込ませず、`error`(再試行可、Nothing was changed)。開始後 → `status: unknown`。どちらもネイティブ処理が終わるまでロックとスロットを保持 |
| 9 | 監査の最終結果 | 書けなくても結果は返す(pending が残る) |

### 権限変更と操作開始の順序(SEC-01)

- 権限を狭める書き込み(失効・再発行・個別の許可取り消し・期限変更・ツールの全体無効化。実装上は `AccessStore` の権限関連の書き込みすべて)は、`AuthorizationGate` の書き込み側で行う。
- 開始点の評価は同じゲートの読み取り側で行う。そのため、開始点より前に完了した変更は必ず反映され、評価中に変更が割り込まない(各条件の読み取りが一貫する)。
- ゲートを持つのは評価(DB の数回の読み取り)の間だけで、ネイティブ処理の間は持たない。長い OS 呼び出しが権限変更を止めることはない(Core.Tests で検査)。
- 開始点の後に完了した変更は、その呼び出しには適用されない(spec §6「すでに実行された副作用は巻き戻せない」)。

管理コンソールの「動作確認」も同じ経路を `Caller.LocalConsole` で通ります(クライアント別許可の代わりにローカルユーザーとして扱うが、サーバー全体の許可・検証・監査は適用)。

ローカル専用ツール(`ToolDescriptor.LocalOnly`。現在は `display_restore_mode` と `power_release_gate`)は MCP には存在しないものとして扱います: `tools/list` に出ず、MCP クライアントからの呼び出しは未知のツール(プロトコルエラー)で、引数の検証・解決・ロックの前に拒否されます。全体・クライアント別の許可を持たず、`Caller.LocalConsole` だけが実行できます(検証・ロック・pending 監査・開始点・最終監査は通常どおり)。

## トークン

- 生成: `RandomNumberGenerator` 256 bit、`sya_` + base64url(43文字)。ユーザー指定のトークンは受け付けない。
- 保存: SHA-256(hex)のみ。原文は発行・再発行時に UI に一度だけ表示し、DB・ログ・設定に保存しない(テスト: DB ファイル全体に原文が含まれないこと)。
- 比較: ハッシュでの検索後、`CryptographicOperations.FixedTimeEquals`。
- 失効・期限・再発行(旧トークン即時無効)は次のリクエストから反映。待機中の呼び出しも、実行直前に「認証に使ったトークンのハッシュ」を照合して拒否する(`Caller.CredentialHash`。ログや応答には出さない)。
- 最終利用日時は 1 分単位で更新。

## 監査ログ

- 記録: 成功・失敗・拒否・認証失敗・結果不明・pending。項目は spec §11 + 接続元(ソケットのアドレスのみ。`X-Forwarded-For` などは使わない)。
- 記録するのは固定値・登録名・解決済み識別子だけ(SEC-03)。クライアントが入力した文字列はどの経路でも記録しない(形式の検査では機密が含まれないことを保証できないため)。
  - ツール名: 登録済みの名前。未登録の名前は `(unknown tool)`。
  - 引数: `ToolDescriptor.AuditedArguments` の許可リストのうち、数値・真偽値・列挙値だけ(文字列の引数はツール登録時にエラーになる)。検証に失敗した呼び出しの引数は記録しない。
  - 対象: 解決に成功したときの `ToolTarget.TargetId`(OS や Sysacta の登録情報から得た識別子)を `target` として記録する。入力されたデバイス文字列そのものは記録しない。
  - HTTP での拒否: 理由コード(`HostNotAllowed` / `OriginNotAllowed` / 認証失敗の種類)、標準メソッドか `other`、パスが `/mcp` か `other` だけ。Host・Origin・パス・クエリ・ヘッダーの値は記録しない。
  - 回帰テスト: 合成の機密文字列を未登録のツール名・デバイス入力・パス・Host・Origin・Authorization に入れ、DB・WAL・CSV・JSON のどこにも残らないことを Mcp.Tests で検査。
- 記録しないもの: トークン、Authorization ヘッダー、リクエスト/レスポンス本文、生の例外、スタックトレース。管理コンソールのエラー表示も、OS・ファイル・DB の例外メッセージ(パスや SQL を含み得る)は出さず固定文言+例外の型名にする(`PageViewModel.SafeMessage`)。
- CSV 出力は全セルを引用符で囲み、`= + - @ タブ CR LF` で始まるセルに `'` を付ける(数式注入対策)。
- 保持期間は既定 30 日(1〜3650)。起動時と 6 時間ごとに削除。

### 保存量の上限(SEC-06)

`AuditLog` が書き込みのたびに強制する。値は `AuditLimits`(既定値は下表)。

| 項目 | 値 |
|---|---:|
| 記録数の上限 | 100,000 件 |
| 論理保存量の上限 | 64 MiB |
| 状態変更の意図 (`pending`) 用の予約枠(上限の内数) | 1,000 件 / 6.4 MiB |
| HTTP の拒否記録(集約を含む)の上限(内数) | 10,000 件 / 6.4 MiB |
| 拒否を個別に記録する予算 | 接続元ごと 30 件/分、全体 120 件/分 |
| 集約の単位 | 理由コードごと・1分 |

- **論理保存量**: 1件 = 128 バイト(整数列・レコードヘッダー・索引の見積もり)+ テキスト列の UTF-8 バイト数 (`AuditLog.SizeOf`)。各行の `size_bytes` と、トリガーで同期する `audit_usage`(全体と `http` の件数・バイト数)で管理するので、上限の確認にテーブル走査は不要。
- **書き込み**: `BEGIN IMMEDIATE` のトランザクションで「使用量の確認 → 必要なら最古の記録を削除 → 挿入」を行う。並行する書き込みでも上限を超えない。削除は `pending` 以外の最古の記録を索引順に、1回の書き込みで最大 4×1,000 件。上限の 1% 分を余分に削除して、毎回は削除しない。それでも入らなければ `AuditCapacityException`。
- **優先度**: `pending` は上限いっぱいまで書ける。それ以外は「上限 − 予約枠」まで。HTTP の拒否記録は拒否記録だけを削除して場所を作る(専用の上限と全体の上限のどちらでも)ので、未認証の洪水がツールの記録を押し出さない。ツールの記録で満杯なら拒否記録は書かれない(書き込み失敗として数える)。最終結果は同じ `request_id` の行を更新するだけで、新しい行にならない(二重計上なし、上限でも失敗しない)。
- **状態変更の監査が書けないとき**: 予約枠も尽きた(進行中の `pending` だけで満杯)か DB が書けなければ、従来どおり `AUDIT_UNAVAILABLE` で拒否し、OS には書き込まない。監査を省略して実行することはない。最終結果を書けなければ `pending` が残る。
- **集約**: 予算・同時実行数・クライアント別予算で拒否した要求と、個別記録の予算を超えた拒否は、メモリ上で理由コード(固定の約10種)ごとに数え、1分経過後に予算を通過した次の要求がバックグラウンドで(要求は待たない)、またはホスト停止時に1件ずつ書く(停止時は書き込み中のバックグラウンド処理を待ってから残りを書くので、通常の終了では失われない)(`aggregate_count` 列。接続元・メソッド・パスは記録しない)。キューは持たない。プロセスが異常終了すると、書く前の集約は失われる。理由コード: `RequestBudgetExceeded`, `AuthenticationBusy`, `ClientRateLimited`, `HostNotAllowed`, `OriginNotAllowed`, 認証失敗の種類。
- **pending の扱い**: 進行中の `pending` は保持期間・容量のどちらでも削除しない。起動時(ツールがまだ動かない時点、単一インスタンス)に残っている `pending` は前のプロセスの異常終了の名残として `unknown` / `INTERRUPTED` に変える(変更が起きたかは不明なため)。以後は通常の記録として削除対象になる。
- **保守** (`AuditLog.Maintain`、起動時と 6 時間ごと、バックグラウンド): 保持期間の削除と上限の強制(どちらも短いトランザクションの繰り返し。アップグレード直後の過大な DB もここで縮む)→ 空きページが 16 MiB 以上かつファイルの 1/4 以上なら `VACUUM` → `wal_checkpoint(TRUNCATE)`。失敗は次回に再試行。

### 物理サイズ(SQLite の DB と WAL)

- 論理保存量は物理ファイルサイズの保証ではない。削除した行のページは SQLite が再利用するので、DB ファイルは最大時の大きさ付近にとどまり、縮むのは保守の `VACUUM` のときだけ。目安として、監査ログ部分は論理上限の約2倍(実測: 論理 90 KB に対しファイル 184 KB)。
- WAL は自動チェックポイント(1,000 ページ)で先頭から再利用され、各接続で `journal_size_limit = 4 MiB` を設定しているので、リセット時に 4 MiB まで切り詰められる。**長時間の読み取りトランザクションがある間はチェックポイントが進まず、WAL は上限なく伸びる**(実測: 1,500 件の書き込みで 43 MB)。Sysacta 自身の読み取りは検索・書き出しの間だけ。読み取りが終われば次のチェックポイントで 4 MiB 以下に戻り、保守で 0 になる。
- ディスクの空き容量は保証しない。ディスクが一杯で書けなければ、状態変更は `AUDIT_UNAVAILABLE` で拒否される(fail-closed)。
- 上限を大きく超えた DB(Phase 0 からのアップグレード直後や上限を下げた場合)は、1回の書き込みで削除できる量(4,000 件)では足りず、起動時の保守 `EnforceLimits` が終わるまで書き込みが失敗し得る。その間の状態変更は `AUDIT_UNAVAILABLE` で拒否される(fail-closed、再試行可)。
- ログ画面には論理保存量に加えて、DB ファイル・未使用領域・WAL の物理サイズを表示する。
- 復旧: DB が壊れたり一杯になったりした場合は、Sysacta を終了して `%LOCALAPPDATA%\Sysacta\sysacta.db*` を退避すれば、次回は新しい DB で起動する(クライアントと権限は再設定が必要)。マイグレーション前の DB は `sysacta.db.v<N>.bak` に残る。

## 設定と権限の変更経路

- 変更できるのは管理コンソール(WPF)だけ。MCP 層は `IAccessStore`(読み取り専用)しか受け取らず、設定変更用のツール・エンドポイントは存在しない。
- 新規 DB では `DefaultPolicy.On` のツールのみ全体で有効。後のバージョンで追加されたツールは無効のまま追加され、既存クライアントにも自動付与されない。
- 新規クライアントの初期権限はプリセット(現在有効な全ツール / 読み取り専用のみ / なし)から明示的な行として保存される。

## 権限レベル

- マニフェストは `asInvoker`。自動起動 (HKCU\...\Run) は昇格しない。MCP から昇格する手段はない。
- 管理者で起動した場合はタイトルとバナーで常時表示する。攻撃面が増えることは残存リスク。

## 禁止事項(実装してはいけないもの)

- 任意のシェル/PowerShell/スクリプト実行、任意のファイル読み書き、GUI 操作・スクリーンショット・クリップボード取得。
- 任意のパス・引数・URI・環境変数・DLL を受け取るツール。
- 認証の例外(localhost だから省略、など)、ワイルドカードの Origin/CORS、転送ヘッダーの信用。
- tools/list の絞り込みだけで認可したことにする実装。
- 監査ログ・エラー・UI への秘密や生の例外の出力。
- DLL インジェクション、カーネル改変、セキュリティ機構の回避(spec §12)。

## 対象識別子とローカル別名(オーディオ)

- 音声セッションの OS 識別子は実行ファイルのパスを含むため Core の外に出さない。公開・監査するのは `session_id` = `as_` + SHA-256(エンドポイント ID, セッションインスタンス ID) だけ(`AudioSessions.SessionId`)。ID の表は持たず、呼び出しのたびに列挙して照合する。
- 変更はロック取得後に同じ実体を開き直して確認し、その COM オブジェクトに書き込んで読み戻す。プロセス名・PID・表示名では指定できず、別のセッションへ切り替えない。
- 返すのは表示名かプロセス名(パス・リソース参照・制御文字は除去)、PID、状態、音量、ミュートだけ。
- デバイス別名の登録・変更・削除・再紐付けは管理コンソールだけ(`AccessStore`)。MCP 層が受け取る型に書き込みはない。

## 対象識別子と一括操作(ディスプレイ)

- 公開・監査する ID は `display-` + SHA-256(OS のデバイスパス)。デバイスパスと GDI デバイス名はアダプターの外に出さない。監査の引数は `level` と `target`(正規 ID か固定値 `all`)だけで、対象別の結果は記録しない。
- 物理モニターを一意に決められない場合(複製表示、1 つの source に複数の物理モニター)は操作しない。列挙順で選ばない。内蔵パネルの WMI インスタンスはデバイスパスから導いた PnP インスタンス ID に一致する 1 件だけを使う。
- 変更は high-level の輝度・コントラスト API と `WmiSetBrightness` だけ。任意の VCP コードや WQL を入力から組み立てる経路はない。
- `all` は輝度だけ。各書き込みの直前に再認可し、拒否・キャンセル・結果不明の後は新しい書き込みを始めない(詳細は [phase-1c-1-progress.md](phase-1c-1-progress.md))。
- DDC/CI と WMI のアクセス、表示モードの変更はアダプター内の 1 つのゲートで直列化する。応答しないネイティブ呼び出しはロック・ハンドル・ゲートを保持し続け、後続の呼び出しはタイムアウトする(fail-closed。回復はプロセス再起動)。
- 表示モード・電源・入力(Phase 1C-2)の 3 ツールは `DefaultPolicy.Off`。ツール画面の「すべて有効」でも有効にならず、個別に有効にする。`device` は必須で、既定の表示・`all` はない。
- 表示モードは `display_list_modes` と同じ `mode_id` を、書き込み直前に Windows がいま列挙するモードから再計算して照合する。適用するのは列挙された DEVMODE で、変更する項目は解像度・色深度・表示フラグ・リフレッシュだけ(位置・回転・スケーリング・プライマリは変えない)。レジストリに保存しない。プライマリ画面は対象外(ローカル復旧の手段であるトレイが同じ画面にあるため)。
- DDC/CI の低レベル API で触れるのは VCP 0xD6(値 0x01 / 0x04)と 0x60(MCCS 2.x の標準値 0x01〜0x12)だけ。コードの選択はアダプター内の列挙型で、値はツールとアダプターの両方で許可リストと照合する。モニターが能力文字列で宣言していない値、`mccs_ver` が 2.x でないモニターには書かない。能力文字列は長さ・深さ・要素数を制限して解析し、応答にも監査にも出さない。
- `mode_id` / `input_id` の入力文字列は監査に残さない(記録するのは `target` と `display_set_power` の `state` だけ)。
- 表示モードの復旧(`display_restore_mode`)は MCP から呼べない。適用するのは Sysacta が記録した元のモードだけで、同じ表示 ID にだけ、現在モードが Sysacta の適用したモードのときだけ(それ以外は記録を破棄)。記録はプロセス内に直近 1 件で、永続化しない。

## 既知の残存リスク

- 同一ユーザー権限のプロセスによる DB・設定の改変、監査ログの改ざん。
- 管理者として起動した場合、ツールの操作も管理者権限で実行される。
- `0.0.0.0` などで HTTP を非ループバック公開した場合、トークンは平文で流れる(UI で警告。HTTPS リバースプロキシを推奨)。
- 署名なしのバイナリは SmartScreen / Smart App Control によりブロックされ得る(このプロジェクトの開発機でも、未署名の `SQLitePCLRaw.batteries_v2.dll` がブロックされた)。コード署名は未決定(spec §15)。
- 開始点(`BeginSideEffect`)の後に完了した権限変更は、すでに始まった OS 操作には適用されない(spec §6)。開始点から実際のネイティブ呼び出しまでの間は、ツールのコードで数命令のみ。
- 開始点の宣言はツールの責務。状態変更ツールが `BeginSideEffect()` を呼ばずに書き込むと、開始点での再認可と「開始前なら何も変更していない」の判定が働かない(executor の早めの再認可だけになる)。docs/tools.md と AGENTS.md で必須とし、参考実装と Core.Tests の境界テストで示している。
- 権限変更の書き込みは、開始点の評価中(DB の読み取りが混雑で待つ場合は最大で SQLite の待ち時間)だけ待たされる。
- 複数回の OS 書き込みを行うツール(`audio_set_default_device` の `role=all` など)では、2 回目以降の各書き込み直前に `ToolExecution.BeginNextSideEffect` でキャンセル・タイムアウトによる切り離し・最新の認可を再確認し、拒否された場合は残りの書き込みを止めて `partial` を返す。既に行われた変更は巻き戻さない。
- `audio_set_default_device` は非公開 COM インターフェース(`IPolicyConfig`)を使用するため `DefaultPolicy.Experimental`(新規・アップグレードとも初期無効)とし、`Sysacta.Windows/Experimental/` に隔離して Windows 11 x64 の QI プローブで能力判定を行う。将来の Windows 更新で動作しなくなる、または ABI 変化でプロセスが異常終了するリスクが残る。
- 要求予算は接続元アドレス単位。リバースプロキシ(Tailscale Serve など)経由ではすべての正規クライアントが `127.0.0.1` を共有するため、接続元予算 240 件/分を分け合う(クライアント別の上限 60 件/分なら4クライアント分)。同じプロキシの後ろにいる攻撃者は、正規クライアントの取り分を使い切れる(同一接続元での公平性はない)。クライアントが多い場合は `ServerEndpointOptions.RequestsPerMinutePerAddress` を上げる(設定 UI はない。コード上の既定値)。全体予算 600 件/分を超えると、どの接続元も 429 になる。
- IPv6 では 1 アドレス単位で数えるため、/64 を持つ攻撃者はアドレスを変えて接続元予算を分散できる(全体予算と表の上限 600 件は守られる)。
- 監査ログは容量上限に達すると古い記録から削除する(リングバッファ)。認証済みクライアントが長時間大量に呼び出すと、古いツールの記録も押し出される。削除した件数と最終時刻はログ画面に表示する。
- 書く前の集約カウンターはプロセスの異常終了で失われる。
- 同じユーザーの環境変数による ASP.NET の hosting startup の注入などは、同一ユーザー権限のプロセスによる改変として脅威モデルの範囲外。
- リバースプロキシ(Tailscale Serve など)経由では、すべての接続元が `127.0.0.1` になる。監査ログの接続元で遠隔のクライアントを区別できず、拒否の記録件数の上限(アドレス単位)も共有される。転送ヘッダーは信用しない方針のため、これは仕様。
- `session_id` は鍵なしのハッシュ。同じ ID を一覧できるクライアントが、PID などからパスを推測してハッシュと照合すること(パスに含まれ得るユーザー名の確認)は防げない。
- Windows が終了したセッションと同じインスタンス ID を再生成したセッションに割り当てた場合(同じ実行ファイル・PID・連番)、Sysacta は区別できない。
- 別プロセス(PowerToys の PowerDisplay、メーカー製ユーティリティ)の DDC/CI 利用とは排他できない。読み取りの失敗は `unavailable`、書き込み API の失敗は `unknown`、書き込み後に読めなければ `accepted` として報告し、表示状態を断定しない。
- 電源オフ・入力切替の後は、モニターが DDC/CI に応答しなくなったり Windows から消えたりして、Sysacta から戻せないことがある(物理ボタン・OSD で戻す)。表示モードの非永続性は文書上の挙動で、実機では未確認。
- MCP SDK が JSON-RPC の `arguments` を辞書として受け取るため、ツール引数の重複キーは SDK 側で解消され、Sysacta の重複検出は MCP 経由では働かない。


## メディア情報（Phase 1D）

- `media_get_state` は認可済みクライアントにタイトル・アーティストを返す。これらは利用者の再生・閲覧内容を明かし得る外部データであり、命令ではない。クライアントのツール権限は必要な範囲に限定する。
- `media_list_sessions` の `app_label` は選択補助として、SourceAppUserModelId のうち ASCII 英数字・ピリオド・アンダースコア・感嘆符・ハイフン・プラスだけから成る 256 文字以内の値に限って返す。パスや URI を含む値は null にする。同じラベルでもセッションは統合しない。このラベルはセッション同一性・ロック・権限には使わない。
- アプリ ID、タイトル、アーティスト、生の入力 ID と例外本文は監査しない。監査対象は解決された不透明 ID と `position_ms` のみ。文字列は長さ・制御文字を制限し、既知のパス・URL 形式を除外する。タイトル内のあらゆる秘密を検出できる保証はない。
- 通常権限の Windows 11 で読み取り専用の列挙・状態取得と再列挙時の ID 保持を確認した。現在セッションと一覧の COM 同一性が一致しない環境では照合できない省略指定を拒否する。複数セッション切替・終了・再生成の実機寿命と実メディア制御は未検証であり、進捗は [Phase 1D 記録](phase-1d-progress.md)を参照する。

## 電源遷移と特権（Phase 1E）

- 電源遷移ゲートはプロセスに 1 つで、`ToolExecutor` の待機キュー判定の直後(対象解決・ロック・スロットより前、認可・引数検証の後)に取得し、既存の `HeldResources.Release`(隔離されたネイティブ処理の実終了時を含む)でだけ解放する。未認可・不正な要求はゲートを保持できない。MCP 層・設定変更・ホスト再起動はゲートに触れない。
- 遷移の区別は信頼済みの `ToolDescriptor.Transition` だけで、クライアントの引数では選べない。
- シャットダウン/再起動の受理後(または不明)は、ローカル利用者が概要画面から確認のうえ解除するまで状態変更を拒否する。解除はローカル専用ツール `power_release_gate`(MCP には存在しない、executor 経由、pending 監査・開始点あり。Held 中に受け付ける唯一の状態変更で `ToolDescriptor.ReleasesPowerGate` だけが例外を表す)で、確認時に取得した遷移の世代番号を同じロックの下で照合し、別の遷移に置き換わっていれば拒否する。実行中も拒否する。スリープは開始点後に suspend→resume を観測したときにも解除する。経過時間・切断・ホスト再開では解除しない。
- `SeShutdownPrivilege` はプロセストークンでは有効にしない。複製した偽装トークンで有効化し(未保持なら拒否、`ERROR_NOT_ALL_ASSIGNED` を検査)、`BeginSideEffect` の後に呼び出しスレッドへ設定して OS 要求 1 回だけ行い、`finally` で `RevertToSelf`(失敗時はプロセス終了)。MCP から昇格・UAC・特権付与を要求する経路はない。
- 状態変更前の pending 監査は `PRAGMA synchronous = FULL`(WAL)でコミット時に永続化される。OS の停止で最終監査が書けない場合は次回起動時に `unknown`。
- 残存リスク: SetSuspendState が偽装トークンの特権を使うことは文書化されていない(使われなければ OS 拒否で安全側)。resume 通知が届かない環境では復帰後もローカル解除までゲートが残る。詳細は [Phase 1E 進捗](phase-1e-progress.md)。

## システム監視（Phase 1F）

- 4 ツールとも引数なし・読み取り専用。PDH カウンター、WMI クエリ（ローカル `root\cimv2`、必要プロパティのみ）、レジストリ値（`CurrentVersion` の `UBR`・`DisplayVersion`）は実装の定数で、MCP から任意のクエリ・カウンター・パス・レジストリ・ファイルを指定できない。
- ドライバーの導入・ロード、権限昇格、汎用メモリ/IO/MSR/PCI アクセス、ベンダー DLL の読み込み、外部コマンドは使わない。DLL は System32 からだけ読み込む。LibreHardwareMonitor は特権ドライバーが必要なため採用しない。
- 返さない: シリアル番号、製品キー、MachineGuid、SMBIOS UUID、コンピューター名・ユーザー名・ドメイン、SID、MAC、デバイスインスタンスパス、PID、ボリュームのシリアル・ラベル・GUID パス・マウント先。機器名は `UntrustedText` で制御文字とパス・URI 形式を除く。GPU の `gpu_id` は再起動で変わる LUID で、永続 ID ではない。
- ネットワーク・リムーバブル・光学ドライブは種別判定の後に一切アクセスしない。SUBST ドライブは除外する。
- 監査に残るのはツール名・結果・所要時間だけ（引数なし、結果本文・機器名・ID・ドライブ名は残さない）。結果は認可済みのクライアントにだけ返る。機器構成は端末の指紋になり得るため、クライアントへの付与は必要な範囲にする。
- 読み取りは電源遷移ゲートの対象外（遷移中も読める）で、ロック・pending 監査は持たない。ハングしたネイティブ呼び出しは executor のスロット隔離で実終了まで数え続ける。詳細と残存リスクは [Phase 1F 進捗](phase-1f-progress.md)。

## デスクトップ通知(Phase 1G)

- 送信元は固定の AppUserModelID `Sysacta.Desktop`。引数は title と body のテキストだけで、XML・画像・音声・ボタン・リンク・起動引数・送信元・優先度は指定できない。値は固定テンプレートの DOM テキストノードに入れ、文字列連結で XML を作らない。制御文字・双方向制御などの不可視の書式文字・無効な UTF-16・リソース参照やバインドと解釈され得る値は拒否する。
- 通知のクリックは何も実行しない(toast activator・launch 引数・イベントハンドラーを登録しない)。クリックを認可や確認として扱わない。実機ではアプリ起動中のクリックで何も起きなかった(終了後は未確認)。
- 登録はアプリの起動時だけ(現在のユーザーのスタートメニューのショートカット 1 つ)。MCP の呼び出しでは何も登録しない。同じ名前の他者のファイルは上書きしない。有効とするのは ID とリンク先がこの exe で引数がないものだけで、送信のたびに開始点より前に再確認する(MCP 呼び出しでは修復しない。確認後の書き換えは防げない)。通知設定・集中モードは変更しない。
- **プライバシー**: 通知の本文は通知センター・ロック画面・画面共有中の画面に残る可能性があり、OS の保持・同期・表示は Sysacta では制御できない。秘密・認証情報・個人情報を送らないこと。Sysacta は本文中の秘密を検出できない。title と body は監査ログ・応答・エラーに残さない。
- **悪用防止**: プロセス全体で直近 60 秒に 5 回まで、2 秒間隔(単調時刻。アプリ再起動でリセット)。超過は送らずに `BUSY`。権限を持つクライアントは任意の文章を Sysacta の名前で表示できるため、付与は必要なクライアントに限る。同一ユーザーの他プロセスが同じ ID を使うことは防げない。詳細は [phase-1g-progress.md](phase-1g-progress.md)。

## アプリ・プロセス(Phase 2A)

- **任意実行の防止**: MCP の引数は `app_id`(`app_` + 32 桁の 16 進、登録時に生成)と `pid` + 正確な `start_time`、一覧の `limit` / `filter` だけ。パス・引数・URL・環境変数・作業フォルダー・終了コード・force/kill_tree は受け取らない(未知の引数は検証で拒否)。登録・許可・再承認・削除は管理画面だけで、MCP 層には書き込みインターフェースを渡さない(`IAppRegistry` は読み取り専用)。
- **実行対象の規則**(登録時と起動前に同じもの。`ExecutablePolicy` + `WindowsAppPlatform`): ローカル固定ドライブ上の `X:\...\name.exe`(259 文字以下、UNC・デバイスパス・ADS・`~`・`%`・ドット区間・末尾のドット/空白・予約デバイス名を拒否)。各親フォルダーとファイルを再解析ポイントを辿らずに開いて再解析ポイントを拒否し、ハンドルの最終パスが一致すること。PE ヘッダーが x86/x64/ARM64 の GUI/コンソールの実行イメージ(DLL・ドライバー・偽装を拒否)。Windows フォルダー・`WindowsApps`・Sysacta 自身のフォルダーとファイルを拒否。シェル・スクリプトホスト・インタープリター・汎用ランタイム・インストーラー/更新ツール・管理ツールをファイル名とバージョンリソースの元の名前で拒否(補助的な防御で、境界ではない)。
- **実体の固定**: 承認したファイルをボリュームシリアル + 128 ビットのファイル ID + サイズ + SHA-256 で記録する。起動前に、各親フォルダーを削除共有なし(名前変更・置換不可)、ファイルを書き込み・削除共有なし(変更・名前変更・削除不可)で開いたまま、同じハンドルで最終パス・ファイル ID・サイズ・SHA-256(512 MiB まで)を照合し、そのまま開始点 → `CreateProcessW` まで保持する。一致しなければ `TARGET_CHANGED`(再承認が必要)。同じファイル(ボリューム + ファイル ID)は 1 つの ID にしか登録できない(一意索引)。
- **起動**: `CreateProcessW` に検証済みのパスを `lpApplicationName` として渡し(コマンドラインの解釈・PATH 探索に依存しない)、コマンドラインは承認済みの固定引数を CommandLineToArgvW の規則で引用して作る。ハンドル継承なし、標準入出力なし、Sysacta 自身の環境、作業フォルダーは exe のフォルダー、シェル・verb・runas・ShellExecute なし。`CREATE_SUSPENDED` で作成し、イメージが保持中のファイルであることを NT パス同士(ドライブ文字の割り当てに依存しない)で確かめ、再開の直前に取消・最終認可・登録の許可と世代をもう一度確認してから再開する。拒否・不一致・失敗では再開せず、そのとき生成したプロセスだけを同じハンドルで回収し、回収を確認できなければ `unknown` を返す。昇格が必要な exe は OS の拒否(740)をそのまま `NOT_SUPPORTED` にする。
- **昇格の継承防止**: Sysacta 自身が昇格中(TokenElevation または integrity が high 以上。読めなければ昇格扱い)の間、`app_launch` は非公開で、直接呼び出しも拒否する。
- **許可リストと最終認可**: 許可リストへの書き込みはすべて `AuthorizationGate.BeginUpdate()` の中。開始点 `BeginSideEffect(targetCheck)` は認可と同じ読み取り側で「登録が存在し、許可され、解決時と同じ世代」を照合する。再承認は世代を上げて許可をオフに戻す(許可を引き継がない)。無効化も世代を上げるので、オフ→オンに戻しても無効化前に待機していた呼び出しは拒否される。旧形式・破損した行は解決しない。
- **プロセスの特定**: `pid` は必ず 100 ns 精度の生成時刻(FILETIME と損失なく変換できる固定書式)と組。解決時は列挙から pid + 生成時刻を固定し(ハンドルを保持しない)、ロック後に最小権限(`PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`、強制終了のときだけ `PROCESS_TERMINATE`)で開いたハンドルで生成時刻・ユーザー SID・セッション・integrity・保護レベル・critical・自己/親・イメージのファイル ID を再検証し、同じハンドルに `PostMessage(WM_CLOSE)` / `TerminateProcess` を 1 回だけ行う。ハンドルを開いている間 pid は再利用されない。推定(`estimated`)の照合は、イメージのパスにあるファイルの ChangeTime がプロセス生成時刻より前のときだけ行い(置換・名前変更の後は「不明」)、一覧表示と「起動済みかもしれない」判定(起動を拒否する側)にだけ使う。プロセス一覧の切り詰め・列挙失敗では起動・通常終了をしない。
- **終了対象**: Sysacta 自身が `app_launch` で承認済みの exe から生成し、再開前にイメージを検証したプロセス(`ManagedProcesses`、プロセス内・最大 256 件。pid + 生成時刻 + 登録 ID + 承認の世代)のうち、そのアプリが今も同じ世代で許可されているものだけ。そのうえで現在のユーザー・同一セッション・medium integrity であること。利用者や他のプログラムが起動したプロセス、Sysacta の再起動前・再承認や無効化の前に起動したプロセスは、イメージがそれらしくても `estimated` として一覧に出すだけで終了しない(ロード済みイメージのファイルを制限付きハンドルから証明する文書化された API がないため。パスや ChangeTime による推定を終了の許可に使わない)。Sysacta 自身、起動元のプロセス、保護プロセス、critical、昇格・低 integrity、他ユーザー・他セッション、判定できない(読めない事実がある)プロセスは終了しない。`SeDebugPrivilege` の有効化・昇格・保護解除はしない。
- **通常終了と強制終了の分離**: `app_close`(既定 Off)はプロセス 1 件・トップレベルウィンドウ 1 件のときだけ `WM_CLOSE` を投函し、強制終了へフォールバックしない。`process_terminate`(既定 Off、ツール画面の「すべて有効」でも有効にならない)は独立したツール。
- **秘匿**: 応答・監査に実行ファイルのパス・固定引数・ハッシュ・ファイル ID・コマンドライン・環境変数・ウィンドウタイトル・SID を出さない。監査に残るのは `target`(登録 ID、プロセスでは `app_id|pid|start_time`)と `pid`、`limit` だけ。`filter` と入力された `app_id` の文字列は残さない(Mcp.Tests で DB・WAL・CSV・JSON を検査)。パスと固定引数は管理画面でローカルの利用者にだけ表示する。
- **残存リスク**: [Phase 2A 進捗](phase-2a-progress.md)の「残存リスク」を参照(同一ユーザーのプロセスによるドライブ文字の再定義、登録したアプリ自身の機能、ウィンドウハンドルの再利用、イメージとディスク上のファイルの同一性の限界など)。
