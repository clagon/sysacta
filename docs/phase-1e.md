# Sysacta — Phase 1E: 電源管理

## 目的と範囲

spec §7.4 / §8 / §9 / §10 / §11 に従い、電源状態・電源プランの取得と変更、Windows のロック、スリープ、シャットダウン、再起動を追加する。PC 全体への影響、OS の権限、接続断、実行意図の永続化、他の状態変更との競合を重視する。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/manual-tests.md、docs/phase-1a-progress.md、docs/phase-1c-2-progress.md、docs/phase-1d-progress.md と現行コード・テストを読む。最新 main を基点とする専用ブランチ（例: phase-1e）で作業し、独立した PR を作成する。自動マージしない。

既存の認証・認可・監査容量・要求予算・対象識別・副作用開始点・非キャンセル可能処理の隔離を維持する。Phase 1F 以降、過去フェーズの残課題、配布方式、管理 UI 全体の再設計には着手しない。

## 1. 技術調査

実装前に Microsoft の公式文書、Windows SDK の定義、通常ユーザー・非パッケージ WPF アプリでの API 契約を確認する。採否・参照 URL・ABI・権限・制約・未確認事項を docs/phase-1e-progress.md に記録する。

| 用途 | 調査候補 |
|---|---|
| AC 電源・バッテリー情報 | GetSystemPowerStatus |
| 電源機能・利用可能なスリープ状態 | GetPwrCapabilities / IsPwrSuspendAllowed 等 |
| 電源プラン列挙・表示名・アクティブプラン | PowerEnumerate / PowerReadFriendlyName / PowerGetActiveScheme |
| プラン変更 | PowerSetActiveScheme |
| セッションロック | LockWorkStation |
| スリープ | SetSuspendState |
| シャットダウン・再起動 | ExitWindowsEx 等の公式 API |
| 必要な権限の確認・限定的な有効化 | OpenThreadToken / DuplicateTokenEx / LookupPrivilegeValue / AdjustTokenPrivileges 等 |
| スリープ復帰・セッション終了 | Windows の電源通知・セッション通知、既存 WPF ライフサイクル |

- Win32 API の P/Invoke の戻り値、エラーコード、BOOLEAN/BOOL、文字列・バッファ、構造体、LocalFree 等の解放責務を公式定義と照合する。未対応機種・OS ポリシー・アクセス拒否と API の一時失敗を区別する。
- Windows 11 の通常権限、現在の対話セッションを前提とする。Modern Standby、従来型 S3、AC/DC、バッテリーなし、リモートセッションでの制約を確認する。
- 状態を変更する API を能力検出に使わない。GetAvailability は安価・副作用なし。現時点の電源状態や一時的な権限/ポリシーの変化によりツールを恒常的に非公開にしない。
- 既存の依存方向を維持し、Windows 固有処理は Sysacta.Windows/Power に置く。Core の型は OS 非依存。追加ライブラリ・権限は必要最小限。
- shutdown.exe、powercfg.exe、rundll32、PowerShell 等の外部コマンド、任意コマンド、GUI 操作、非公開 API、権限昇格、自動的なポリシー変更は使用しない。

## 2. 公開ツールと権限

以下は spec §7.4 の既定値をそのまま採用する。

| ツール | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| power_get_state | なし | 読み取り | On |
| power_list_plans | なし | 読み取り | On |
| power_set_plan | plan_id | 状態変更 | Off |
| power_lock | なし | 状態変更 | On |
| power_sleep | なし | 状態変更 | Off |
| power_shutdown | なし | 状態変更 | Off |
| power_restart | なし | 状態変更 | Off |

- 新規 DB は上表、既存 DB への追加は全 7 ツールが無効、既存クライアントへの自動付与なし。既存の権限の積集合、明示許可、失効・期限・再発行、全体無効を維持する。
- Off のツールを管理 UI の「すべて有効」で有効にしない。PC 停止・接続断・未保存作業への影響を個別の注意文に明記する。ロックは spec 上 On だが、再ログインが必要になる可能性を明記する。
- MCP では既に付与された許可に従って実行し、毎回の対話確認を追加しない。一方、ローカル管理画面の動作確認では、ロック・スリープ・シャットダウン・再起動などの操作について明示確認を設けるか、動作確認ボタンを無効にする。実行する場合は必ず executor 経由。
- plan_id 以外のユーザー指定引数を追加しない。未知引数、null、型不正を拒否。force、delay、schedule、reason、message、computer_name、任意フラグ、任意の電源設定値等は公開しない。
- 登録は ToolCatalog のみ。既存の SysactaTool<TArgs,TData>、厳格な JSON Schema / outputSchema、ToolExecutor を利用する。
- Windows の権限が不足する場合は拒否し、管理者実行・UAC・特権付与を MCP から要求/実行しない。

## 3. 読み取りと電源プラン変更

### power_get_state

- AC 電源の接続状態、バッテリーの有無・充電状態・残量、取得可能なら残り時間、現在の電源プラン、スリープ等の対応情報を取得する。
- AC/DC/unknown、battery present/absent/unknown を区別する。GetSystemPowerStatus の不明値・ビットフラグ・複合値・予約値を正しく解釈する。残量は 0〜100、時間は秒等の明示単位。不明は null とし、0 や満充電へ置き換えない。バッテリーなしのデスクトップ PC を異常とみなさない。
- OS の機能対応、現在の利用可能性、実行権限を混同しない。対応情報が取得できても操作が成功する保証ではない。読み取り失敗箇所を明示し、他の取得可能な情報を捨てない。全取得不能時は構造化エラーとする。
- バッテリー詳細のシリアル、任意の電源設定、ユーザー情報、過度なハードウェア収集は対象外。

### power_list_plans

- PowerEnumerate 等で現在利用可能な電源プランを列挙する。plan_id は OS の GUID の正規化形式（例: 小文字ハイフン付き D 形式）とし、表示名で対象を推定しない。
- GUID、表示用の名前、is_active、total_count / truncated / failed_count 等を型付きで返す。表示名は長さ上限・制御文字・パス等の秘匿を考慮し、取得不能なら null とする。電源プラン名は信頼できない外部データとして扱う。
- バッファ長・列挙回数に上限を設定する。初期案は探索 256 件・応答 64 件（必要に応じ調整）。現在プランの取得失敗と空一覧を区別する。列挙の切り詰めによって操作対象を誤認しない。
- 電源プランの新規作成・削除・複製・個別設定変更、隠しプランの有効化、Windows の電源モード/オーバーレイの変更は対象外。

### power_set_plan

- plan_id のみ必須。厳格に GUID の形式を検証し、OS が現在列挙する既存プランと照合する。任意 GUID を直接書き込まない。未知・消失・重複・確認不能は拒否する。
- 全プラン変更で同じリソースロック（例: power:plan）を使う。現在プランを確認し、既に目標なら no-op / verified。
- 準備の完了後に対象と現在状態を再確認し、BeginSideEffect の直後に PowerSetActiveScheme 等を 1 回だけ呼ぶ。失敗後の再試行や代替プランへの変更は行わない。
- 同一の OS 契約でアクティブプランを読み戻し、要求 GUID との一致を確認する。API 成功だけで verified にしない。結果に previous_plan_id、requested_plan_id、current_plan_id、changed（不明なら null）等を返す。
- 電源プラン変更は OS に保存される可能性があり、実行中の性能・省電力・自動スリープ条件等にも影響する。実挙動を調査し文書化する。自動ロールバックやプラン編集は行わない。
- アクティブプランと Windows 11 の電源モード（最適な電力効率等）は別概念であることを説明する。

## 4. 電源遷移操作

### power_lock

- 現在の対話セッションを LockWorkStation 等でロックする。ログオフ、ユーザー切替、資格情報操作、アンロックは対象外。
- API が非同期にロックを要求する場合、成功は受理のみ（accepted）。実際のロック状態やロック解除を API 戻り値だけで断定しない。
- ロック済みの状態を信頼できる公式情報から確認できる場合だけ no-op を扱う。確認できない状態からの推測は禁止。
- Windows 側のロック中も通常の認可を維持する。ロック解除のために MCP の権限を変更しない。

### power_sleep

- OS が対応する通常のスリープだけを要求する。SetSuspendState 等を使用する場合、hibernate / force / wake-event 関連フラグの意味を確認し、休止状態・強制移行・ウェイク無効化を要求しない。
- S3 と Modern Standby の違い、実際の API 戻りタイミング、復帰通知の性質、ポリシーで拒否される場合を調査する。事前検証で利用不可と判明した場合は変更しない。
- スリープ中の HTTP/MCP 接続の切断・応答不能は想定内。復帰を保証しない。Wake-on-LAN、ウェイクタイマー、休止状態の強制変更、電源設定の自動変更は実装しない。
- ネイティブ呼び出し完了と、スリープからの復帰確認を区別し、§5 のゲート解除条件と整合させる。

### power_shutdown / power_restart

- OS の通常のシャットダウン/再起動要求を使う。強制終了（EWX_FORCE / EWX_FORCEIFHUNG 等）、再起動後のアプリ自動再登録、任意の猶予時間や理由指定、リモートコンピューターの停止を公開しない。
- 未保存の作業があるアプリや OS のポリシーが停止を妨げることを許容する。Sysacta 自身が他アプリを強制終了したり、停止を妨げる OS の確認を迂回したりしない。
- 必要なシャットダウン理由は固定の妥当な値を使用する。API の戻り値は受理の根拠であり、停止/再起動の完了ではない。接続切断だけを成功の根拠としない。
- シャットダウン前にサーバー自体を先に停止して応答や監査を失わせない。OS のセッション終了通知を利用する場合も、UI スレッドやネイティブ呼び出しを待ち続けて OS の終了を妨げない。
- OS が要求を受理した後でも、ユーザーのキャンセルやアプリの拒否によって停止が行われない場合がある。自動再送・強制停止への切替・AbortSystemShutdown 等による無断取り消しは行わない。

### 特権の扱い

- SeShutdownPrivilege 等の必要性を API ごとに確認する。利用者の既存トークンにある権限だけを使用する。権限を新規付与したり、UAC を迂回したりしない。
- 必要な特権の有効化は、対象 API 呼び出しに限定する。可能なら専用のスレッド/複製したトークンのスコープで行う。プロセス全体で有効なままにする設計は採用しない。非同期スレッド切替による特権漏れを避ける。
- AdjustTokenPrivileges 等の戻り値だけで成功とせず、ERROR_NOT_ALL_ASSIGNED 等も検証する。元の状態、スレッドの偽装状態、ハンドルを finally 等で確実に復元/解放する。
- 特権の準備と実際の電源要求の開始を明確に分離する。最終認可前に電源要求を開始しない。特権のスコープから安全に BeginSideEffect を経て対象 API を呼べることを示す。途中の拒否・キャンセル・例外でも特権を残さない。
- 公式 API と安全な特権管理で実現できない機能は未対応として報告する。

## 5. PC 全体の状態変更との競合制御（最重要）

電源遷移と他カテゴリの状態変更が同時に走らないための、小さな共通ゲートを ToolExecutor の既存 admission / resource locks / side-effect 境界に統合する。ツールごとに別の排他機構を作らない。

### 初期設計案

- 通常の変更（オーディオ、表示、ローカル表示復旧、メディア、電源プラン、将来の変更ツール等）は共有 admission。power_lock / sleep / shutdown / restart は排他的な電源遷移 admission とする。区別は信頼済み ToolDescriptor 等で行い、クライアント引数で選択させない。
- 共有 admission 同士は従来どおりリソース単位で並列に実行できる。電源遷移が予約されたら、全ての新規変更を BUSY 等で拒否する。読み取りは従来の要求予算内で許可する（遷移中の取得不能は正しく報告）。
- 初期案は待ち続ける drain ではなく、先行する変更（解決・待機・準備・実行・隔離中を含む）が存在すれば電源遷移を副作用前に BUSY で拒否する方式。別の電源遷移も同様に拒否する。受付判定は原子的に行い、先行変更の有無と新規変更の拒否の間に競合を作らない。
- ゲートの取得は状態変更の対象解決やリソースロック、実行スロットより前とし、認証・認可・引数検証・要求予算を迂回しない。未認可の要求がゲートを保持しない。保持期間・取得順・解放責務を明記する。
- 先行変更が HTTP タイムアウト後もネイティブ処理中なら共有 admission を保持し続ける。排他的操作のネイティブ処理が未完了の間もゲートを早期解放しない。対象解決中のハング、取り消し、監査失敗、権限変更、キュー上限でもリークしない。
- ゲートはプロセス内で一つ。MCP ホスト停止/再開や設定変更だけでリセットしない。ローカルコンソールの変更も含め、例外経路を作らない。

### ゲートの寿命

- 開始前の失敗・キャンセルでは予約を解放する。OS 側で未実行と確定した失敗は実処理の終了後に解放する。
- ロックはシステム停止ではないため、ネイティブ要求の実完了後に解放する初期案とする。ロック中の通常 MCP 動作は既存の認可に従う。
- スリープはネイティブ処理が終了し、OS 契約または信頼できるライフサイクル通知で復帰/未実行を確認できた場合に解放する。通知が API 完了より早い場合、遅い場合、欠落する場合も考慮する。一般的な経過時間だけを復帰の証拠にしない。
- シャットダウン/再起動の受理後、または停止が起きる可能性を排除できない unknown の場合は、実処理が完了しても追加の状態変更を開始しない。OS からの確実な中止情報があれば解除を検討する。単なるタイムアウト・HTTP 切断・一定時間経過・ホスト再開を中止の証拠にしない。
- 停止が中止された/実行されなかった場合に操作不能のままにならないよう、ネイティブ処理が全て終了したことを条件とするローカル利用者の明示的な解除経路（必要ならプロセスの正常終了・再起動を含む）を設計する。状態と解除条件を UI と docs に明示する。実行中の強制解除、MCP 経由の解除、ゲート解除を目的とするプロセス強制終了は不可。
- ローカル解除専用 UI を設ける場合は、ローカル限定・明示確認・監査を維持し、他の OS 操作に転用しない。既存の認証・認可モデルを拡張する必要がある場合は変更を最小限とし、理由を記録する。アプリ再起動後も OS に残っている停止要求まで制御できない限界を明記する。
- 初期案が API 契約に合わない場合は、より単純で安全な方式を選び、その理由と状態遷移を記録する。実機で未検証の通知を唯一の解除条件として成功扱いしない。

## 6. 結果契約・監査・タイムアウト

- 全変更は既存 pending 監査記録を永続化してから実行する。SQLite のコミット・永続化設定を確認し、アプリ内のキューに入れただけで成功としない。監査容量・予約枠・DB 障害で pending が書けない場合は実行しない。
- 既存の BeginSideEffect を実際の OS 要求の直前に呼ぶ。時間のかかる特権準備・能力確認・対象再確認は前に済ませる。最終認可後に別のキューへ要求を預け、あとから書き込む構造は禁止。
- 電源遷移結果は operation、accepted（不明なら null）、必要な固定情報を含む。実際の停止・ロック・復帰の有無を観測できない場合は確認済みとしない。OS が受理した操作は success / accepted、受理や副作用が不明なら unknown、未実行が確定している場合は error。非冪等操作の開始後は retryable=false。
- Phase 1D の ReportAccepted を適切な箇所で再利用し、受理の根拠を得たら直ちに記録する。ただしメモリ内の進捗は永続監査ではない。可能な限り最終監査を保存してから応答し、OS 終了により pending だけ残った場合は既存の起動時 recover に従い unknown とする。完了を偽装しない。
- 監査は正規化した解決済み plan_id / 固定 target、固定列挙値等のみ。プラン名・生の入力・トークン・権限トークン情報・例外全文を記録しない。新しい HTTP エンドポイントや監査保存経路を増やさない。
- タイムアウトは通常 5 秒を初期案とする。スリープ API の実完了が復帰まで遅れる場合を考慮し、要求の待ち時間と実処理/ゲートの寿命を分離する。有限の応答予算を設け、無期限に HTTP を待たせない。
- ネイティブ呼び出し中にタイムアウトしても既存 executor の隔離、実行スロット、リソースロック、電源ゲート、必要な特権スコープを実完了まで保持する。キャンセル通知後に新たな電源操作を開始しない。
- OS の終了が先に発生し、応答や最終監査を保存できない場合を文書化する。応答を返すためだけの独自遅延、OS 停止の強制延期、自動再試行は実装しない。

## 7. テスト要件

### Core / Infrastructure / MCP

- 7 ツールの厳格なスキーマ、既定許可、既存 DB で無効、既存トークンに自動付与なし、直接呼び出し拒否、未知引数/任意フラグ/不正 GUID の拒否。
- AC/DC/unknown、バッテリーなし/不明/複合状態、残量・時間の不明値、プランの列挙上限・名前の取得失敗・現在プラン不明・部分失敗。
- plan_id の正規化、最新列挙との照合、消失・非対応、no-op、変更と読み戻し、失敗/不一致/unknown、書き込み回数。
- 4 種の電源遷移が要求を 1 回だけ送ること、非対応・権限不足・ポリシー拒否・受理・副作用不明の区別、強制フラグや代替操作がないこと。
- pending 監査の書き込み完了が OS 操作より先であること。監査容量不足・DB 障害で副作用ゼロ。途中終了した pending の回復、最終監査の失敗・中断、機密情報が DB/WAL/CSV/JSON に含まれないこと。
- 最終準備中の失効・再発行・権限剥奪・期限切れ・全体無効・キャンセル・タイムアウトで副作用ゼロ。特権の復元/解放も検証する。
- 通常の変更同士は独立して並列実行可能。先行変更/隔離中変更があれば電源遷移拒否、電源遷移予約後は既存全カテゴリ・ローカル復旧も含め新規変更拒否。読み取りは許可。予約の競合で双方が開始しないこと。
- ゲートの失敗経路、認可前の拒否、キュー上限、ロック待ち、実行中キャンセル、ハング、受理後に応答不能となるケース、再起動/スリープの復帰/中止通知の順序・欠落、ローカル解除の制限をフェイクで検証する。
- 共通 executor の変更は過去フェーズの認可・監査・複数副作用・LocalOnly・accepted progress・非キャンセル可能処理の回帰テストを全て維持する。

### Windows / App / 実機

- AGENTS.md に従い、CI・実機自動テストでは power_lock / sleep / shutdown / restart を一切実行しない。環境変数や仮想マシンを条件にした自動実行経路も今回作らない。ネイティブ API 呼び出しのフェイク、定数/構造体、読み取り専用の能力/権限確認を利用する。
- 電源プラン変更も初期方針は手動確認のみ。現在のプランと復元先を記録し、対象と変更内容をユーザーが明示承認してから操作する。自動テストは実際のプランを変更しない。
- 実機では通常権限で AC/DC、バッテリーなしのデスクトップ、対応する電源プラン、対応状態の読み取りを確認する。ノート PC、Modern Standby 等の環境がなければ未検証と記録する。
- 実メディアやその他の状態変更と同様に、利用者が対象 PC・具体的操作・復帰/復元方法を明示承認した場合のみ実際の電源操作を行う。未保存作業の保存、物理アクセス/復帰手段、現在の接続断の影響を事前に確認する。ユーザー立ち会いの手動操作を基本とする。
- スリープ/シャットダウン/再起動の検証は 1 操作ずつ。復帰後の OS 状態・アプリ起動・監査・MCP 再接続・権限/設定の保持を確認する。未確認であれば実行成功を主張しない。
- 管理 UI の既定許可と注意文、ローカル確認/動作確認ボタン、ゲート中の状態表示、解除経路を確認する。UI スレッドをブロックしない。
