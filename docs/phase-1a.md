# Sysacta — Phase 1A: 共通セキュリティ基盤の残課題

## 目的と範囲

Phase 0 のマージ後、機能追加およびリモート運用の前に、独立セキュリティレビューで延期した SEC-05 と SEC-06 を解消する。

- SEC-05: [認証・DB 処理より前の要求予算](https://github.com/clagon/sysacta/pull/1#discussion_r4701667255)
- SEC-06: [監査ログの保存量上限](https://github.com/clagon/sysacta/pull/1#discussion_r4701667259)

本書は実装指示であり、完了報告ではない。Phase 1A は追加の実装管理上の区分で、全体仕様の機能範囲を変更しない。

最初に README.md、AGENTS.md、docs/spec.md、docs/security.md、docs/tools.md、docs/phase-0-progress.md、docs/manual-tests.md と現行コードを確認する。既存の実装とテストを基準とし、Phase 0 の認証・認可・監査・排他・タイムアウト・副作用開始点の保証を弱めない。

## 1. 作業方針

- 最新の main から専用ブランチ（例: phase-1a）を作成し、独立した PR にする。main へ直接実装をコミットしたり、自動マージしたりしない。
- SEC-05 と SEC-06 に限定し、追加の MCP ツール、全面的な UI リニューアル、配布機構、依存関係の大規模変更には着手しない。
- 既存の型、責務、依存方向を優先し、不必要な汎用フレームワークを作らない。
- 新しい上限値は個人用・少数クライアントの MCP サーバーを前提とする。下記の値は初期案であり、安全性と通常利用への影響を測定して調整してよい。変更理由を記録する。
- テストは一時 DB、合成トークン、フェイク OS アダプター、ループバック専用ホストで行う。実際の認証情報、通常のユーザーデータ、公衆ネットワーク、電源・切断操作を使用しない。
- Windows 実機で確認できないものは未確認として記録する。計画のみで終了せず、実装・ビルド・テスト・修正まで進める。

## 2. SEC-05 — 認証前の処理予算

### 現状

`RequestGuards.InvokeAsync` が Host/Origin を検証した後に `TokenAuthenticator.Authenticate` を呼ぶ。認証失敗の監査制限はその後であり、形式が正しい不明トークンは毎回 SQLite を照会できる。有効なトークンも認証内で `RecordClientUse` を呼ぶため、クライアント別のレート制限より先に DB 更新処理へ到達する。

主要な変更対象: `Sysacta.Mcp/RequestGuards.cs`、`McpServerHost.cs`、`ServerEndpointOptions.cs`、`Sysacta.Core/Security/ClientTokens.cs`、関連テスト。必要に応じて AccessStore を変更する。

### 要件

1. DB 照会・監査書き込みに到達する前に、全体と接続元単位の要求予算を適用する。Host/Origin などの安価な検査は先行してもよいが、不正リクエストの監査自体が予算を迂回しないこと。
2. 接続元はソケット由来のアドレスだけを利用し、IPv4-mapped IPv6 等を必要に応じ正規化する。Forwarded / X-Forwarded-For や任意ヘッダーを信用しない。localhost も例外にしない。
3. 認証は引き続き毎回検証する。トークンや権限をキャッシュして即時失効を弱めない。生トークンや未認証トークンのハッシュをレート制限のキーにしない。
4. 認証成功後のクライアント別要求予算（既存の 60 件/分）を通過した場合にのみ最終利用日時を更新する。更新の既存間隔（1 分）も維持する。過剰リクエストに対して書き込みを行わない。
5. 全体・接続元・クライアント単位の各上限は有限にする。認証前の同時処理も有限にし、無制限の待機キューやパーティションの増加、リミッターのタイマー漏れを発生させない。使用済みキーの保持・解放とホスト再起動時の破棄を確認する。
6. 予算超過は原則 429 とし、可能なら Retry-After を付与する。予算を通過した不正認証は 401、Host/Origin 違反は 403 を維持する。エラー応答には秘密・入力文字列・内部例外を含めない。過負荷の拒否ごとに DB を更新しない。
7. Tailscale Serve 等のリバースプロキシでは複数クライアントが同じ接続元に見える。正規クライアント数と認証前予算の関係、同一接続元での公平性の限界、調整方法を docs/security.md に記載する。

初期値の案（計測で変更可）:

| 項目 | 初期案 |
|---|---:|
| 認証前の全体要求予算 | 600 件/分 |
| 認証前の接続元別要求予算 | 240 件/分 |
| 認証前処理の同時実行数 | 8 |
| 認証後のクライアント別要求予算 | 60 件/分（既存値維持） |
| 拒否監査の接続元別予算 | 30 件/分（既存値を上限として維持） |

これらは HTTP リクエストの予算であり、ツール実行数とは区別する。待機は原則なし。必要なテスト用設定は注入可能にするが、設定 UI を複雑にする必要はない。

### テスト・完了条件

- 実 Kestrel と一時 DB、または呼び出し回数を数えるストアを使用する。
- 形式が正しい不明トークンの超過リクエストが DB 照会・監査書き込みを増やさない。
- 有効トークンのクライアント別上限を超えた要求が最終利用日時の更新処理を増やさない。
- Host/Origin 違反・認証失敗・不正ヘッダーも全体予算を迂回できない。
- 偽造転送ヘッダーで接続元予算を分散できない。
- 複数の正規クライアントの通常リクエストが成功し、既存の認証・権限分離・再発行・失効テストが引き続き成功する。
- 同時リクエスト、接続元の増加、停止・再起動・起動失敗でも予算とリソース管理が破綻しない。
- 低い試験用上限や制御可能な時計で決定的に検証する。実際の利用環境に負荷攻撃を行わない。

## 3. SEC-06 — 監査ログの保存量上限

### 現状

`AuditLog.Write` は SQLite の audit_events に記録し、`Purge` は保持日数による削除だけを行う。継続的な拒否やツール呼び出しによって監査 DB が肥大化し、同じ DB を利用する認可・設定保存・事前監査が失敗する可能性がある。

主要な変更対象: `Sysacta.Infrastructure/AuditLog.cs`、`SysactaDatabase.cs`、`Sysacta.Core/Auditing/AuditEvent.cs`、`ToolExecutor.cs`、`RequestGuards.cs`、`SysactaRuntime.cs`、必要最小限のログ管理 UI、関連テスト。

### 要件

1. 既存の保持日数（既定 30 日）に加えて、監査レコード数と監査データの保存量を制限する。各レコードの可変長フィールド、集約データ、インデックス、SQLite DB/WAL の増加も考慮する。件数だけで物理ファイルサイズの上限を保証したことにしない。
2. 監査の新規書き込み・更新・古い記録の整理を競合に強い形で実装する。並列リクエストでも上限を無制限に超えない。毎回の全テーブル走査、長時間の UI ブロック、要求ごとの VACUUM を避ける。
3. 認証失敗・Host/Origin 拒否・過負荷拒否など低優先度の監査は、全体予算を超えたら一定期間の集約カウンターで表現する。入力文字列、未認証トークン、任意の接続元を無制限に集約キーにしない。集約レコード自体のサイズ、件数、書き込み頻度も制限する。無制限の非同期キューを作らない。
4. 状態変更の pending 監査と最終結果の保存を優先し、低優先度ログによって必要な枠が使い切られないようにする。進行中の pending レコードは保持期間・容量整理の対象にしない。異常終了で残った pending と現在進行中の pending を区別する方針を明確にする。
5. 状態変更前の監査が永続化できない場合、従来どおり AUDIT_UNAVAILABLE で拒否し、OS に副作用を発生させない。監査枠不足を理由に監査を省略して実行しない。完了記録の書き込みに失敗した場合は pending を残し、結果不明の可能性を誤魔化さない。
6. SQLite のページ再利用、WAL チェックポイント、必要に応じた安全な圧縮・整理方法を検討する。WAL の上限設定だけでは長時間の読み取り等による増加を完全には防げない。物理サイズの目安・超過時の動作・ファイル縮小の条件を区別して文書化する。監査以外の設定・権限・トークンを削除しない。
7. 既存 DB を壊さずアップグレードできるよう、必要な変更は新しいマイグレーションとして追加する。既存マイグレーションを書き換えない。過大な既存 DB は安全に整理し、処理失敗時の動作と復旧手段を明記する。
8. ログ画面から保持期間・容量制限・集約や欠落の有無を理解できるようにする。最低限、現在の上限と集約・削除が発生したことが利用者に分かること。すべての試行を個別記録できたように見せない。
9. 検索・フィルタ・CSV/JSON 出力において、集約記録と通常レコードを区別できるようにする。既存の機密情報保護（SEC-03）と CSV 数式注入対策を維持する。MCP からログ削除や設定変更の手段を追加しない。

初期値の案（計測で変更可）:

| 項目 | 初期案 |
|---|---:|
| 保持期間 | 30 日（既存設定維持） |
| 通常監査レコード上限 | 100,000 件 |
| 監査の論理保存量上限 | 64 MiB |
| 拒否監査の全体個別記録予算 | 120 件/分 |
| 拒否集約の期間 | 1 分 |
| 状態変更用の予約枠 | 1,000 件および論理保存量の 10% を目安 |

予約枠は全体上限の内数とする。具体的な計算方式、集約フラッシュの頻度、バイト数の定義、物理 DB/WAL の管理方式は現行 SQLite 実装に合わせて決定する。上記値を機械的に採用して過剰な複雑化を招かないこと。実ディスクの残容量を保証できない場合は fail-closed の動作を優先する。

### テスト・完了条件

- 小さな件数・保存量上限を使用した一時 DB で、大量の拒否を発生させても保存レコード数と集約処理が有限である。
- 容量上限に達したときも、予約枠が残っていれば状態変更の pending と最終結果が記録される。
- 予約枠も尽きた場合や DB 書き込み失敗時は、状態変更が拒否され、フェイク OS アダプターの書き込み回数がゼロ。
- 同一 request_id の pending から最終結果への更新が、新規行として二重計上されない。
- 進行中の pending が整理処理で消えない。異常終了からの再起動で、古い pending を所定の方針に従い扱える。
- 並行する書き込み・整理・検索・エクスポートの整合性が保たれる。
- 既存 DB のマイグレーション後もクライアント・権限・設定が保持される。
- DB 本体、WAL、論理データ量を長時間読み取り・継続書き込みのテストで観測し、上限・超過時の挙動を記録する。負荷試験は有限の回数・時間で終了させる。
- 合成の機密文字列が DB・WAL・CSV・JSON に残らない。集約時にも自由入力値を保存しない。
- 既存の監査・認可・タイムアウト・副作用開始点の回帰テストが成功する。

## 5. 完了条件

- 認証前の全体・接続元の処理予算が DB 照会と拒否監査より前に適用される。
- クライアント別予算の超過要求から最終利用日時の更新が発生しない。
- 拒否監査の総量、集約、監査保持量に有限の制限がある。
- 状態変更用の事前監査は保護され、保存できないときに副作用が発生しない。
- 監査整理が既存データ・権限・進行中の監査を破壊しない。
- SQLite の物理容量と論理容量を区別し、WAL や異常時を含む管理方針が明記されている。
- 既存機能の回帰テスト、新規テスト、Windows CI が成功し、未検証事項が記録されている。
- Phase 1A の PR に修正・テスト・判断理由がまとまり、独立レビュー可能な状態になっている。

最終報告には実装内容、上限の一覧、テスト結果、仕様との差分、残存リスク、PR URL を含める。重大な問題が残る場合は完了とせず、ブロッカーを報告する。Phase 1B 以降の機能実装やマージは別タスクとする。
