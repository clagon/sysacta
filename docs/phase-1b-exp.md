# Sysacta — Phase 1B-EXP: 既定オーディオデバイス変更

## 目的と範囲

spec §7.1 / §8 / §9 / §10 / §12 および phase-1b.md §8 に従い、audio_set_default_device の実現性を調査し、安全に実装できる場合に限り追加する。Phase 1B の通常機能はマージ済み。既定デバイス変更は Experimental の独立したタスクとする。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/phase-0-progress.md、docs/phase-1a-progress.md、docs/phase-1b-progress.md、docs/manual-tests.md を読み、現行コードとテストを確認する。最新 main から専用ブランチ（例: phase-1b-exp）を作成し、独立した PR にする。自動マージしない。

既存の 7 オーディオツール、デバイス管理画面、認証・認可・監査容量・要求予算を維持する。Phase 1C 以降には着手しない。

## 1. 技術調査・採否判定

実装前に、以下を確認し、根拠を docs/phase-1b-exp-progress.md に記録する。

- Microsoft の公式 API で、ユーザーセッション全体の既定オーディオエンドポイントを方向・役割別に変更できるかを調査する。既定値の読み取り、アプリ個別のルーティング変更、音量変更の API と混同しない。
- 公式 API を優先する。利用可能な公式の変更 API が見つからなければ、既存 OSS で使われている方式（例: PolicyConfig 系 COM インターフェース）を候補として調査する。候補名だけで ABI や動作を確定しない。
- 採用候補について、参照したソースの URL・コミット・ライセンス、COM クラス / インターフェース / メソッドの契約、Windows 11 での対応状況、x64 での互換性、必要権限、アパートメントモデル、失敗時の挙動を確認する。
- 非公開 API は将来の Windows 更新で動作しなくなる可能性を明記する。ABI が確認できない方式を試行錯誤で呼び出さない。危険な複数方式の自動フォールバックは作らない。
- サードパーティのコードを無断で転用しない。依存パッケージを追加する場合は、ライセンス、必要性、実行時の外部通信、ネイティブコードの由来を確認する。
- DLL 注入、カーネル改変、レジストリの直接書き換えによる強引な代替、GUI 自動化、外部 CLI、権限昇格、セキュリティ機構の回避は禁止する。

調査の結果、通常権限で安全に変更・検証できる根拠が十分な場合だけ実装に進む。Windows 実機での検証に至らない場合は未検証とし、利用可能だと断定しない。根拠が不足する場合は、未対応という結論と調査結果を PR にまとめる。動作しない実装を無理に公開しない。

## 2. ツール契約

| 項目 | 内容 |
|---|---|
| 名前 | audio_set_default_device |
| カテゴリ | audio |
| 引数 device | 必須。デバイス ID または登録済み別名 |
| 引数 direction | 必須。input / output |
| 引数 role | 必須。console / multimedia / communications / all |
| 種別 | 状態変更、ReadOnly=false |
| DefaultPolicy | Experimental |
| タイムアウト | 既存の 5 秒を初期案とし、実測で必要なら理由付きで変更 |

引数は既存の型定義・JSON Schema 生成・検証を使う。device には長さ制限と NoControlCharacters を付ける。方向・役割は列挙型で厳密に検証する。all は指定方向の 3 役割を意味し、デバイスの一括指定ではない。既存の AudioRole（OS の 3 役割）に all を混入させて未定義値を OS に渡さない。

明示的な対象指定を必須とし、device の省略、null、予約語 all / default、未知引数、範囲外の列挙値、型の暗黙変換を拒否する。対象は OS の正規 ID に解決し、別名・ID が見つからない場合、別方向、不活性・切断の場合はエラー。別機器へのフォールバックは行わない。

DefaultPolicy.Experimental は初回導入・アップグレードのどちらでも無効とする。既存トークンへ権限を自動付与しない。管理コンソールの既存の実験的表示を活用し、通常ツールと区別する。公式 API が見つかった場合も本タスクでは Experimental として扱い、通常機能への昇格は別途判断する。

## 3. アダプター・能力判定

- Core に最小限の変更用インターフェースを定義し、既存の IAudioEndpoints.GetDefaultEndpointId(direction, role) を読み戻しに活用する。通常の読み取り・音量・ミュートに非公開 API を混ぜない。
- 非公開 API 実装は Sysacta.Windows/Experimental/Audio 等の明確な場所に隔離し、COM 初期化・参照の所有権・解放・HRESULT の変換を確認する。
- 実行前の COM オブジェクト生成や対象検証など、変更を伴わない準備を可能な限り済ませてから最終認可を行う。生の COM 例外、ローカルパス、内部診断情報を応答に含めない。
- 能力判定は安価で副作用なし。既知の恒常非対応、必要なインターフェースの欠如等では tools/list に出さず、直接呼び出しも拒否する。能力判定のために既定デバイスを実際に変更しない。
- 一時的な COM 障害やデバイス切断は構造化エラーとし、根拠なく恒常非対応と判定しない。未検証のビルド・環境では安全側に扱い、根拠とサポート範囲を文書化する。
- ToolCatalog、既存の許可管理・動作確認 UI を通す。別の HTTP エンドポイントや OS 操作経路を作らない。

## 4. 既定対象操作との排他

現状の AudioTarget.Resolve は省略時に multimedia の既定 ID を取得してから audio:device:{id} と audio:default:{direction} を取得する。ロック取得前の解決結果が古くなる可能性があり、また read-only ツールは ToolExecutor でロックされない。今回、変更操作の競合を明示的に扱う。

- 役割ごとの共通キーを定義する（例: audio:default:{direction}:{role}）。既存の省略時変更操作（audio_set_volume / audio_set_mute）は multimedia のキーを共有するように揃える。
- 新ツールは対象方向・役割のキーと必要な正規デバイスキーを取得する。all の場合は 3 役割すべてを固定順序で取得する。ResourceLocks の既存の順序付けを利用し、ネストしたロック取得によるデッドロックを避ける。
- 既定指定の音量・ミュート変更がロック待機中に既定デバイス変更をまたいだ場合、ロック取得後に現在の既定 ID を再検証する。解決済み ID が既定でなくなったら副作用なしで明示的に拒否し、再取得・再試行を促す。別の ID にロックを持たず変更したり、暗黙に再ターゲットしたりしない。
- 新ツールもロック取得後に対象の正規 ID、方向、Active 状態、役割ごとの現在値を再確認する。明示 ID や別名で解決済みの操作は別機器にすり替えない。
- ロックは変更後の読み戻しまで保持する。ネイティブ処理がタイムアウトしても終了前に解放しない。
- 読み取り専用ツールは既存仕様上、変更ロックを取らない。読み取りが競合時のスナップショットとなることを明記し、混在した状態を不可分な一貫性のあるスナップショットと主張しない。必要な場合だけ局所的な再確認を行う。
- Windows の設定画面など外部操作は Sysacta の排他対象外である。外部操作による変化を検出したら実測の結果として返し、無断で上書きし続けない。

## 5. 副作用開始点と複数役割の変更

- 既存 ToolExecutor の認証・認可・pending 監査・実行制限・AuthorizationGate・ToolExecution を必ず利用する。
- 状態が既に目標と一致する役割は no-op。すべて一致すれば書き込みゼロで成功 / verified を返す。
- 最初の実際の OS 書き込み直前に execution.BeginSideEffect() を呼ぶ。事前の監査永続化や最終認可が失敗した場合、OS 書き込みはゼロとする。
- all は複数の OS 呼び出しになる可能性があるため、最初の書き込み後にキャンセル・期限切れ・トークン失効・権限取り消し・全体無効化が発生しても、その後の新しい書き込みを無条件に続けない。役割ごとの開始直前にキャンセルと最新の認可を確認する。
- 現行 BeginSideEffect() は Started 状態では no-op であり、再度呼ぶだけでは再認可にならない。複数副作用に必要な場合は、開始点の状態管理を壊さず、後続の副作用の直前に認可を再検証する最小限の共通 API を追加する。前の変更済みの事実を失わず、タイムアウト後に新たな書き込みが始まらないようにする。
- 長時間の OS 呼び出し全体を AuthorizationGate の内側に置かない。既に開始したネイティブ処理は取り消せないという既存の残存リスクは維持する。
- 一つの役割だけを指定した操作が他の役割や方向まで変更しないか、採用 API の実際の挙動を確認する。役割ごとの独立変更を保証できない API は、仕様どおりの成功を返さない。
- 失敗、不一致、認可取り消し、キャンセルが起きた場合は残りの変更を停止する。自動リトライ、無断のロールバック、別機器への変更を禁止する。

## 6. 結果契約・部分成功

各役割について変更前の ID、要求 ID、確認できた変更後の ID、changed（確定できなければ null）、処理状態、必要に応じた固定のエラーコードを返す。all の未着手役割も区別する。OS から取得できない値は null 等で表現し、成功を推測しない。

結果データの初期案:

- device_id: 正規の対象 ID
- direction: input / output
- requested_role: console / multimedia / communications / all
- roles: 各役割の role / previous_device_id / current_device_id / changed / status / error_code
- 役割の status: unchanged / changed / failed / unknown / not_attempted（命名は既存契約と調整可）

外枠の status は spec §9 に従い、すべての指定役割が一致すれば success / verified、確定した一部成功と未達が混在すれば partial、不明な副作用が残る場合は unknown（確認済みの役割結果を可能な限り維持）、変更されていないことが確実な失敗は error とする。変更 API が成功しても読み戻しできなければ verified にしない。partial / unknown は無条件に再試行可能としない。

現行 ToolStatus / AuditOutcome は Partial を持つが、ToolOutcome<TData> と ToolExecutor の正常経路は success 固定である。今回必要な範囲で、型付きの部分結果と不確実な結果を伝える仕組みを共通基盤に追加する。既存の成功・拒否・エラー・unknown の契約を壊さず、MCP isError、outputSchema、管理 UI、監査の最終 outcome と整合させる。認可拒否が初回書き込み前か変更開始後かを区別する。タイムアウト時に全役割の詳細を確定できない場合は unknown を返し、完了したと偽らない。全ツールの実行基盤を全面的に作り直さない。

監査は既存の allow-list（direction / role 等の列挙値）と解決済み target を使う。生の device、引数全文、結果全文、トークン、例外メッセージを記録しない。pending → 最終結果の一貫性と Phase 1A の容量制限を維持する。

## 7. テスト・検証

### Core / Infrastructure / MCP

フェイクアダプターと一時 DB を使い、以下を自動テストする。

- Experimental が新規 DB・既存 DB とも無効で開始し、既存トークンに自動付与されない。全体許可と個別許可、能力判定が tools/list と直接呼び出しの両方に適用される。
- 必須引数、明示 null、未知引数、不正 role / direction、予約語、未知 ID、別方向、非 Active 機器を拒否する。
- 各方向・各役割の変更、全役割変更、no-op、変更前後の読み戻し、API エラー、読み戻し不一致・不能、部分成功、未着手役割、結果不明。
- 同一役割の変更と既定指定操作が共有ロックを利用し、all が他の役割変更と競合してもデッドロックしない。ロック取得後に既定が変わった既存音量・ミュート操作は誤対象に書き込まない。
- 初回書き込み前の失効・再発行・権限剥奪・期限切れ・監査不能で副作用ゼロ。
- all の途中で失効・再発行・権限剥奪・期限切れ・キャンセル・タイムアウト・API 障害が起きた場合、既に行った変更を報告し、未着手役割への書き込みがないこと。
- 開始前のタイムアウトは未変更、開始後は結果不明となり、実際のネイティブ処理が終了するまでロック・スロットを維持する。
- partial / unknown の構造化結果・スキーマ・監査・UI 表示の整合性、既存ツールの回帰テスト、SEC-03 / SEC-05 / SEC-06 の保証維持。
- 合成の機密入力が DB/WAL/CSV/JSON に残らない。

### Windows 実機

- 調査だけでは安全性・互換性を保証しない。実機の Windows ビルド、権限、API 実装、検証結果を記録する。
- 副作用のない能力判定、方向別・役割別の既定デバイス読み取りは通常テストで確認する。
- 既定デバイス変更は会議・通話・録音や音声入出力に影響するため、利用者が対象機器と変更を明示承認した場合に限って実行する。SYSACTA_HARDWARE_TESTS=1 だけを根拠に無断実行しない。
- 変更テストを実施する場合、元の 3 役割の ID を方向ごとに保存し、復元可能であることを事前確認する。役割別・all の変更と読み戻しを行い、テスト専用の復元処理で元の状態に戻す。復元失敗は明示する。製品側の自動ロールバックとは区別する。
- 同じ機器を操作するテストは直列に実行する。必要な別機器がない、復元手段がない、承認がない場合はスキップする。通常の Windows CI では実際の既定デバイスを書き換えない。
- 実機検証前の実装は検証状況を明示する。安全な方法で検証できない場合、動作確認済みとして公開しない。

## 8. 完了条件・成果物

実装可能と判断した場合:

- 根拠付きの API 選定、隔離されたアダプター、Experimental の許可制御、役割別の排他・開始点・結果検証が実装されている。
- 既存ツールの契約を壊さず、partial / unknown の必要な共通基盤と回帰テストが追加されている。
- dotnet build Sysacta.sln -c Release が警告・エラーゼロ、dotnet test Sysacta.sln -c Release と Windows CI / スモークテストが成功する。
- Windows 実機での確認状況を明示し、未検証は未検証のまま記録する。
- README.md、docs/security.md、docs/tools.md、docs/manual-tests.md、docs/phase-1b-exp-progress.md を実態に合わせて更新する。必要な場合のみ AGENTS.md に追記する。

実装不能または実機検証不能の場合:

- 確認した方式・参照元・採用できない理由・必要な検証条件・次に進める条件を記録する。
- 未対応・未検証の機能を成功扱いしない。根拠がない API 呼び出し、実用不能なスタブ、既定有効化を追加しない。
- 調査結果と必要な安全な変更だけを独立レビュー可能な PR にまとめる。調査の完了と機能の完了を区別する。

最終報告には API 選定の根拠、実装した範囲、仕様との差分、回帰テスト、実機の確認結果、残存リスク、PR URL、公開可否の判断を含める。安全性の重大なブロッカーがある場合は報告し、Phase 1C 以降や自動マージには進まない。
