## 採用した上限値

指示書の初期案をそのまま採用した。個人用・少数クライアントでは、クライアント別 60 件/分が実際の上限になり、他の値には届かない。実利用での計測は未実施(P1/P2)。

| 項目 | 値 | 根拠 |
|---|---:|---|
| 認証前の全体要求予算 | 600 件/分 | クライアント別 60 件/分 × 10 |
| 認証前の接続元別予算 | 240 件/分 | プロキシの後ろの 4 クライアントが上限まで使える |
| 認証段階の同時実行数 | 8 | 認証は DB の 1 回の読み取り。ツールの同時実行数と同じ |
| 認証後のクライアント別予算 | 60 件/分 | 既存値 |
| 拒否の個別記録 | 接続元 30 件/分・全体 120 件/分 | 既存値(接続元)と初期案(全体) |
| 集約の期間 | 1 分 | 初期案 |
| 監査の記録数 / 論理保存量 | 100,000 件 / 64 MiB | 初期案。1件の論理サイズは約 250〜350 バイトなので、通常は件数が先に効く |
| 状態変更用の予約枠 | 1,000 件 / 6.4 MiB (10%) | 初期案。同時に進行し得る状態変更は最大 40 件(実行 8 + 待機 32) |
| HTTP 拒否記録の上限(追加) | 10,000 件 / 6.4 MiB | 未認証の洪水がツールの記録を押し出さないため(下記) |
| WAL の切り詰めサイズ | 4 MiB | `journal_size_limit`。下記の計測で必要と判断 |
| VACUUM の条件 | 空き 16 MiB 以上かつファイルの 1/4 以上 | 保守(6時間ごと)でのみ。要求ごとには行わない |

## 設計判断

### SEC-05

- **独自の小さな固定窓 (`RequestBudget`) を使い、ASP.NET の `PartitionedRateLimiter` をやめた。** 理由: (1) 拒否された要求が何も消費しない「接続元 → 全体」の順の判定と、キーの数の上限(通過した要求だけがキーを作るので窓あたり最大 = 全体予算)を同時に満たせる。(2) タイマーを持たないので SEC-11 のタイマー漏れが原理的に起きない(`HostLimiters` は不要になり削除)。(3) `TimeProvider` で決定的にテストできる。窓の切り替えは次の呼び出しで遅延して行い、前の窓のキーは全部捨てる。
- 順序: 要求予算 → 認証段階の同時実行数(待たずに 429)→ Host → Origin → 認証(読み取りのみ)→ クライアント別予算 → 最終利用日時。Host/Origin の拒否も予算の後なので、予算を迂回できない。
- `TokenAuthenticator.Authenticate` から `RecordClientUse` を外し、`RecordUse` に分けた。クライアント別予算を通過した要求だけが呼ぶ。保存済みの最終利用日時が 1 分以内なら DB に書かない(従来は UPDATE 文を毎回実行し、SQL の条件で書き込みを抑えていた)。最終利用日時の書き込み失敗はリクエストを失敗させない(情報表示用のため)。
- 接続元のキーはソケットのアドレスを正規化した文字列だけ。トークンやそのハッシュはキーにしない。
- 429 には可能な限り `Retry-After`(窓の残り秒数、同時実行数の超過は 1 秒)を付ける。認証失敗の記録予算を超えた 429 だけは、従来どおり付けない(要求自体は予算内のため)。

### SEC-06

- **使用量はトリガーで同期する `audit_usage` で管理**(マイグレーション v2)。書き込みのたびの `COUNT(*)` / `SUM` を避け、保持期間の削除・上限の削除・更新のどれでも整合する。テストで実テーブルとの一致を確認している。
- **上限に達したら古い記録から削除する(リングバッファ)。** 「新しい記録を捨てる」方式は、上限到達後に状態変更が全部止まる(認証済みの大量呼び出しで機能停止させられる)ため採らなかった。予約枠は「pending 以外は上限−予約枠まで」という形で実装し、通常の記録が予約枠を使うことはない。
- **HTTP の拒否記録に専用の上限を追加した**(指示書にない項目)。全体の上限だけでは、個別記録の予算 120 件/分の洪水が約 14 時間でツールの記録をすべて押し出せるため。拒否記録は拒否記録同士で入れ替わる。
- **集約のキーは理由コードだけ**(接続元を含めない)。キーの数が固定(約 10)になり、接続元を増やしても集約レコードが増えない。代償として集約記録から接続元は分からない(個別記録の範囲では分かる)。
- 集約の書き出しはタイマーではなく、1分経過後の次の要求とホスト停止時。キューを持たない。
- 異常終了で残った pending は、起動時(単一インスタンス、ツール実行前)に `unknown` / `INTERRUPTED` に変える。実行中の pending はどの削除の対象にもしない。
- 1回の書き込みで削除するのは最大 4,000 件(1,000 件 × 4 回)。それ以上必要な過大な DB(アップグレード直後など)は、起動時の保守 `EnforceLimits` が短いトランザクションの繰り返しで縮める。それが終わるまでの間に入りきらない記録は書き込み失敗になり、状態変更なら拒否される(fail-closed)。
- ログ画面: 保存量・上限・予約枠・削除件数と最終時刻・起動後の書き込み失敗件数・集約の説明を表示。「記録の種類」(すべて/個別/集約)で絞り込み、集約記録は結果欄に「×件数」、詳細欄に説明。CSV/JSON に `aggregate_count` 列を追加(数式注入対策はそのまま)。

### 物理サイズの計測(Infrastructure.Tests、上限 500 件 / 256 KiB)

| 段階 | 記録 | 論理 | DB ファイル | WAL |
|---|---:|---:|---:|---:|
| 3,000 件書き込み後 | 450 | 91,890 B | 188,416 B | 4,161,232 B |
| 長い読み取り中に 1,500 件 | 450 | 91,890 B | 188,416 B | 43,111,712 B |
| 読み取り終了後に 3,000 件 | 450 | 91,890 B | 188,416 B | 4,194,304 B |
| 保守 (`Maintain`) 後 | 450 | 91,890 B | 188,416 B | 0 B |

- DB ファイルは削除ページの再利用で増えない。WAL は長い読み取り中に上限なく伸びる(1,500 件で 43 MB)。`journal_size_limit` がないと読み取り終了後も 43 MB のままだったため、各接続で 4 MiB を設定した。
- 1 件の書き込みで約 7 ページ(28 KiB)が WAL に追記される。

## 仕様・指示書との差分

- HTTP 拒否記録の専用上限を追加(上記)。
- 集約のキーに接続元を含めない(上記)。
- ASP.NET の `RateLimiter` ミドルウェアを使わなくなった(クライアント別予算も `RequestGuards` 内)。
- 最終利用日時の書き込み失敗でリクエストを失敗させないようにした(従来は 500)。
- ディスクの空き容量そのものは監視しない。書けなければ fail-closed。

## 残存リスク

- リバースプロキシの後ろでは全クライアントが接続元予算を共有し、同じ経路の攻撃者が正規クライアントの取り分を使い切れる(security.md に調整方法)。
- IPv6 のアドレスを変えて接続元予算を分散できる(全体予算で上限)。
- 長時間の読み取りトランザクション(同じユーザーの他のプロセスが DB を開いたままにするなど)の間、WAL は上限なく伸びる。
- 容量上限でのリングバッファにより、認証済みクライアントの大量呼び出しは古いツールの記録を押し出せる(件数はログ画面に表示)。
- 書く前の集約カウンターは異常終了で失われる(最大 1 分ぶん)。
- 同一ユーザー権限のプロセスによる DB の改変(Phase 0 から変わらず)。
