# Sysacta — Phase 1B: オーディオ機能の拡張

## 目的と範囲

Phase 0 で実装した audio_get_state / audio_set_volume を基盤に、spec §7.1 のオーディオカテゴリを拡張する。Phase 1A の要求予算・監査容量制限も維持する。

通常機能の実装 (Phase 1B) と、非公開 API の可能性がある既定デバイス変更の技術検証 (Phase 1B-EXP) を分ける。まず通常機能を独立した PR として完成させる。Phase 1B-EXP は後述する別タスクであり、通常機能の完了を妨げない。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/phase-0-progress.md、docs/phase-1a-progress.md、docs/manual-tests.md を読み、現行コードとテストを確認する。

## 1. 作業方針

- 最新 main を基点とする専用ブランチ (例: phase-1b) で作業する。PR を作り、自動マージしない。
- 既存の Core / Windows / Infrastructure / Mcp / App の依存方向、ToolExecutor と SysactaTool<TArgs,TData> の共通経路を維持する。
- 既存の IAudioEndpoints、AudioTarget、CoreAudioEndpoints を優先して拡張する。セッションの責務を分ける必要があれば最小限のインターフェースを設ける。
- 現在採用している NAudio.Wasapi の実 API と公式 Core Audio の契約を確認する。存在しない API を推測で使わない。依存追加やバージョン変更は必要性と理由を記録する。
- 通常権限・ユーザーセッションで動作させる。外部 CLI、録音、プロセスへの注入、任意のアプリ実行、任意ファイル操作を追加しない。
- Phase 1C 以降の機能や管理 UI 全体の再設計には着手しない。
- 実装・ビルド・テスト・修正まで実施する。Windows 実機未確認の項目は未確認として残す。

## 2. ツール一覧

| ツール | 引数 | 種別 | DefaultPolicy | 範囲 |
|---|---|---|---|---|
| audio_list_devices | direction=all | 読み取り | On | 1B |
| audio_set_mute | enabled, device?, direction=output | 変更 | On | 1B |
| audio_list_sessions | device? | 読み取り | On | 1B |
| audio_set_app_volume | session_id, level | 変更 | On | 1B |
| audio_set_app_mute | session_id, enabled | 変更 | On | 1B |
| audio_set_default_device | device, direction, role | 変更 | Experimental | 1B-EXP |

既存環境へのアップグレードで追加されるツールは、DefaultPolicy.On でも全体許可は無効で追加し、既存クライアントには自動付与しない。新規 DB と新規クライアントの初期許可は現行ルールに従う。

引数・結果の詳細は下記を初期実装案とする。仕様 §7.1 と既存の JSON 契約を優先する。既存ツールの引数・結果を破壊的に変更しない。

## 3. デバイス列挙とミュート

### audio_list_devices

- direction は all / output / input。省略時 all。列挙用の all を既存の AudioDirection や変更操作の引数に無条件に追加しない。
- 入力・出力を列挙し、OS 由来の正規 ID、表示名、方向、状態、既定デバイス情報、登録済み別名、取得可能な操作を返す。既定情報は既存の Multimedia 役割との互換性を維持し、可能なら console / multimedia / communications の役割を区別する。
- Active / Disabled / Unplugged / NotPresent を区別する。非 Active デバイスでは音量・ミュートを null とし、存在しない値を捏造しない。
- デバイスがないときは空一覧。個別項目の API エラーと、列挙全体の失敗を区別する。一時的な列挙失敗で利用可否を恒常非対応に変更しない。
- 取得対象、返却件数、応答サイズを合理的に制限し、切り詰めが起きた場合は明示する。

### audio_set_mute

- enabled は必須の bool (true=ミュート、false=解除)。トグル操作ではない。
- device は ID または別名、省略時は指定方向の Multimedia 既定デバイス。direction は output / input。all 指定は禁止する。
- 既存の AudioTarget.Resolve と正規 ID の audio:device ロックを再利用する。既定対象のロックも既存ルールと揃える。
- 変更前の値を読み、既に一致していれば Changed=false で verified。違う場合は最終認可の開始点を宣言してから変更し、読み戻して検証する。
- 結果は対象デバイス、変更前後のミュート状態、changed を含める。音量を変更しない。
- 読み戻しで不一致なら VERIFICATION_FAILED、変更後に状態が不明になったなら status=unknown。切断・不存在は適切なエラーに変換する。

## 4. アプリ別音声セッション

### audio_list_sessions

- device は出力デバイスの ID または別名、省略時は Multimedia 既定出力。指定した機器が見つからなければ別の機器へフォールバックしない。
- Core Audio のセッション列挙 API を使う。マイクのキャプチャセッションや音声データ取得は対象外とする。
- 返却項目の案: session_id、device_id、表示名、取得可能な PID、セッション状態、音量 (0〜100)、ミュート、システム音セッションかどうか、対応操作。取得不能な任意項目は null 等で明示する。
- プロセスのコマンドライン、環境変数、実行ファイルの完全パス、不要なウィンドウ内容は返さない。プロセス名が取れないシステム音や終了済みプロセスも安全に扱う。
- session_id はセッションの実体を一意に識別する。Core Audio のセッションインスタンス ID と正規エンドポイント ID を利用する方式を優先する。PID、プロセス名、セッション表示名、列挙順だけを ID にしない。
- ID にパス等が含まれ得る場合は、生の OS 識別子を公開・監査するのでなく、衝突耐性のある不透明な識別子を決定的に生成し、実体の再照合で解決する。無制限の ID キャッシュは作らない。
- 同じアプリの複数セッションは別々に列挙する。Inactive / Expired 等を適切に区別し、操作可能性を明示する。空一覧と API 障害は区別する。
- session_id の有効期間（セッション終了・再生成・機器変更等で変わり得る）をツールの説明と文書に記載する。

### audio_set_app_volume / audio_set_app_mute

- session_id は必須。未知・古い・曖昧な ID は拒否する。プロセス名や PID による自動推測、一括変更、別セッションへのフォールバックは禁止する。
- level は必須の整数 0〜100。enabled は必須の bool。
- session_id から実際のエンドポイントとセッションインスタンスを特定し、正規のセッション単位のロックを得る。音量変更とミュート変更で同一セッションのロックを共有し、読み戻しまで保持する。
- 解決と実行の間にセッションが終了・再生成されることを想定する。ロック取得後も同じ実体を再確認し、置き換わったセッションに書き込まない。
- 既に目標値であれば no-op とする。それ以外は、変更前の読み取り・対象検証を済ませ、execution.BeginSideEffect() を最初の書き込みの直前に呼んでから実行する。
- 音量変更はセッションのマスター音量だけ、ミュート変更はセッションのミュートだけを対象にする。デバイス全体の音量やミュート、他のセッションには変更を加えない。
- 結果は対象の session_id、device_id、変更前後の値、changed を含める。読み戻しできないときは accepted / unknown / error を既存契約に従って区別する。書き込み後のセッション消失を未実行として扱わない。

## 5. 共通実行基盤・セキュリティ

- 全ツールを ToolCatalog に登録し、MCP もローカルの動作確認も ToolExecutor 経由とする。個別ハンドラーや認証例外を作らない。
- 状態変更ツールは ReadOnly=false。開始点の宣言は必須であり、読み取り専用ツールは OS への書き込みをしない。
- 共通の pending 監査、再認可、AuthorizationGate、タイムアウト、実行中のロック保持、監査容量の予約枠を利用する。監査不能なら副作用を拒否する。
- 監査の文字列型引数は禁止。AuditedArguments は level / enabled / direction 等の安全な型のみ。target は OS またはローカル登録情報から解決された安全な識別子だけとし、生の device / session_id / 表示名を無条件に記録しない。
- OS に渡す文字列には既存の長さ制限・NoControlCharacters を適用する。明示 null、未知引数、不正 enum、型変換、範囲外は拒否する。
- 状態変更前後の例外処理は区別する。生の COM 例外やパスを応答・ログに出さない。
- COM オブジェクトは適切なアパートメントで生成・利用・解放する。セッションマネージャー・列挙コレクション・個別セッション等も所有関係を確認し、途中失敗でも解放する。UI スレッドへの同期 OS 呼び出しを避ける。
- 既定デバイス変更の将来実装を想定し、既定指定操作は方向・役割に対応するロックを共有する方針を維持する。対象を別の機器へ暗黙に切り替えない。
- docs/tools.md のサンプルコードが現在の ToolExecution / Phase 1A の実行経路と一致しない場合は、説明の範囲で修正する。

## 6. デバイス管理画面（オーディオ）

spec §4 / §8 に従い、実装済みのオーディオデバイスの管理画面を追加する。後続カテゴリも追加できる単純な構成にする。

- ID・名称・方向・状態・既定・対応操作・登録済み別名を表示し、再読み込みできる。
- ローカル UI から別名を登録・変更・削除できる。既存 AccessStore の device_aliases を再利用する。
- 別名はカテゴリ内で一意、予約語、制御文字、既知 ID との衝突を拒否する。大小文字の扱いは DB と解決で統一する。
- 切断中の登録機器や ID が変化した機器も把握できるようにし、別機器へ再紐付けする場合は利用者が明示的に選ぶ。曖昧な自動再紐付けは行わない。
- 別名の設定変更を MCP に公開しない。ローカル表示と MCP 列挙結果の整合性を確認する。
- 既存の WPF UI、テーマ、DPI、非同期 UI、空状態とエラー表示に従う。Windows 設定アプリの代替となる音量ミキサー画面や録音画面は作らない。

## 7. テスト要件

### Core / Infrastructure

- 列挙の方向・空一覧・切断状態・既定役割・別名・一部取得失敗。
- ミュート・アプリ別音量・アプリ別ミュートの成功、no-op、不正引数、範囲外、別方向、対象なし、セッション消失、OS エラー、読み戻し不一致、書き込み後の結果不明。
- 同一名・同一 PID の複数セッション、セッション再生成、別エンドポイントの同じセッション識別表現を区別する。
- 同じ正規デバイス・セッションに対する変更がロックを共有し、異なる対象は並列化できる。
- 各変更ツールで BeginSideEffect の直前に失効・再発行・権限剥奪・期限切れが確定した場合、フェイク OS の書き込みがゼロであること。
- 監査の予約枠不足、タイムアウト・キャンセル、書き込み前後の状態が既存契約に従う。
- デバイス別名の一意性・衝突・削除・再紐付け。マイグレーションが必要なら既存データ保持を確認する。

### MCP 統合

- 新規ツールの厳格なスキーマ、構造化結果、直接呼び出し時の権限拒否。
- 新規 DB と既存 DB での許可の違い、既存トークンへの権限自動付与がないこと。
- 認可・監査を迂回しないこと、未許可時に OS 側副作用がないこと。
- 合成機密文字列が DB/WAL/CSV/JSON に保存されないこと。監査の保存量上限と認証前予算の既存テストを維持する。

### Windows / App

- Core Audio の実デバイス列挙、出力・入力の状態取得、音声セッション列挙、管理画面の XAML・別名操作を確認する。
- 状態変更の実機試験は SYSACTA_HARDWARE_TESTS=1 の場合だけ実行し、対象を明示し、元の状態を finally 等で復元する。通信・会議中などの実デバイスを勝手に変更しない。
- 実機に検証用セッションがない場合はスキップし、理由を記録する。テスト専用の音声セッションを作る場合も録音・外部通信を行わず、終了と状態復元を保証する。
- 最新の CI でビルド・テスト・アプリスモークテストを確認する。docs/manual-tests.md に手動確認項目を追加する。

## 8. Phase 1B-EXP — 既定デバイス変更（別タスク）

通常機能の PR 完了後に上位モデルで実現性調査・実装を行う。通常機能の作業中は、必要な設計上の注意事項を記録するだけでよい。

- 公式 API の有無と対応 Windows バージョンを確認する。非公開 API が必要なら既存 OSS の実績、API 契約、ライセンス、互換性、失敗時の挙動を調査する。検証可能な根拠がない方式を採用しない。
- 引数: device 必須、direction=input/output、role=console/multimedia/communications/all。role の all は対象方向の役割すべてであり、複数デバイスへの一括操作ではない。
- 非公開 API は Sysacta.Windows/Experimental に隔離し、DefaultPolicy.Experimental、初期無効、UI の注意表示、能力判定を維持する。未対応環境では tools/list から隠す。
- 既定デバイス変更と既定対象の操作で共有ロックを設計し、役割 all は固定順序で複数ロックを取る。ロック後の状態確認と対象の一貫性を検証する。
- 役割ごとに結果を読み戻し、部分成功・失敗・結果不明を明示する。失敗時に無断で別デバイスを選んだり、無条件で再試行・ロールバックしたりしない。
- DLL 注入、カーネル改変、セキュリティ機構の回避、権限昇格、外部 CLI は禁止。
- 実機で検証できなければ未検証、実現不能なら未対応として記録する。成功を偽装するスタブは作らない。
- 既定デバイス変更は別 PR、別完了判定とする。上位モデルに渡す追加指示は調査結果に応じて整備する。

## 9. 完了条件・成果物

Phase 1B（通常機能）の完了条件:

- デバイス管理画面で列挙・別名管理が可能である。
- 各状態変更ツールの開始点、排他、読み戻し、監査、失効時の副作用ゼロが検証されている。
- dotnet build Sysacta.sln -c Release が警告・エラーゼロ、dotnet test Sysacta.sln -c Release と Windows CI が成功する。
- docs/phase-1b-progress.md に実装したツールと JSON 契約、判断理由、検証結果、既知の制約、未確認の実機項目、Experimental の残タスクを記録する。
- docs/tools.md、docs/manual-tests.md、README.md を実態に合わせて更新し、必要な場合のみ AGENTS.md にルールを追記する。
- 独立レビュー可能な PR を作成する。Phase 1B-EXP や Phase 1C に着手せず、自動マージしない。

最終報告には実装内容、仕様との差分、テスト結果、未確認事項、残存リスク、PR URL を含める。Phase 1B-EXP を通常機能と混同して完了扱いしない。
