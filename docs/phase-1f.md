# Sysacta — Phase 1F: システム監視

## 目的と範囲

spec §7.5 / §9 / §10 に従い、Windows 11 の CPU/GPU 使用率、メモリ、稼働時間、OS・ハードウェア情報、温度、ストレージ容量を読み取り専用の MCP ツールとして追加する。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/manual-tests.md、docs/phase-1d-progress.md、docs/phase-1e-progress.md と現行コード・テストを読む。最新 main を基点とする専用ブランチ（例: phase-1f）で作業し、独立した PR を作成する。自動マージしない。

既存の認可・監査・要求予算・タイムアウト・実行スロット・電源遷移ゲートを維持する。Phase 1G 以降、プロセス単位の監視、過去フェーズの残課題、永続的な監視履歴、ダッシュボード、警告通知、ファイル管理は今回の対象外。

## 1. 技術調査と安全境界

実装前に Microsoft の公式文書、Windows SDK、.NET 10 の契約、通常権限の非パッケージ WPF アプリでの利用可否を確認し、採否・参照 URL・依存関係・ライセンス・対応環境・制約を docs/phase-1f-progress.md に記録する。

| 用途 | 調査候補 |
|---|---|
| CPU 使用率 | GetSystemTimes、PDH の全 CPU カウンター |
| GPU 使用率 | PDH / Windows GPU Engine カウンター、必要に応じ DXGI によるアダプター照合 |
| メモリ | GlobalMemoryStatusEx |
| 稼働時間 | GetTickCount64 |
| OS、CPU、RAM、GPU 等の構成 | System.Diagnostics / System.Environment、Win32、限定的 WMI、DXGI |
| 温度 | 公開の Windows API、既存 GPU ドライバの公式読み取り API、LibreHardwareMonitor（採否調査のみから開始） |
| ストレージ | DriveInfo / GetDriveType / GetDiskFreeSpaceEx 等 |

- Windows 固有処理は Sysacta.Windows/SystemMonitoring 等へ隔離し、Core には OS 非依存の型とインターフェースだけを置く。既存の System.Management 等を必要に応じ再利用し、新規依存は最小限にする。名前空間の System との衝突に注意する。
- 通常ユーザー権限、ログオン中の Windows 11、win-x64 自立型配布が前提。追加 SDK やネイティブ DLL が必要なら、配布条件・読み込み先・署名/由来・ABI・動作条件を記録する。DLL 検索パスを安全に限定し、作業ディレクトリ等から任意 DLL を読み込まない。
- 外部 CLI、PowerShell、wmic、任意 WMI クエリ、任意のパフォーマンスカウンター、任意ファイル・レジストリの読み取りを MCP に公開しない。クエリ・カウンター・フィールドは実装で固定する。
- 計測のための負荷生成、プロセス起動/停止、GPU 設定変更、ファン制御、ストレージへの書き込み、サービス起動、権限昇格、ドライバ導入・更新・ロード、OS のセキュリティ設定変更を行わない。
- LibreHardwareMonitor は候補であり、必須依存ではない。採用前に固定バージョンのコードと依存を確認し、初期化・Open/Update/Close 等がドライバ、サービス、デバイス設定、ファン制御等の副作用を起こさないこと、必要権限とライセンスを確認する。WinRing0/PawnIO 等を同梱・導入・起動する経路は今回作らない。安全に分離できない場合は不採用とし、温度の取得不能を正しく返す。
- 既に導入されているベンダーの公式 API が通常権限で読み取り可能な場合は候補とする。NVIDIA/AMD/Intel 等の未導入環境にインストールを強制しない。汎用メモリ/IO ポート/MSR/PCI アクセスや未検証の非公開インターフェースを追加しない。

## 2. 公開ツール

| ツール | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| system_get_status | なし | 読み取り | On |
| system_get_hardware | なし | 読み取り | On |
| system_get_temperatures | なし | 読み取り | On |
| system_get_storage | なし | 読み取り | On |

- 全ツールを ReadOnly: true とする。ただし読み取りという宣言で副作用のある初期化を許容しない。Phase 1E の PowerTransitionGate が読み取りを許可する設計を壊さない。
- 新規 DB の既定は spec の表どおり On。既存 DB への追加は 4 ツールすべて無効、既存クライアントへの自動付与なし。共通の認可、失効、無効ツールの非公開・直接呼び出し拒否を維持する。
- 既存の SysactaTool<TArgs,TData>、厳格な空引数スキーマ、additionalProperties: false、outputSchema、ToolCatalog 登録を使用する。追加の filter、path、device_id、sampling_ms 等の引数は公開しない。
- 通常のツールタイムアウトは 5 秒を初期案とする。OS 取得の実測により調整する場合は根拠・影響を記録する。全体の予算内で取得不能な項目は欠損として扱う。
- GetAvailability は安価・副作用なし。センサーがない、GPU が非対応、WMI の一時失敗等を理由にツール全体を恒常的に非公開にしない。

## 3. 共通のデータ契約

- すべての結果に測定/取得時刻（UTC、ISO 8601）を含める。必要に応じサンプリング開始・終了、実測 sampling_ms、項目別時刻、取得元と測定方法を記録する。異なる時刻の観測を一つの原子的なスナップショットと説明しない。
- サイズは原則 bytes、利用率は percent（0〜100）、温度は °C、時間は seconds または ms をフィールド名/description で明示する。整数と浮動小数点の範囲・変換・オーバーフローを検証する。
- 取得不能は null と型付きの理由を返す（例: not_supported、permission_denied、unavailable、invalid_data、timeout）。不明を 0、空文字、架空のセンサー値で埋めない。0 と null を明確に区別する。NaN / Infinity / 無効な負値等を JSON に出さない。
- 項目や機器単位の失敗を区別し、利用可能な情報は返す。全体の取得が失敗した場合は構造化エラー。正常に取得した結果として対象が存在しない場合は空一覧で表現する。能力がない/取得できない場合は理由付きで説明し、正常な空一覧と混同しない。
- 欠損を含む読み取り成功は success / not_applicable とし、各項目の欠損・失敗・切り詰めを型付きデータで明示する。状態変更の partial を読み取り欠損の代用にしない。既存の結果契約に従う。
- 全一覧の件数・文字列長・ネイティブバッファを制限し、total_count / failed_count / truncated 等を必要に応じ返す。初期案は一般的な機器一覧 64 件、内部探索 256 件。GPU Engine カウンター等は用途に応じ別の有限上限を設け、超過時に集計を正確な全体値と見なさない。
- 機器名・OS 由来文字列は信頼できないデータとして長さ制限、制御文字除去、パス・URI 等の除外を行う。デバイスの対応付けが曖昧なら unknown とし、名前や列挙順で別機器と結び付けない。

## 4. system_get_status — 現在の利用状況

### CPU

- システム全体の CPU 使用率、論理プロセッサ数等を取得する。瞬間的な未初期化カウンターを使用率として返さない。
- GetSystemTimes を使う場合は 2 点の差分を用い、kernel に idle が含まれる契約を考慮する。単調時刻で実測間隔を測る。差分の逆転、分母ゼロ、スリープ等の異常な間隔を検出する。
- 初期サンプリング時間は 500〜1000ms 程度。複数リクエストで同じ観測を共有する方式は必要性があれば採用してよいが、古いサンプルを現在値と偽らない。
- GetSystemTimes は 64 論理プロセッサ超で呼び出し側のプロセッサグループに限定され得る（[公式契約](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes)）。全グループを扱える方法を選ぶか、測定範囲を明示して全体値を null にする。周波数補正された Processor Utility と単純な Processor Time を混同しない。
- 既存の Windows 設定・タスクマネージャーと測定間隔/方法が異なる場合は差異を説明する。完全一致を成功条件にしない。

### RAM と稼働時間

- OS が利用可能と報告する物理メモリ総量、available、used（total - available）、使用率を取得する。コミット、ページファイル、実装 RAM 容量とは別概念。
- 予約済みメモリやキャッシュのため他ツールの表示と異なり得る。値の関係を検証し、差分が不正な場合は欠損として扱う。
- uptime は OS 起動後の経過時間（スリープ・休止状態を含むかは採用 API 契約に従い明示）。アプリ自身の起動時間や壁時計差分で代替しない。Fast Startup 等の影響も記録する。

### GPU（重要）

- 複数 GPU を区別し、可能なら物理/論理アダプターごとの利用率と取得方法を返す。OS のアダプター識別子（LUID 等）を内部照合に使用し、必要な範囲で安全な識別子を結果に返す。再起動後も同じ ID であると保証しない。
- PDH / GPU Engine カウンターを使う場合、英語カウンターの利用方法またはローカライズに依存しない取得を調査する。カウンター初期化、複数時点の収集、CStatus、終了したインスタンス、カウンター追加/消失を扱う。
- 同一物理エンジンに属するプロセス別インスタンスを重複計上しない。物理エンジンの単位に正しく集計し、異なるエンジンのパーセントを単純加算しない。GPU 全体の代表値はタスクマネージャーと同様、最も利用されているエンジンの値を使う方式を初期案とする（[Microsoft の説明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)）。
- 集計方法・エンジンの識別が検証できない場合は、検証可能な個別値だけを返すか全体値を null とする。不正な総和を 100 に丸めて正しい計測と見なさない。
- 専用 VRAM 使用量/容量、共有 GPU メモリは別概念。信頼できるシステム全体値が取得できる場合のみ追加する。DXGI のプロセス別メモリ予算/利用量を GPU 全体の VRAM 使用量と見なさない。
- ソフトウェアアダプター、iGPU、dGPU、複数 GPU、ドライバの非対応を考慮する。利用率ゼロは有効な測定結果である場合だけ返す。
- GPU Engine カウンターに含まれる PID 等は内部集計に限定し、プロセス単位の一覧は返さない。

## 5. system_get_hardware — 構成情報

- Windows の製品名/バージョン/ビルド・アーキテクチャ、CPU のモデル名・物理コア/論理プロセッサ数、RAM 総容量、GPU のモデル名・取得可能な専用メモリ容量、必要な場合に機器の種類等を返す。
- 物理 RAM の搭載容量と OS 利用可能容量は区別する。物理コア数を論理プロセッサ数から推定しない。GPU のメモリ容量を WMI の 32-bit AdapterRAM のみから大容量 GPU の正しい容量として断定しない。
- CPU/GPU が複数ある場合は個別に列挙する。GPU の識別方法は status/temperatures と整合させ、照合不能な値は別の機器へ割り当てない。
- マザーボードのメーカー/モデルや RAM の速度等は公式情報で取得できる必要最小限の範囲に限定する。PCI/USB 全デバイス、インストール済みアプリ一覧、全ドライバ列挙は対象外。
- WMI を使用する場合は必要クラス・プロパティのみ取得し、SELECT * や広範な探索を避ける。接続先はローカルの固定 namespace のみ。COM オブジェクト等を適切に解放する。
- Windows の製品キー、シリアル番号、MachineGuid、SMBIOS UUID、ユーザー名、コンピューター名、ドメイン、SID、MAC、デバイスインスタンスパス、個人ファイル情報を取得・返却・監査しない。

## 6. system_get_temperatures — 安全な温度取得

- センサーごとに sensor_id（安全に識別可能な範囲）、device_id（照合可能なら）、device_type、sensor_type、label、temperature_c、取得元、取得時刻、欠損理由等を返す。機器とセンサーの種類を明確に区別する。
- CPU package、CPU core、GPU core、GPU hotspot、GPU memory junction、ストレージ、ACPI thermal zone は別の観測値であり、相互に置き換えない。ACPI ゾーンを根拠なく CPU 温度として扱わない。センサーの値・単位を公式契約で確認する。
- CPU package 等のセンサーが通常権限の標準 API で取得できない環境では、null と理由を返す。値を推定したり、固定値、稼働率から換算した温度を返さない。
- GPU 温度等は既存の公式ベンダー API から取得可能なら優先する。ベンダー非対応、DLL 不在、初期化失敗、センサー非対応を区別する。ベンダー API のファン・クロック・電力制限等の変更機能は使わない。
- ドライバを必要とする LibreHardwareMonitor の機能をツール内部から自動で利用可能にしない。安全な読み取り専用経路が立証できない場合は採用を見送る。既存権限/ドライバを利用する案でも副作用・ライセンス・安全性を個別検討する。
- 温度の無効値（センサー独自の sentinel、単位不明、非有限値等）を除外する。一般的な想定値域だけで実測値を捏造・補正しない。
- 全センサーが取得できない環境でも、取得能力の診断結果として意味のある理由付き応答を返す。取得不能を実装済みの温度計測と報告しない。少なくとも GPU 等の安全な取得経路を調査し、採否・未対応範囲を明記する。

## 7. system_get_storage — ローカル容量

- ローカルのドライブ/ボリュームについて、安全な volume_id、ドライブ文字等の識別ラベル、種類、total_bytes、free_bytes、available_bytes、used_bytes、usage_percent、欠損理由を返す。物理ディスク容量ではなく論理ボリューム容量であることを明記する。
- 初期範囲はドライブ文字を持つローカル固定ディスク。リムーバブル、光学、ネットワークドライブ、UNC、接続が不明な媒体、フォルダーにマウントされたパスは今回対象外。ドライブ種別確認の前にネットワークドライブへアクセスしない。
- ドライブ文字は論理ボリュームの選択用ラベルであり、物理ディスクの永続 ID ではない。ボリュームのシリアル、GUID パス、マウント先フォルダー、ボリュームラベル等の個人情報は返さない。
- ファイル・ディレクトリの列挙、サイズ集計、ディスクの生読み取り、SMART 詳細、ファイルシステム検査、空き容量確保処理は行わない。
- 全体空き容量と現在ユーザーが利用可能な容量はクォータ等で異なる。API が返す total/free/available の意味を確認し、同じ基準の値のみで使用率を算出する。区別できなければ該当値を null にする。
- 未準備・取り外し・容量取得失敗は個別の理由を返し、他ドライブの読み取りを継続する。容量ゼロで割らない。複数パーティション、仮想ディスク、ストレージプール等の容量を重複加算した「PC の物理ストレージ総容量」は返さない。

## 8. 実行制御・プライバシー

- CPU/GPU の計測は要求時に有限時間で行うのを初期方針とし、常時ポーリング、永続キャッシュ、履歴 DB は追加しない。共有サンプラーを採用する場合は期限・同時実行数・キャンセル・リソース寿命を明記する。
- WMI、PDH、GPU DLL 等のブロッキング処理は UI スレッド外で実行する。共有プロバイダーのスレッド安全性を確認し、必要な範囲だけを直列化する。独立した取得処理を不用意に全体直列化しない。
- ネイティブ処理がキャンセル不能な場合、待機の打ち切りを実処理の完了と見なさない。既存 ToolExecutor のスロット隔離を利用し、終了までプロバイダー参照・必要な内部ゲートを保持する。タイムアウトするたびに新規バックグラウンド処理を無制限に生成しない。
- 内部リトライは読み取りに限り少数・有限。キャンセル後に追加の収集を始めない。ハングしたプロバイダーを並行再初期化しない。サーバー停止/再開、スリープ/復帰、アプリ終了時にハンドルと購読を安全に解放する。
- PowerTransitionGate に対する読み取りの扱いを変えない。電源遷移中の測定欠損は欠損として返し、スリープ前後をまたぐ不正な CPU/GPU サンプルを有効扱いしない。
- 認可済みの結果に限って OS/機器の情報を返す。監査に結果本文、ハードウェア名、ドライブ名、WMI 出力、内部識別子、例外全文を残さない。既存の監査容量・要求予算を維持する。
- 既存のツール/クライアント/ログ UI への統合で十分とする。新しい常時更新画面やバックグラウンド監視、HTTP エンドポイント、メトリクス配信は作らない。

## 9. テスト要件

### Core / MCP / Infrastructure

- 4 ツールの厳格な空引数スキーマ、outputSchema、ReadOnly、On、既存 DB で無効、既存クライアントへの自動付与なし、未許可/無効の直接呼び出し拒否。
- CPU 差分計算、kernel/idle、ゼロ分母、逆転、異常なサンプル期間、64 論理プロセッサ超の測定範囲、RAM の整合、時刻・単位・巨大整数の変換。
- GPU の複数アダプター/エンジン/プロセスインスタンス、重複、消失、カウンター無効、上限超過、集計不能、真の 0 と欠損を区別する。誤った集計で 100% を超えたり強制クランプして成功しない。
- CPU/GPU/センサーの識別不能、同名機器、温度単位、無効値、ドライバや権限の不足、部分的な温度取得、全取得不能。
- ローカル固定ドライブのみを選択し、ネットワーク/UNC 等を容量取得前に除外すること。クォータ、容量ゼロ、取り外し、権限不足、取得失敗を検証する。
- 全ツールで部分取得・欠損理由・時刻・truncated・型/単位、非有限値の除外、読み取り結果と監査の区別を検証する。秘密・パス・シリアル等の合成データが応答/監査/ログに出ないこと。
- 同時要求の上限、計測中キャンセル、初期化ハング、タイムアウト後も実処理完了までスロットやゲート保持、共有サンプラー採用時の鮮度・再利用・競合。
- 電源遷移中に読み取りが既存方針どおり扱われること、読み取りから副作用が始まらないこと、過去フェーズの認可/監査/電源ゲート等の回帰テストを維持する。

### Windows / App / 実機

- Windows CI は読み取り専用 API、データ変換、フェイク、Release ビルド、アプリのスモークテストを確認する。特定 GPU/センサーが存在しない場合は欠損を確認し、実機計測成功と混同しない。
- Windows 実機の通常権限で、OS/CPU/RAM/GPU 構成、CPU/GPU 使用率、ストレージ容量、取得可能な温度を確認する。タスクマネージャー・Windows 設定・既存のモニタリングツール等の同時期の値と、測定方式の差を踏まえて比較する。
- 16GB 超の GPU 等も含め VRAM 容量の桁落ちがないことを確認する。複数 GPU や GPU センサー、温度取得、異なるドライブ等は実機で確認できる範囲を記録する。確認環境がない場合は未検証とする。
- 計測のために負荷テスト、実ゲーム起動、特権ドライバ導入、設定変更、スリープ等を自動実行しない。既に稼働している処理を読み取るか、利用者が自分で操作した状態で観測する。
- 実際の MCP クライアントから 4 ツールの許可・取得結果・欠損・監査の確認手順を docs/manual-tests.md に追加する。管理 UI のカテゴリ、ツール/クライアント許可、動作確認も既存方式で確認する。
