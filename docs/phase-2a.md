# Sysacta — Phase 2A: アプリ・プロセス管理

## 目的・範囲

spec §7.6 / §8 / §9 / §10 / §11 に従い、ローカル管理画面でのアプリ検出・登録・許可リスト管理、登録済みアプリの起動・通常終了、プロセス一覧・限定的な強制終了を追加する。

最初に README.md、AGENTS.md、docs/spec.md、docs/tools.md、docs/security.md、docs/manual-tests.md、docs/phase-0-progress.md、docs/phase-1a-progress.md、docs/phase-1e-progress.md、docs/phase-1f-progress.md、docs/phase-1g-progress.md と現行コード・テストを読む。最新 main を基点とする専用ブランチ（例: phase-2a）で作業する。

今回の主なリスクは、登録アプリ機能が任意コマンド実行の入口になること、権限剥奪と起動の競合、PID 再利用やアプリ識別の曖昧さによる誤終了である。安全性を保証できない操作は未対応として扱い、便利さのために境界を緩めない。

実装は (A) 登録・検出・起動と一覧、(B) 通常終了・プロセス一覧・強制終了の順で進める。独立したコミット・テストでレビュー可能にする。必要なら PR を分けてよいが、Phase 2B 以降には着手せず、自動マージしない。

対象外: 任意シェル・ファイルパス・コマンド・引数・URL・URI・環境変数の MCP 指定、GUI 自動化、任意アプリのインストール、サービス管理、プロセスツリーの一括終了、OS/セキュリティ設定変更、Phase 1 の残課題、配布全体の整備。

## 1. 技術調査

実装前に Microsoft 公式文書、Windows SDK、.NET 10 の契約、通常権限の非パッケージ WPF アプリでの利用可否を確認し、採否・参照 URL・依存/ライセンス・制約を docs/phase-2a-progress.md に記録する。

| 用途 | 調査候補 |
|---|---|
| 候補アプリ検出 | ユーザー/共通 Start Menu の既知フォルダー、IShellLinkW / IPersistFile の読み取り、必要なら公式のパッケージアプリ列挙 |
| 実行ファイル検証 | CreateFileW、GetFinalPathNameByHandleW、GetFileInformationByHandleEx、PE ヘッダー、ファイルハッシュ、必要に応じ WinVerifyTrust |
| 起動 | CreateProcessW（lpApplicationName を明示）、または同等の安全性を実証できる ProcessStartInfo（UseShellExecute=false） |
| プロセス情報 | System.Diagnostics、OpenProcess、GetProcessTimes、QueryFullProcessImageNameW、ProcessIdToSessionId、プロセストークンの読み取り |
| 保護判定 | IsProcessCritical、GetProcessInformation 等の保護レベル、ユーザー SID・セッション・IntegrityLevel・昇格情報 |
| 通常終了 | EnumWindows、GetWindowThreadProcessId、限定した WM_CLOSE / CloseMainWindow の契約 |
| 強制終了・確認 | TerminateProcess（特定プロセスハンドル）、WaitForSingleObject / GetExitCodeProcess |

- Windows 固有処理は Sysacta.Windows/Apps 等に隔離する。Core は OS 非依存、Infrastructure は DB、App は構成ルートと WPF UI。新規依存を最小限にし、既存 TFM・通常権限・win-x64 自己完結配布・WSL ビルドを維持する。
- COM/WinRT のアパートメント、P/Invoke 型・ハンドルの所有/解放、読み取り権限、キャンセル不能な呼び出しを検証する。System32 の DLL 等の安全な読み込みを維持する。
- UWP/MSIX は公式のアプリ ID による安全な列挙/起動が可能か調査する。初期実装は Win32 の明示的に登録した exe を優先する。パッケージアプリの起動権限・固定引数・同一性・終了対象を保証できないなら、検出のみまたは未対応として明示する。Explorer、shell:AppsFolder、explorer.exe の引数、URI、ShellExecute などを汎用フォールバックにしない。

## 2. ツール契約

| Tool | 引数 | 種別 | DefaultPolicy |
|---|---|---|---|
| app_list_available | なし | 読み取り | On |
| app_list_running | なし | 読み取り | On |
| app_launch | app_id | 状態変更 | On |
| app_close | app_id | 状態変更 | Off |
| process_list_running | limit?, filter? | 読み取り | On |
| process_terminate | pid, start_time | 状態変更 | Off |

- SysactaTool<TArgs,TData>、厳格な JSON Schema/outputSchema、ToolCatalog に登録。全体・クライアント別許可に加え、アプリの登録と allowed を状態変更の独立した必須条件とする。新規 DB は表のとおり、既存 DB の追加ツールはすべて無効・既存クライアントへの自動付与なし。
- app_id は登録時に生成する不透明で永続的な ID（例: app_ + UUID）。名前・パス・PID・AUMID・エイリアス・all/default による代替解決は禁止する。削除した ID を別アプリへ再利用しない。
- pid は正の整数（Windows の有効範囲を確認）、start_time は一覧から返したプロセス生成時刻の正確な表現をそのまま要求する（例: UTC ISO 8601 の固定書式・100ns 精度）。丸めやタイムゾーン曖昧性を排除し、Windows の FILETIME と損失なく照合する。PID 単独・名前・開始時刻の近似一致は不可。
- process_list_running の limit は初期案 100、1〜256。filter は任意の短い文字列（例: 1〜64 文字）で、公開するプロセス名に対する大文字小文字を区別しない部分一致のみ。正規表現・glob・WMI/SQL・コマンド・パス探索に使わない。
- 明示 null、未知引数、型不正、空/予約語、過長文字列、制御文字、不正な時刻書式は拒否する。説明・エラーは英語、UI は日本語。
- 既定タイムアウト 5 秒を初期値とする。ファイル検証・列挙・終了の確認を含めて有限とし、必要な変更は実測と根拠を記録する。終了確認の待機は少数・有限、無期限にアプリ終了を待たない。

## 3. 許可リストとローカル管理 UI

### 保存モデル

既存 DB の registered_apps (id, display_name, launch_target, fixed_args, allowed) を利用する。必要な列（種別、承認済み実行対象の識別情報・ハッシュ、設定世代等）は SysactaDatabase.Migrations に追記する。出荷済みのマイグレーションを変更しない。

- Core に読み取り専用登録ストア契約を設け、書き込みは App/Infrastructure のローカル管理経路のみ。MCP 層には管理用の書き込みインターフェース・エンドポイント・ツールを渡さない。
- 新規登録・自動検出された候補は未許可が既定。候補の検出だけで DB に登録/許可しない。明示的なローカル登録・安全性確認・許可を必要とする。
- 登録 ID と実行対象は固定。別アプリへの差し替えは新規 ID として登録する。固定引数・実行ファイルの更新を承認する場合は同一対象の再確認と明示承認、世代変更を必要とする。対象・引数の変更時は許可を自動継承しない。無効化/削除は即座に反映する。
- 実行ファイルの同一性に基づき、同じ exe を複数 ID に登録してロックや許可を分割できないようにする。ハードリンク・別表記などの照合限界を記録する。既存の不明な形式の登録行・破損行は自動で有効化しない。
- 固定引数は構造化した文字列配列として保存し、上限（初期案 16 個、各 256 UTF-16 コード単位、全体 2048 程度）と無効な文字を検証する。単一の任意コマンドラインを登録・解釈する方式は採らない。既存 fixed_args の解釈が不明なら再登録/明示承認を要する。

### 検出・手動登録

- 自動検出は管理画面の明示操作で、固定のローカル Start Menu 既知フォルダーを対象にする。ショートカットは読み取りのみ。Resolve によるリンク追跡、ネットワーク接続、起動、スクリプト実行、ShellExecute は行わない。
- 深さ・探索件数・文字列長・処理時間を制限する（初期案: 深さ 8、探索 2048、表示 256 件）。再解析ポイントを辿らない。ネットワーク、UNC、リムーバブル、リダイレクトされた非ローカルフォルダーは除外/未対応として説明する。キャンセル・アクセス拒否・破損ショートカットは安全に扱う。
- 候補には表示名・ローカルパス・固定引数の有無・対応可否と理由をローカル UI に表示する。検出された引数を無条件に許可リストへ取り込まない。複雑なショートカット引数は手動で構造化・確認できなければ登録不可。
- 手動登録はローカルの exe 選択ダイアログと固定引数の編集、対象の再確認を経由。任意のコマンド文字列や URI を登録する入力欄は作らない。起動許可は明示操作で設定する。
- spec §4 の「アプリ」ページを追加し、候補検出、手動追加、登録情報、許可切替、無効/差し替えの理由、再承認、削除を提供する。ローカルユーザーにだけ実際のパスと固定引数を見せる。MCP 応答・監査・UI エラーに漏らさない。
- WPF の既存 PageViewModel/Navigation 構成、AGENTS.md のスクロール/リスト/テーマ/確認ダイアログ規約に従う。OS/DB/ハッシュ計算は UI スレッド外、選択中のデータを勝手に上書きしない。追加のアプリランチャー UI やタスクマネージャーの再実装は不要。UI の起動・終了の動作確認を提供するなら共通 executor 経由とし、危険操作はローカルで確認する。

## 4. 起動対象の安全性（最重要）

登録時・起動時の両方で同じ安全性判定を適用する。許可リストの登録はローカルユーザーによる信頼判断であり、登録したアプリの内部機能を制限するサンドボックスではない。

- 絶対パスのローカル固定ドライブにある通常の実行可能 PE exe のみに限定する。相対パス・PATH 探索・環境変数展開による動的対象・UNC/ネットワーク・デバイスパス・ADS・フォルダー・.lnk/.url/.bat/.cmd/.ps1/.vbs/.js/.msi/.dll 等の直接実行は禁止する。
- パスの正規化とハンドル由来の最終パス/ボリューム・ファイル識別を検証する。ジャンクション/シンボリックリンク等を暗黙に辿らず、初期方針は対象および親パスの再解析ポイントを拒否する。通常の実行対象として扱えないものは明示的に未対応とする。
- 登録時の実体を固定するため、ファイル ID/ボリュームと SHA-256 等の組合せを初期案とする。実装方法は公式契約と実測に基づく。更新・差し替え・同名ファイルへの変更を検知したら、勝手に追従せずローカル再承認を要求する。署名があることだけで承認済み実体と同一とはみなさない。
- 起動前に対象を開き、必要なら書き込み・削除を拒否する共有モードのハンドルを保持し、実体確認・ハッシュ・最終認可・CreateProcess の完了まで維持する。親パスの置換やハードリンク等の TOCTOU を調査し、採用方式で防げる範囲と Windows API の残存競合を具体的に記録する。安全性を確認できない場合は起動拒否。ファイルハッシュはサイズ/時間を制限し、未完了を承認済みと扱わない。
- シェル、スクリプトホスト、汎用ランタイム、任意コマンド/URL を起動するランチャー、インストーラー、管理・権限操作ツール等は登録/起動の禁止または明示的な安全性審査対象とする。例: cmd、PowerShell、pwsh、wscript/cscript、mshta、rundll32、regsvr32、msiexec、汎用 Python/Node 等。名前だけの denylist を完全な境界と主張しない。必要に応じ PE の製品情報・元ファイル名・署名等を補助し、名前変更による回避を考慮する。判別不能な対象や不適切な固定引数は拒否する。
- 固定引数はローカル承認済み配列のみ。MCP が与えた文字列、表示名、filter、パス、環境変数等を起動引数・コマンドラインに埋め込まない。シェル展開を行わず、Windows の argv エスケープを正しく扱う（空引数、空白、引用符、末尾バックスラッシュ等）。アプリ独自の引数解析やアプリ自体の機能は制限できない旨を説明する。応答・監査に引数を出さない。
- 実行時に lpApplicationName を明示する等、実行対象が argv の解釈や PATH に依存しないことを確認する。作業ディレクトリは承認済み exe の親フォルダー等の固定方式とし、MCP 入力を使わない。任意環境変数の注入、ハンドル継承、標準入出力の公開、シェル/verb/runas は禁止する。
- Sysacta が管理者権限/高 integrity で動作している場合は、通常権限の子プロセスを確実に生成できる正式方式を別途立証しない限り app_launch を非公開・直接呼び出しも拒否する。初期方針は昇格中の起動禁止。UAC の昇格要求を誘発する実行対象は拒否するか、OS の拒否をそのままエラーとする。自動昇格しない。
- Sysacta 自身の別コピー、設定/トークン管理を起動引数で操作する経路等を登録しない。実行対象のハッシュ/固定引数/パスは MCP に返さない。

## 5. 許可リスト更新と最終認可の競合

- 登録の許可・無効化・削除・承認済み実体/引数/世代の更新は、既存 AuthorizationGate.BeginUpdate() の書き込み側で DB をコミットする。待機中に無効化されたアプリを起動/終了できないことを保証する。
- 解決時には登録 ID/世代のスナップショットを固定し、ロック取得後に再取得して一致と allowed を確認する。OS 取得・ハッシュ・プロセスハンドル準備等は最終認可前に完了する。
- 最終認可と登録 ID/世代/allowed の一致判定は同じ AuthorizationGate の読み取り側で原子的に行う。単なる BeginSideEffect() の前の別 DB 読み取りでは競合窓が残る。現行 BeginSideEffect / BeginNextSideEffect が対象固有の条件を評価できない場合は、Core の既存開始点に小さな型付き検証フック等を追加する。全体/クライアント認可・放棄状態・電源遷移通知の既存意味を維持し、対象条件を迂回する経路を作らない。
- 対象固有の最終検証は短い DB/インメモリ条件のみ。ゲート内で OS API、ハッシュ、UI、長時間 await をしない。ReaderWriterLockSlim の再入やロック順逆転を避ける。変更が確定してから開始点に達した要求は拒否、開始後の変更は既存仕様どおり取り消せない。
- 再承認・世代変更後に、待機していた古い要求が新しい実行対象/固定引数に切り替わらないことを確認する。拒否には TARGET_CHANGED / PERMISSION_DENIED 等の固定エラーを使う。
- 状態変更は共通 executor の認可、引数検証、PowerTransitionGate、リソースロック、pending 監査、最終認可を通る。ローカルのアプリ登録/許可設定は管理操作であり、MCP ツールを追加しない。既存管理操作の監査方針に合わせる。

## 6. アプリ一覧・起動

### app_list_available

- 起動許可済みかつ安全性判定上の候補である登録アプリのみを公開する。未許可の検出候補・ローカル登録設定は返さない。app_id、サニタイズ済み表示名、種別、現在の利用可否と固定理由を返す。登録済みだが現在の実体が変更/欠損/非対応ならその旨を明示し、起動可能と断定しない。
- 一覧で高コストな全 exe ハッシュを必須にしない。cheap check と最終起動時の実体検証を区別し、未確認状態を正確に返す。昇格中の起動禁止も明示する。
- 一覧上限（初期案 256、内部登録上限も有限）、件数・truncated、正常な空と失敗を区別する。無効/削除されたアプリの情報をキャッシュから公開し続けない。

### app_list_running

- 許可済み登録アプリと現在のユーザー/セッションのプロセスを安全な実体情報で照合して返す。basename、表示名、PID 単独、ウィンドウタイトルで一致と判断しない。子プロセスや別 exe をアプリ全体として推測しない。
- app_id、表示名、正規のプロセス識別子（pid/start_time）、必要な状態・終了可否等。プロセスの列挙/照合不能・複数インスタンス・切り詰めを明示する。
- 同一アプリの複数プロセスは一覧で分離する。未確認のものを他アプリとして返さない。フルパス・コマンドライン・環境変数・ウィンドウタイトル・ユーザー SID は返さない。

### app_launch

- app_id のみで登録済み固定対象を起動する。既に稼働している場合に別ウィンドウをフォーカスする等の GUI 操作をしない。アプリが複数起動を許容するかは OS/アプリに依存する。初期方針は既存の確実なインスタンスがある場合は no-op / verified（既存実体の存在確認のみ）とし、起動済みか不明な場合に無条件で成功/追加起動しない。採用方針を description に明記する。
- app_id の共有ロック（例: app:{id}）で app_close / 対応 process_terminate と競合を制御する。登録 ID の重複・別名によるロック回避を防ぐ。
- 準備、実体検証、設定世代再確認、キャンセル、BeginSideEffect() の直後に OS のプロセス作成を 1 回だけ行う。開始後の自動リトライ・フォールバックは禁止する。
- API が起動を受理したこととアプリが起動済み/利用可能になったことは別。返せるなら生成したプロセスの pid/start_time を同じハンドルから取得する。ランチャーが別プロセスに引き継ぐ場合等、アプリの UI や永続稼働を保証しない。原則 accepted。結果の不確実性を unknown と区別し、出力は登録 ID・安全な識別子・結果に限定する。
- 生成プロセスのハンドル・スレッドハンドル・承認対象ファイルのハンドルを適切に解放する。タイムアウト後の遅延起動を防ぐため、開始点前のキャンセル・放棄を厳守する。

## 7. プロセス一覧と終了対象の固定

### process_list_running

- 現在の対話ユーザー・同一セッションの通常プロセスを優先し、システム全体の別ユーザー情報・サービス・他セッション・保護プロセスを無制限に公開しない。実装できる対象範囲を明記する。
- pid、正確な start_time、サニタイズ済みのプロセス名、対応する app_id（確実に照合できる場合）、can_terminate と理由を返す。必要なら CPU/メモリの軽量な単時点情報のみ。コマンドライン・環境変数・ファイルパス・ユーザー名/SID・ウィンドウタイトル・詳細な親子ツリーは返さない。
- limit/filter は公開情報のフィルターのみ。列挙は内部上限（初期案 4096）、タイムアウト、キャンセル、安定順序、failed_count/truncated 等を設ける。列挙中に消えた対象・アクセス拒否・開始時刻不明は誤った操作可能 ID を生成しない。
- can_terminate は現在の観測に基づく参考情報であり、将来の権限・安全性を保証しない。強制終了時は独立して検証する。

### 終了対象の安全境界

今回の初期方針は、app_close / process_terminate ともに、明示許可済み登録アプリの正確な exe に紐付く、現在ユーザー・同一対話セッション・通常 integrity のプロセスに限定する。プロセス一覧に存在するだけで終了可能にはしない。対象の登録許可は起動・終了の必要条件であり、app_close/process_terminate 自体の全体/クライアント許可（既定 Off）も必要。

- Sysacta 自身、同一実行ファイル/別コピー、親プロセスや管理経路の基盤、重要 OS プロセス、シェル/ログオン/セキュリティ関連、サービス、保護プロセス、critical process、他ユーザー・他セッション・昇格プロセスは終了しない。
- Windows の公式 API による critical/protection・トークン・セッション・実行対象の判定を調査する。失敗/不明時は終了拒否。特定のプロセス名の denylist は追加防御であって単独の境界ではない。管理者起動時も終了対象を拡大しない。SeDebugPrivilege の有効化、権限昇格、保護解除は禁止。
- 解決は PID + 正確な生成時刻 + 登録 ID/世代等を固定する。対象ロック取得後にプロセスハンドルを開き、GetProcessTimes 等で生成時刻、実体、セッション、ユーザー、権限、保護、終了状態を再検証する。
- TerminateProcess は検証した同じハンドルに対して行う。PID を後から引き直して別ハンドルに書き込まない。必要最小限の権限（QUERY_LIMITED_INFORMATION / SYNCHRONIZE / TERMINATE 等、採用 API の要件を確認）で開く。プロセスの実行イメージとディスク上のファイルの同一性確認の限界、外部変更との競合を文書化する。
- ResolveTargetAsync 中に解放されないネイティブハンドルを取得しない（executor の待機・キャンセル経路でリークし得る）。対象の固定に必要な値を解決し、ハンドルはロック内の実行段階で開き、実完了まで保持して finally/using で解放する。
- app_close と process_terminate は共通 app:{id} と process:{pid}:{start_time} 等のロックを共有し、app_launch も app:{id} を共有する。固定順序で取得し、解決時点の対象が消失・別実体に変化していたら拒否。別インスタンスや別登録に自動で切り替えない。

## 8. 終了操作

### app_close（通常終了）

- app_id のみ。許可済み登録アプリの確実に識別できる対象を解決する。初期方針は対象プロセス 1 件・安全に識別できるトップレベル通常ウィンドウ 1 件に限定する。複数プロセス/ウィンドウ、バックグラウンドのみ、ウィンドウなし、対象不明は NOT_SUPPORTED/TARGET_CHANGED 等で拒否し、最初のものを選んだり一括終了したりしない。
- WM_CLOSE 等の公式な通常終了要求のみ。ウィンドウハンドルが再利用され得るため、対象プロセスの生存と PID/生成時刻、HWND の所有、同一対象であることを最終準備後に再確認する。OS による外部競合を完全には防げないこと、採用 API の限界を文書化する。安全に同一対象へ限定できない方式は不採用とする。
- 最終認可・キャンセル後に 1 回だけ終了要求を送る。アプリが保存確認を表示、終了を拒否、要求を遅延処理することは正常にあり得る。ユーザーの確認ダイアログを自動操作しない。強制終了へフォールバックしない。
- API 受理のみなら accepted、元のプロセスハンドルが終了を示した場合のみ verified。ウィンドウが消えただけでプロセス終了と断定しない。対象が存在しないことを確実に確認した場合の no-op と、識別不能/列挙失敗を区別する。
- ハングしたウィンドウに無期限の SendMessage を行わない。要求の受理が不明なら unknown、再送しない。

### process_terminate（強制終了）

- pid と start_time の組で指定する。許可済み登録との照合、保護判定、同一ハンドルによる生成時刻確認は省略しない。PID が再利用されていた場合は TARGET_CHANGED、古いプロセスが消失した場合は TARGET_NOT_FOUND 等で拒否。
- 最終認可と対象固有の許可/世代確認後、検証済みハンドルに TerminateProcess を 1 回だけ実行する。子プロセス・プロセスツリー・同名アプリを連鎖終了しない。exit code は固定値。force、任意 exit code、kill_tree 等の引数は追加しない。
- API の受理と実終了を区別し、同じハンドルの終了シグナルで確認した場合 verified、受理のみなら accepted、受理不明なら unknown。対象の消失を別の PID の状態で判断しない。開始後は retryable=false、自動再試行しない。
- データ消失の可能性を description とローカル UI に明記。MCP 実行中の確認ダイアログは要求しない（事前の明示許可による設計）。既定 Off かつ管理画面の一括有効化で自動有効にしない。

## 9. 実行制御・情報最小化

- 全状態変更で pending 監査を永続化し、監査不能なら OS 操作なし。電源遷移中は変更しない。登録 ID、解決済み pid/start_time 等の最小の安全な識別情報だけを監査する。生の app_id / filter / パス / 固定引数 / コマンドライン / 環境変数 / SID / ハッシュ / 生例外 / 結果全文を記録しない。
- 表示名とプロセス名は外部データとして長さ・制御文字・パス/URI 等を検証する。結果の失敗・制約は固定文言と型付き理由。登録に関連するローカルの実パス表示以外は AGENTS.md の情報秘匿を維持する。
- GetAvailability は安価・副作用なし。昇格中に安全な起動を保証できない場合は app_launch を非公開、直接呼び出しも拒否。未登録/対象消失/一時 API エラーは全体の恒常非対応にしない。
- キャンセル・タイムアウト・失効後に新規の OS 変更や追加収集を開始しない。非キャンセル可能処理は実完了までスロット・ゲート・ロック・必要なハンドルを保持する。準備と開始を分離し、BeginSideEffect/BeginNextSideEffect から実際の OS 呼び出しまでに長い処理を入れない。
- OS の受理と変更の確認を区別する。成功を偽装しない。新規 HTTP エンドポイント・任意クエリ・永続的なプロセス監視・履歴・バックグラウンドキューは作らない。
